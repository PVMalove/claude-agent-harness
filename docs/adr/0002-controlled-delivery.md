# Контролируемая поставка изменений

## Контекст системы

Харнесс работает в проектах с разными базовыми ветками, трекерами, языками и командами
проверки. Агент может подготовить изменение, но защищённые ветки и решение о включении
изменения принадлежат разработчику. Тикет и проверяемые evidence связывают задачу с
конкретным commit.

## Действующий контракт

`.harness/project.json` задаёт `base_branch`, `branch_pattern`, язык и `qa_gate_commands`.
Работа начинается с зарегистрированного тикета и ведётся в изолированной issue-ветке.
Дочерний тикет берёт точную `integration/<service-or-team>` ветку из своего epic; тикет
без epic — `base_branch`. Ветка создаётся от этой базы, а не от случайного текущего checkout.
Git и операции трекера выполняются через CLI (`git` и `gh` либо `glab`). Тикет фиксирует
scope, блокеры и требуемую ветку; QA выполняет команды проекта. До коммита проверяются
результаты локальных тестов, а до PR — полный quality gate.

PR открывается лишь после отдельного подтверждения разработчика. Его тело хранится в файле
и передаётся CLI через `--body-file`; результаты проверок и риски указываются фактически.
Merge в integration или базовую ветку делает только разработчик вручную. Для PR в default
branch используется `Closes #<ID>`, для PR в integration — `Related to #<ID>` с явным
закрытием тикета после подтверждённого merge. Автоматическое завершение тикета проверяется,
а не предполагается.

## Операционные последствия

Тикет, база ветки, проверенный commit, результаты QA и approval должны быть доступны для
ревью. Агент не пишет напрямую в защищённые ветки и не выполняет merge. Изменение
`project.json` требует согласования схемы, валидатора, шаблона и руководства;
`harness health` проверяет контракт проекта.
