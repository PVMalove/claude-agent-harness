# Улучшения харнесса разворачиваются 4 фазами, каждая гейтится зелёным `scripts/verify`

## Context

Владелец репозитория принёс список из 10 улучшений вперемешку: единый стандарт ADR, диагностика
`harness init`, smoke-тесты критичных сценариев CLI, drift-стратегия для вендоренного апстрима,
документация «когда что использовать», явная схема `.harness/project.json`, привычка гонять
health/registry/diff после правки capability, и отдельная roadmap-ADR — от чистой документации
до CI и кода `harness/bin/harness`/`bin/install-global`. Список сам себя приоритизировал на 4 фазы
(`Phase 1: язык + ADR-шаблон + диагностика`, `Phase 2: smoke-tests + health checks`,
`Phase 3: drift-стратегия + docs clarity`, `Phase 4: roadmap ADR + polish`), но не решал, что именно
входит в каждую фазу технически и в каком виде.

## Decision

Каждая фаза — отдельный проход, начинается только по прямому «переходим к Phase N» и заканчивается
зелёным `python scripts/verify`. Итог по фазам:

- **Phase 1** — `docs/adr/template.md` (5 обязательных секций) + правило в README «Политика
  репозитория»; `harness/bin/harness` и `bin/install-global` получили проверку версии Python и
  сообщения об ошибках с конкретной командой-фиксом, а не только именем флага (важный нюанс:
  подсказка зависит от вызвавшей команды — `init` не умеет `--replace-conflicts`, в отличие от
  `adopt`); новый раздел Troubleshooting в `docs/agents/harness-guide.md` (обе копии).
- **Phase 2** — дополнен `scripts/test-clean-room`: `registry` как отдельная команда (раньше
  проверялась только как побочный эффект `init`), полный прогон `pvmalove-suite`
  (extends/overrides/additions, ADR 0001) — раньше не тестировался вообще, негативный тест на
  коллизию имён при выборе `mattpocock-suite` + `pvmalove-suite` одновременно, и fallback
  `check-branch-name.sh` на отсутствующий `.harness/project.json`.
- **Phase 3** — три проверки в `scripts/verify`, поймавшие два реальных, уже случившихся
  расхождения (`harness-guide.md` называл 7 переопределённых скиллов вместо 8, README забыл
  `harness-guide.md` в собственном перечислении файлов, которые сам же и разворачивает): сверка
  `docs/agents/*.md` с `harness/project/docs-agents/*.md` по содержимому (без учёта BOM/CRLF),
  сверка `{...}.md`-перечислений с реальными файлами, сверка таблицы раздела 7 с
  `CAPABILITIES.json`. Плюс `scripts/check-upstream-drift` (сеть, только читает) и периодический
  `.github/workflows/upstream-drift.yml` (раз в неделю, `workflow_dispatch` вручную — не блокирует
  PR) — показывает, что из вендоренного апстрима реально поменялось, и какие переопределённые
  скиллы стоит сверить руками (ADR 0002). Плюс 4 таблицы «когда что использовать» в разделе 0.
- **Phase 4** (эта фаза) — эта ADR; `harness/project/project.schema.json` для
  `.harness/project.json` (JSON Schema, деплоится рядом с `project.json` через
  `scaffold_pvmalove_extras`, `$schema`-ссылка для автодополнения в редакторе) плюс ручная
  валидация формы в `harness health`; заточенная (не новая) строка в `AGENTS.md` — после правки
  `harness/CAPABILITIES.json` или `skills/` гонять `scripts/verify`/`scripts/test-clean-room`
  против одноразовых репозиториев, которые он сам создаёт.

Статус: все 4 фазы выполнены на момент создания этой ADR.

## Alternatives

- Один большой проход по всем 10 пунктам сразу вместо 4 гейтированных фаз.
- Автоматический бот, который сам открывает PR с ресинком вендоренного апстрима при обнаружении
  дрейфа, вместо read-only отчёта.
- Проверка «апстрим ушёл вперёд» как обязательный шаг в `verify.yml` на каждый PR, а не отдельный
  periodic workflow.

## Rejected

- **Один большой проход**: отклонено — каждая фаза трогает разные системы (доки, CLI-код, CI,
  process-конвенции), отдельные проходы с `scripts/verify` между ними держат откат дешёвым и не
  смешивают ревью.
- **Авто-PR-бот для ресинка апстрима**: отклонено — резолвинг конфликтов между апстримным
  изменением и first-party-переопределением (8 скиллов, ADR 0002) требует человеческого суждения;
  скрипт остаётся read-only, финальное решение принимает мейнтейнер.
- **Апстрим-дрейф проверка на каждый PR**: отклонено пользователем явно — сетевая проверка в
  обязательном чеке добавляет риск флейка и будет шуметь о дрейфе апстрима на PR, вообще его не
  касающихся. Выбран periodic workflow.
- **`default_capability` в `.harness/project.json`** (опциональное поле из исходного списка):
  отклонено — `harness.lock` уже хранит `capabilities` и `harness update` уже читает его как
  дефолт при отсутствии `--capability` (`cmd_update`, `harness/bin/harness`); второе поле с тем же
  фактом воспроизвело бы ровно ту проблему «дрейф между двумя источниками», которую эта же фаза
  устраняла в других местах (Phase 3).
- **Валидация `.harness/project.json` через пакет `jsonschema`**: отклонено — репозиторий нигде не
  тянет сторонние Python-пакеты (`hashlib`/`json`/`subprocess`/`argparse`... — только stdlib);
  схема остаётся редактор-facing документацией, а фактическую проверку в `harness health` делает
  рукописный код на тех же правилах.

## Consequences

`scripts/verify` стал медленнее (три новые сверки плюс более полный `test-clean-room`), но ловит
классы дрейфа, которые раньше проходили молча — два таких случая он поймал бы, будь эти проверки
написаны раньше. Новый periodic workflow требует, чтобы кто-то время от времени смотрел на его
статус — обычный `verify.yml` этого не покажет. `project.schema.json` для уже развёрнутых
`pvmalove-suite`-проектов появится не сразу, а на следующий `harness update`/`adopt` — тот же
`_copy_if_absent`, что и у остальных файлов, деплоится при отсутствии, а не переписывается заново,
но и не привязан к тому, свежий ли рядом `project.json`.
