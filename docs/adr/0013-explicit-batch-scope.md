# Явный scope batch вместо backend zone

## Контекст системы

ADR 0004 привязывал каждую роль к именованной backend zone, а coordinator не давал запустить два
batch в одной зоне. Зона работала как замок планировщика: batch с пересекающимися файлами не могли
идти параллельно, хотя у каждого своя issue-ветка и worktree, а пересечения всё равно решаются при
интеграции. Новому проекту при этом приходилось объявлять зоны до первого batch. Граница полномочий
writer-а должна быть явной и проверяемой, а не следовать из имени зоны.

## Действующий контракт

Часть ADR 0004 о backend zone заменена этим ADR; остальное в 0004 действует.

- Batch закрепляет `allowed_paths` — явный scope записи (`batch create --allowed-path`, повторяется).
  Он входит в immutable plan и в `write_paths` каждого brief writer-а. Brief, checkpoint и completion
  report отклоняются, если меняют файл вне этого scope. Исключение (#633): completed-отчёт developer с
  `changed_files` вне `write_paths` записывается как предупреждение `scope_warnings`, которое
  принимает только `override-warning` с `--note` и явным `--approved-by`; так же `accept` architect-плана
  с `expected_paths` вне `allowed_paths` записывает предупреждение, а не отклоняется. Batch без scope не создаётся.
- Потолок записи роли — `write_paths` в assignment plan, по умолчанию весь репозиторий. Scope batch не
  может быть шире потолка; потолок проверяет и `batch create`, и `dispatch create`.
- Zone необязательна. Поле `zone` в batch, brief и `dispatch_preflight` остаётся историческим
  аудит-полем (`null` у новых записей), `backend_zones`, `zone` в assignment plan и `low_risk_zones`
  остаются валидными и отображаются на пути. Конфиг, ledger и briefs с зонами принимаются обычным
  путём обновления; immutable briefs, reports и pinned runtime snapshots не переписываются.
  Batch, запланированный до явного scope, ограничен потолком роли, как и раньше.
- Единственный предел параллелизма — `concurrency_budget`: превышение отклоняется с remedy, который
  называет бюджет. Замка по зоне и по пересечению файлов нет; занятая serialized QA lane не мешает
  параллельной реализации.
- Повтор незавершённой работы отклоняется при создании batch: тикет, issue-ветка и worktree другого
  незавершённого batch (включая `blocked` с открытым dispatch, пока его не возобновили или не прекратили;
  `blocked` после решения `block`, где все dispatch закрыты, считается завершённым). Один writer на
  batch и запрет записи в protected и integration ветки не меняются.
- `approval_policy: low_risk` берёт `low_risk_paths`: batch подходит, только если весь его
  `allowed_paths` лежит внутри них. Сравнение идёт по сегментам пути: граница `dir/**` принимает только
  пути под `dir`, а формы с `./`, `//`, `..`, ведущим `/` или `\` отклоняются. Без `low_risk_paths` ничто не считается низкорисковым. Legacy
  `low_risk_zones` отображается на пути своих зон, а batch без scope по-прежнему определяется своей
  зоной, поэтому автопринятие не расширяется. Ручные risk и publish gates остаются.

## Операционные последствия

- `harness health` и schema принимают конфиг без `backend_zones` и без `zone` в планах.
- Координатор указывает `--allowed-path` при `batch create`; skill `/implement` и playbook требуют
  этого, а при превышении бюджета подсказывают дождаться активного batch или поднять
  `concurrency_budget`.
- Ключ идемпотентности read-only dispatch больше не сравнивается между batch: независимые batch на
  одной базе не конфликтуют, а дубль работы отсекается при создании batch.
- Clean-room проверяет установку без зон, обновление проекта с зонами в конфиге и ledger, а также
  параллельные batch с пересекающимся scope.
- Учёт после публикации (интеграция, rebase, конфликты) не входит в этот контракт.
