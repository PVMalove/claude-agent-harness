# Маршруты восстановления `/implement`

## Контекст системы

После отчёта воркера batch может пойти не по плану. Отчёт расходится с commit plan или несёт
дефект, integration base уходит вперёд, read-only роль выполняет задание не полностью, а hook,
классификатор безопасности или ledger мешает законному действию. Без закрытого набора маршрутов
coordinator решает каждую такую ситуацию вручную: батч упирается в тупик, работа повторяется в
новом batch, история candidate переписывается без нужды. Маршрут должен быть самым дешёвым из
корректных и сохранять уже проверенное evidence.

## Действующий контракт

### Приоритет и полномочия

Цели по убыванию: сохранить проверенное evidence, не перезапускать batch, сократить число
dispatch, сократить число approvals, сохранить чистоту истории. Переписать историю candidate
можно только по approval человека.

Маршрут записывается в routing record полем `route` (закрытый enum). Coordinator вычисляет его из
структурного evidence, а не из свободного текста; decision packet показывает маршрут до решения.
Audit хранит маршрут, ссылки на evidence и approver (policy или человек).

- Маршрут без нового dispatch и без смены candidate исполняет сам coordinator. Это повтор
  `dispatch wait` или `dispatch status`, докат policy-шага, снятие зависшего lock после проверки
  владельца, эскалация сбоя инструмента.
- Маршрут с новым dispatch проходит обычный dispatch approval по `approval_policy`.
- Abandon, замещающий batch и rebase утверждает только человек.

### Маршруты

| Ситуация | Маршрут |
| --- | --- |
| Число коммитов расходится с планом | По #478: план architect, сопоставление многие-ко-многим, покрытие DoD и обоснование расхождения. |
| Coordinator нашёл дефект в чистом developer-отчёте | Accept. Находка координатора уходит перенесённым пунктом в brief code-review; один fix-forward после review закрывает её вместе с findings ревьюера. Retry без accept (#477) допустим, только если не выполнен пункт DoD или изменения вышли за зону. |
| Нужен дополнительный коммит | Fix-forward: developer-retry, продолжающий candidate, с закрытым списком перенесённых пунктов. Snapshot обязан быть предком нового SHA. Отдельного типа перехода нет. |
| Integration base ушла вперёд | Review, QA и publish проверяют закреплённый candidate; финальное обновление базы выполняет `integration refresh` при подготовке PR (ADR 0014). Rebase внутри developer-retry остаётся маршрутом для конфликта и для работы, которой нужен developer: он выполняется в том же retry, что и исправление. Каждый коммит прежнего candidate либо указан ровно один раз как `rebased_from`, либо помечен удалённым с причиной. Пары сверяются по patch-id: расхождение допустимо, но помечается. |
| Hook заблокировал законную команду | Воркер не обходит блокировку другой формой команды. Он останавливается с блокером `tooling`: инструмент, команда, сообщение. Coordinator подтверждает ложное срабатывание, заводит bug-тикет и делает operational retry того же этапа. |
| Read-only роль выполнила задание не полностью | Отчёт перечисляет неполные пункты: пункт, причина, целевая роль. Такой отчёт не принимается автоматически. Человек выбирает: accept с переносом пунктов в brief следующей роли или суженный retry той же роли. Прерывание классификатором безопасности относится к `tooling`. |
| Ledger занят | `dispatch wait` и `dispatch status` считают занятый lock временным и опрашивают дальше до timeout. Если `report submit` упал после записи отчёта, он называет невыполненный шаг и команду докатки. Зависший lock снимает команда с проверкой владельца; файлы state руками не правят. |

### Сбой инструмента

`tooling` — операционная категория причины. Coordinator присваивает её только по структурному
evidence; без него причина остаётся `unknown`. Такой retry не расходует `max_developer_retries`.
- Read-only роль повторяется на том же SHA.
- Developer перезапускается от своего последнего коммита. Незакоммиченные изменения переходят в
  новый dispatch, если их список точно совпадает с отчётом и лежит в allowed paths; всё прочее
  отклоняется preflight.
- Больше двух `tooling`-retry подряд на одном candidate поднимают attention.

### Review после fix-forward

Delta-review проверяет новые коммиты и закрытие перенесённых пунктов, а прежний review-отчёт
служит evidence. Rebased-коммиты с совпавшим patch-id считаются проверенными. Полный review нужен,
если новые коммиты дают новые risk triggers или меняют файлы вне перенесённых пунктов, среди пар
есть расхождение patch-id, rebase отбросил коммит прежнего candidate или новых коммитов для
проверки нет. Clean-room QA всегда идёт на новом SHA.

### Abandon

`batch create --supersedes <batch>` с approval человека создаёт замещающий batch. Если DoD тот
же, в него переносятся принятый отчёт architect и план коммитов. Candidate из `last_accepted`
становится snapshot, если он потомок текущей базы; иначе применяется маршрут rebase. Risk, review
и QA проходят заново. Решения оператора не копируются, на них остаётся ссылка.

### Отклонённые варианты

- **Отдельный переход fix-forward со своим бюджетом.** Он дублирует developer-retry, который после
  #477 продолжает candidate.
- **Merge integration base в issue-ветку вместо rebase.** Он сохраняет SHA, но делает историю
  issue-ветки нелинейной.
- **Retry без accept как маршрут по умолчанию.** Он тратит единственный developer-retry до review,
  и review-blocker после этого ведёт только в block, fail или abandon.

## Операционные последствия

- ADR 0005 сужается в двух пунктах. Rebase больше не обязан идти отдельным developer-dispatch.
  Delta-review разрешён не только для test-only исправления.
- Нормативная таблица маршрутов живёт в `harness/orchestration/playbook.md`, CLI-уровень — в
  `docs/backend-orchestration.md`. `/implement` ссылается на таблицу, а контракты ролей
  запрещают обход hook-а и описывают неполные пункты.
- Контракт реализуют тикеты, нарезанные из #479. До их слияния coordinator работает по ADR 0005.

## Уточнение lifecycle и ручного восстановления (#662)

`blocked`/`failed` — восстанавливаемые состояния, `paused` — записанная остановка автоматического
пути. Завершение без реализации записывается как `completed` с отдельным evidence
`not_required` и `completion_kind: no-implementation`, без фиктивного publish или commit.
Старое `not-required` остаётся читаемым терминальным состоянием.
Оба abandon-пути означают явный отказ оператора: `abandoned` с `last_accepted`. Старое
`failed + abandoned` допускает supersede только при recorded human abandon, без переписи источника.

`environmental-restart` повторяет ту же работу после подтверждённого сбоя запуска с отдельным
операционным бюджетом. `rewind` выбирает прежний достигнутый gate и исключает зависимое старое
evidence. Новая code-попытка расходует developer retry budget. Оба пути требуют человеческого
approval и остаются manual_all. Sealed events и startup evidence связываются с audit; наблюдение
`auto-report` ничего не пишет, `ledger validate` ничего не исправляет.
