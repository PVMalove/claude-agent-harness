# `triage` возвращается к namespaced-таксономии (`workflow::*`/`hitl`/`afk`); `epic::<slug>` заменён на native sub-issues

ADR 0004 зафиксировал как контекст, что `triage` уже был first-party override'ом с таксономией `hitl`/`afk` + `type::*` + `workflow::*`, и был откачен обратно к каноническим ролям апстрима (`bug`/`enhancement` + 5 состояний). Причина того первого отката до нас не дошла — сохранился только факт отката, не обоснование (сама история репозитория была squash'нута в один коммит раньше). Сейчас возвращаем `workflow::*`/`hitl`/`afk` заново (`skills/first-party/pvmalove/triage/`, override зарегистрирован в `pvmalove-suite`), потому что канонические 5 состояний не умеют выразить «тикет сейчас в работе» (`workflow::in-progress` — состояния, которого в апстримной модели нет вообще) и не отличают «эпик ещё проектируется» от «тикет готов к взятию» — обе ситуации канон сваливает в `ready-for-agent`/`ready-for-human`.

В отличие от версии до ADR 0004, категорийная ось (`bug`/`enhancement`) в этот раз остаётся канонической — `type::*` не возвращается. Ось `workflow::*` расширена четвёртым значением, `workflow::specs`, которое полностью заменяет `epic::<slug>`: эпик, ожидающий декомпозиции, теперь просто `workflow::specs` на самом issue, а группировка дочерних тикетов идёт через нативные GitHub sub-issues (`docs/agents/issue-tracker.md#wayfinding-operations`) — тот же механизм, которым уже пользуется `wayfinder` для своей карты, вместо отдельного лейбла-слага, который приходилось создавать ad hoc под каждый эпик.

Решение ADR 0004 о том, кто снимает блокировку (`implement`, а не `triage`, проверяет блокеры и снимает лейбл в момент старта работы, а не отдельным проходом триажа), сохранено без изменений — просто переориентировано на `workflow::blocked`/`workflow::ready` вместо узкого `blocked-by-ticket`. Аргументация ADR 0004 (не нужен отдельный шаг, который кто-то должен не забыть запустить) не зависит от имени лейбла.

`task-report::required` в версии до ADR 0004 был частью state machine `triage` (применялся на шаге «Apply the outcome»). В этот раз он — целиком поведение `/implement` (пишет отчёт о завершении при закрытии тикета); лейбл ставят `/to-spec`/`/to-tickets` по умолчанию, `triage` его не читает и не применяет.

**Rejected**: оставить `workflow::*`/`hitl`/`afk` контекстными лейблами поверх нетронутого vendor `triage` (по образцу `epic::<slug>`/`blocked-by-ticket`). Отклонено — состояние пайплайна (workflow) это ровно то, чем управляет state machine `triage`, а не довесок сбоку; держать два параллельных state machine (канонический внутри `triage`, `workflow::*` снаружи) хуже, чем один явный override.

**Rejected**: `workflow::specs` сосуществует с `epic::<slug>` (первый — стадия, второй — принадлежность к эпику). Отклонено в пользу единого паттерна группировки на весь репозиторий — тот же native sub-issue link, которым уже пользуется `wayfinder`, без дублирующего лейбла-слага.

**Rejected**: вернуть `type::*` вместо `bug`/`enhancement`, как было до ADR 0004. Отклонено — в этот раз проблема именно в видимости *состояния* пайплайна, категорийная ось не мешает и не помогает её решить.
