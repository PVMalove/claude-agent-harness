# Вести поставку изменений через явные проектные контракты

## Контекст

Coding agent может подготовить изменение, но не должен сам получать полномочия на публикацию,
слияние или необратимые операции. Команды проверки, ветки и язык результата различаются между
проектами.

## Решение

`.harness/project.json` хранит проектный контракт: базовую ветку, шаблон issue-ветки, язык и
команды QA. Работа начинается с тикета, выполняется в изолированной issue-ветке от зафиксированной
integration-ветки, проходит тестирование, независимые оси review и QA. Создание PR требует
отдельного подтверждения разработчика; merge всегда ручной. Таксономия `workflow::*`, `hitl`/`afk`
и native связи тикетов делают состояние работы явным для людей и инструментов.

## Альтернативы

- Давать агенту прямой доступ к базовой ветке и merge.
- Хранить workflow только в prompt каждой сессии.
- Использовать одинаковые команды QA для всех проектов.

## Почему не они

Прямой доступ смешивает подготовку и выпуск. Prompt не является проверяемым состоянием и теряется
между сессиями. Универсальный QA не отражает реальный стек проекта.

## Последствия

Перед реализацией требуется тикет, а перед PR и merge — человеческие решения. Владельцы проекта
поддерживают `.harness/project.json` и документируют фактические команды проверки.
