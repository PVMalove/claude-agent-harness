## 2. Полный перевод текста скила

````text
---
name: to-tickets
description: Разбейте план, спецификацию или разговор на набор tracer-bullet тикетов с блокирующими рёбрами и опубликуйте их в настроенном трекере.

# В тикеты

**Цель:** разбить план, спецификацию или разговор на набор **тикетов** — tracer-bullet вертикальных срезов, каждый из которых объявляет свои блокирующие рёбра.

Вам уже должны быть предоставлены трекер задач и словарь triage-меток. Если `docs/agents/issue-tracker.md` или `docs/agents/triage-labels.md` отсутствует, скажите пользователю запустить `harness update` — он создаёт оба файла из шаблонов харнесса.

## Выполнение в двух фазах

Выполняйте скил в две фазы: ничего не публикуйте в трекере задач и не создавайте локальные файлы, пока пользователь явно не одобрит разбиение на тикеты.

### Фаза 1: подготовка и review

1. **Соберите контекст:** работайте из контекста разговора. Если передана ссылка (путь к спецификации, номер/URL issue), прочитайте полное тело и комментарии.
2. **Исследуйте кодовую базу (необязательно):** используйте глоссарий домена проекта. Ищите возможности prefactoring («сделайте изменение лёгким, затем сделайте лёгкое изменение»).
3. **Подготовьте вертикальные срезы:** разбейте работу на **tracer bullet** тикеты.
   - *Вертикальные срезы:* проложите узкий, но ПОЛНЫЙ путь через каждый слой (схема, API, UI, тесты). Он должен быть демонстрируем/проверяем сам по себе и помещаться в одно контекстное окно.
   - *Широкие рефакторинги (исключение):* если изменение имеет огромный радиус воздействия (например, переименование общего столбца), используйте **expand-contract** вместо вертикального разбиения. Последовательность: Expand → Migrate (пакетами) → Contract.
   - *Блокирующие рёбра:* задайте каждому тикету его блокирующие рёбра (какие другие тикеты должны завершиться первыми).
   - *Оценка времени человека:* оцените примерное время, нужное разработчику-человеку для завершения этого среза (например, «2 часа», «1 день») — для каждого тикета, включая `afk`, а не только `hitl`. Это сигнал качества декомпозиции, а не обязательство: оценка в неделях означает, что срез не tracer-bullet размера — разбейте его ещё до показа пользователю.
4. **Подготовьте Discovery Context, если у родителя есть `## Relevant Files (Discovery Context)`:** назначьте каждый путь всем тикетам, которым он действительно нужен; для каждого сохраните исходное пояснение и добавьте короткую причину для тикета. Если путь не относится ни к одному срезу, покажите его как **unassigned** и остановитесь для решения пользователя.
   - Постройте **Path inventory**: пути из Discovery Context, их содержащие директории, а также существующие `tests/` и `shared/`. Не читайте и не отправляйте содержимое файлов и сигнатуры символов; применяйте стандартные исключения (секреты, зависимости, build/dist, cache, generated/minified, большие логи, базы, временные данные и несвязанное media). Root-файл включайте только как файл.
   - Выполните ровно один cheap-model advisory call на весь batch (если runtime умеет закрепить модель — `haiku` или самый дешёвый эквивалент). Передайте названия, scope, назначенные пути и Path inventory. Advisory может вернуть только точные дополнительные пути из Path inventory с причиной; он не удаляет/перемещает назначенные пути, не изобретает новые и не меняет scope. Без дешёвого маршрута остановитесь с blocker.
   - Добавьте только валидные advisory-зависимости в Discovery Context соответствующего тикета. Итог готов, когда каждый исходный путь назначен либо явно показан как unassigned, а каждое добавление трассируется к Path inventory.
5. **ОСТАНОВИТЕСЬ И СПРОСИТЕ (опросите пользователя):** представьте предложенное разбиение нумерованным списком. Для каждого тикета покажите:
   - **Название:** короткое описательное имя;
   - **Заблокирован:** какими тикетами он ограничен;
   - **Оц. время (человек):** оценённое время человека на завершение;
   - **Что он поставляет:** сквозное поведение;
   - **Relevant Files (Discovery Context):** назначенные и добавленные advisory-пути с причинами; опускайте поле, если у родителя нет Discovery Context.
   - *Спросите пользователя:* правильно ли выбрана гранулярность? Верны ли блокирующие рёбра? Что-то следует объединить/разделить? Реалистична ли оценка времени?
   - Остановитесь здесь, пока пользователь не одобрит разбиение.

### Фаза 2: публикация и резюме (после одобрения)

1. **Опубликуйте в трекере:** метод зависит от настроенного трекера:
   - **Integration-ветка:** прочитайте раздел родительского эпика `## Integration Branch` до записи любого дочернего тикета. Скопируйте его точное имя ветки в каждый дочерний тикет; если у эпика нет integration-ветки, остановитесь и сообщите об отсутствующем prerequisite вместо вывода ветки.
   - **Локальные файлы:** запишите один файл на тикет под `.scratch/<feature-slug>/issues/<NN>-<slug>.md` (01, 02...). Используйте `<local-ticket-template>`. Установите `**Workflow:**` в `status::blocked`, если есть блокеры, иначе в `status::ready`. Установите `**Execution:**` в `hitl` или `afk` по лучшему суждению о тикете (см. `docs/agents/triage-labels.md`). Добавьте `**Task report:** required`, если не сказано пропустить (полностью опустите строку, если не требуется). `/fast-implement` находит следующий тикет, читая поле `**Workflow:**` каждого файла — исключительно линейная цепочка разрешается сверху вниз.
   - **GitHub / GitLab:** `<project-url>`, `<host>` и `<project-id>` в командах GitLab определены в `docs/agents/issue-tracker.md` → GitLab → Conventions.
     - Опубликуйте один issue на тикет в порядке зависимостей по `<issue-template>`. GitHub: `gh issue create --body-file <path>`. GitLab: `glab issue create -R <project-url> --title '<title>' --description-file <path> --yes`; номер тикета — последний сегмент URL issue, который печатает команда. Не передавайте тело inline через `--body`/`--description` или heredoc — это ломает shell quoting (см. `docs/agents/git-workflow.md` §1).
     - Примените метки (полную таксономию смотрите в `docs/agents/triage-labels.md`): `bug`/`enhancement`, `status::ready` (или `status::blocked`, если тикет ограничен другим тикетом в этом batch), `hitl`/`afk` и `task-report::required`, если не сказано пропустить. GitLab: `glab issue update <n> -R <project-url> --label '<label>,<label>'`; метку, которой ещё нет в проекте, GitLab молча создаёт с цветом по умолчанию, поэтому `/setup-labels` должен быть выполнен заранее.
     - *Группировка:* свяжите каждый тикет с родительским эпиком через родительскую связь трекера. НЕ используйте метки `epic::<slug>`.
       - GitHub: свяжите тикет с эпиком как **нативную подзадачу** (sub-issue).
       - GitLab: секция `## Parent: #<epic>` в тикете плюс ровно одна связь `relates_to` от тикета к эпику, созданная сразу после тикета: `glab api --hostname <host> --method POST projects/<project-id>/issues/<n>/links -F target_project_id=<numeric-project-id> -F target_issue_iid=<epic> -F link_type=relates_to`. `<numeric-project-id>` — поле `id` из `glab api --hostname <host> projects/<project-id>`; получите его один раз на batch. Блокирующие рёбра остаются в строках `Blocked by #<M>`; связи между тикетами не создаются. Epics, связи `blocks` и нативная иерархия issue — возможности GitLab Premium, и они не используются.
     - *Локальное зеркало:* спецификация эпика уже находится в собственной папке под `docs/tasks/` (согласно `docs/agents/artifacts.md`) — сначала переименуйте эту папку в `issue-<epic-id>-<epic-slug>/`, если она всё ещё содержит только slug. Сохраните тело issue каждого опубликованного тикета в той же папке как `issue-<ID>-<slug>.md`.
     - *Frontier:* не прослеживайте `Blocked by` вручную, чтобы узнать, что можно взять, — запросите его: те же поля и механизм, что у frontier-запроса `/wayfinder` для настроенного трекера (`docs/agents/issue-tracker.md#wayfinding-operations`), но ограниченный дочерними тикетами эпика вместо дочерних элементов карты: его GitHub sub-issues, а на GitLab связанными с эпиком issue, в описании которых есть `## Parent: #<epic>`. `/fast-implement` выполняет этот же запрос сам, когда ему передан эпик вместо конкретного тикета.
     - Не закрывайте и не переписывайте родительское issue эпика, кроме добавления короткого списка созданных номеров подзадач.
2. **Сделайте резюме batch:**
   - Прочитайте `language` из `.harness/project.json` (по умолчанию `ru`, если файла или поля нет) — это определяет только колонку «Что построить» ниже, а не названия/тела публикуемых тикетов, которые остаются на том языке, на котором вы их подготовили.
   - Если этот runtime поддерживает dispatch sub-agent, закреплённого за конкретной моделью, отправьте один вызов с `model: haiku` (самая дешёвая доступная, один вызов на весь batch) — передайте ему название и тело каждого тикета плюс целевой язык, попросив одно краткое предложение для каждого тикета на этом языке. Иначе напишите описания сами, собственной моделью, на том же языке.
   - Выведите итоговую таблицу, объединяющую все данные. Колонка меток должна перечислять все применённые теги таксономии (например, `enhancement`, `status::ready`, `afk`, `task-report::required`).

   | Тикет | Что построить | Оц. время (человек) | Метки |
   |---|---|---|---|
   | <номер/ссылка/путь> | <однострочное резюме> | <время> | <метки через запятую> |
````

## 3. Контракты

- **Вход (Input/Brief):** план, спецификация либо контекст разговора; родительский эпик и его integration-ветка; явное одобрение предлагаемой декомпозиции.
- **Выход (Output/Report):** tracer-bullet тикеты с зависимостями, метками, оценками и локальным зеркалом; итоговая таблица batch.
