# Реализация

**Цель:** Пройдите один тикет через архитектора → разработчика → проверки кода → контроля качества, сделав паузу для
явное одобрение разработчика на каждом этапе и передать готового кандидата `/to-pull-requests`.

Эту сессию **ведёт** координатор. Он управляет `coordinator.py` — партия, отправка, отчет, решение —
и никогда не редактирует файлы реализации самостоятельно. Работа выполняется распределенными ролями.

Это пятый этап цепочки доставки — `/grill-with-docs` → `/to-spec` → `/to-tickets` →
**`/implement <id>`** → `/to-pull-requests` — и оттуда требуется ровно один билет
разложение.

команда: CLI упаковщика находится в репозитории жгутов, а не в связанном проекте, поэтому

`.harness/orchestration.json` является **необязательным**. Без этого координатор по умолчанию устанавливает зону в
весь репозиторий (`repository`) и берет модель роли и усилия из этого сеанса, передаваемые как
`--model`/`--effort` на `dispatch create`. Благодаря этому проект владеет зонами, моделями, усилиями и
для каждой роли `transport`.

Если эта команда отсутствует или ее выход не равен нулю, не исправляйте и не делайте вывод о согласии: остановитесь и сообщите об этом
Вместо этого пользователь должен запустить `/fast-implement`, который представляет собой нерегулируемый путь для одного сеанса.

Обработайте один билет до конечного пакетного состояния перед запуском другого. Никогда не отслеживайте перекрытие
одобрения несвязанных билетов.

**Сначала посмотрите, что уже существует для этого билета.** Вывод `dispatch status` из маршрута.
В списке выбора перечислены все известные координатору отправки, каждая со своими `ticket`, `batch_id`, `state` и
Флаг `stale`. Если какая-либо запись упоминает этот билет, остановитесь, прежде чем предлагать что-либо, и покажите разработчику
что вы нашли: какая партия, какая роль, какое государство и как долго оно молчало.

Отправка, оставшаяся от предыдущей попытки, — это именно та ситуация, для которой существует этот конвейер, поэтому
относитесь к этому как к доказательству, а не как к мусору. Никогда не используйте его повторно, никогда не удаляйте и никогда не открывайте второй пакет.
рядом с ним — координатор все равно отказывается от перекрывающейся зоны, и тихая повторная попытка — это то, как
первоначальный инцидент сжег окно использования. Разработчик решает, что произойдет.

Закройте старый пакет через CLI, никогда ничего не редактируя в разделе
`.harness/orchestration/state/`. Эти записи являются контрольным журналом; ручное редактирование уничтожает
одна вещь, которую производит этот конвейер.

- **Отчет уже готов и ожидает решения** — `batch decide` с `accept`, `override-warning`,
  `retry`, `block` или `fail`, как обычно.
- **Он вообще больше не может сообщать** — работник, который умер до того, как его модельный самоотчет никогда не сможет этого сделать,
  и партия без ожидающего отчета не может быть решена. Вот для чего нужен `batch abandon`:

  ```bash
  python .harness/orchestration/coordinator.py --repo . batch abandon \
    --batch <batch-id> --approved-by '<кто>' --approved-at <ISO-8601> \
    --reason '<почему решение больше недостижимо>'
  ```

  Требуется явное одобрение и причина, отмечается в пакете `failed`, закрывается каждое открытие.
  отправляет и ничего не удаляет. `batch list --open` показывает то, что еще не закрыто; `--ticket <id>`
  сужает его до одного билета.

Только когда для билета ничего не открыто, вы продолжаете.

Затем прочитайте `.harness/orchestration/roles/` и `.harness/orchestration/playbook.md`. Предложите один
пакет — тикет, ветка/рабочее дерево задачи, зона, определение готовности, запреты, проверки, зависимости,
ворота риска — и покажите это разработчику.

Бриф — единственный канал, который имеет отправляемая роль, поэтому собственные правила доставки этого репозитория должны быть
записано в пакете, а не предполагается. Прочтите `docs/agents/git-workflow.md` и перенесите его.
контракт реализации в записи `--definition-of-done` дословно, чтобы его можно было проверить. В
в частности, когда этот документ требует TDD, в одной записи «Определение готовности» должно быть указано это, например
`write the failing test first at the seams the architect named, then make it pass` — потому что
отправленный разработчик ничего не наследует от `/tdd`: это не этот сеанс, а `verification_commands`
запускайте тесты только после этого, они никогда не требуют, чтобы тест был первым.

**Ворота 0 — план.** Остановитесь для явного одобрения. Только после этого запустите `batch create` и далее
`batch approve`.

## Фаза 3: Пять врат

Последовательность ниже фиксирована. Выполняйте каждый шаг в этом порядке для каждого билета — изменение с низким уровнем риска.
здесь нет более короткого пути; билет, который не заслуживает церемонии, принадлежит
Вместо этого `/fast-implement`.

```text
architect ─► HUMAN approve ─► developer ─► code-review ─► HUMAN approve ─► qa ─┐
                                  ▲                                            │
                                  └────── qa findings: developer fixes ◄────────┤
                                                                                │
                            final report ─► publish ─► HUMAN runs /to-pull-requests
```

Все ворота имеют одинаковую форму: предложить → **остановиться до явного одобрения разработчика** →
`dispatch create` → `dispatch send` → смотреть → `report submit` → `batch decide`. Никогда не создавайте бриф
до его утверждения и никогда не принимать решение об отчете для разработчика. Отчет работника является доказательством
только решения координатора: принять, переопределить, повторить, заблокировать и не выполнить.1. **Архитектор.** `--role architect`. Только для чтения: он анализирует архитектуру, существующую сегодня в
   этот репозиторий и предлагает план — границы, возможные варианты, выбранный вариант,
   компромиссы, риски, критерии приемки и швы, на которых должны сидеть тесты — с репозиторием
   доказательства для каждого. **Этот отчет утверждается человеком до написания любого кода.**
   координатор обеспечивает соблюдение порядка: `dispatch create --role developer` не выполняется, пока архитектор
   отчет для этого пакета был принят, поэтому этот шаг также нельзя пропустить из CLI.
2. **Разработчик.** `--role developer`, после принятого отчета архитектора. Он реализуется на
   собственная ветка задач пакета в изолированном рабочем дереве test-first — неудачный тест у архитектора
   швов перед кодом, который его удовлетворяет, когда определение готовности пакета требует TDD — запускается
   проверяет, фиксирует и отправляет эту ветку проблемы, а не базовую ветку или ветку `integration/*`. Это
   commit SHA является кандидатом. В отчете `changed_files` вы увидите, действительно ли тесты
   появилось с изменением: разница только в реализации с определением готовности TDD является
   `--decision retry`, не принимается. Затем запустите `risk assess` на этом SHA.
3. **Проверка кода.** `--role code-review --candidate-commit <sha>`, прикрепленный к оцениваемому кандидату,
   только для чтения, выполняется для каждого кандидата — оценка риска решает только, будет ли проверка
   *обязательно*, никогда, если это разрешено. Стандарты и спецификации остаются отдельными доказательствами. Блокатор
   требуется `--decision retry`; для предупреждения требуется `--decision override-warning` с записанным примечанием.
   **Покажите человеку проверенные изменения и две оси и остановитесь, чтобы получить одобрение на проведение контроля качества.**
4. **QA.** `--role qa --candidate-commit <sha>` после принятия отзыва. Контроль качества независим: он работает
   на полосе чистой комнаты (`qa run`) против закрепленного SHA, а не через транспорт и не на
   собственные проверки застройщика. Вывод QA не является поражением: `batch decide --decision retry` отправляет
   возвращайтесь к разработчику с выводами, и цикл повторно запускает оценку рисков, проверку и контроль качества.
   о новом кандидате, как только сообщат об исправлении. Повторяйте, пока QA не станет зеленым.
5. **Окончательный отчет, затем опубликуйте.** После принятия зеленого ОК дайте человеку заключительный отчет.
   *до* публикации чего-либо: билет, SHA кандидата, выводы каждой роли, принятый контроль качества.
   доказательства и путь их артефактов, остаточные риски и то, что намеренно опущено. Затем создайте
   опубликовать отправку (`--role developer --purpose publish --candidate-commit <sha>`). Никогда не передавайте
   опубликуйте бриф на `dispatch send`/адаптер; используйте `dispatch publish`, собственный координатор
   проверенная граница, которая точно соответствует принятому SHA.

## 3. Контракты

- **Вход (Input/Brief):** Тикет `afk` или эпик, доступный coordinator CLI, integration-ветка, worktree и явные решения разработчика на каждом gate.
- **Процесс (Process):** Coordinator создаёт batch и проводит Architect → Developer → Code Review → QA, наблюдая dispatch и принимая только доказанные reports.
- **Выход (Output/Report):** Принятый candidate SHA, evidence всех gates и предложение `/to-pull-requests`.
