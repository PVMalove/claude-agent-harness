# To Spec — В спецификацию

## 1. Название и локализация

- **Английское название:** `To Spec`
- **Русский перевод:**

```text
В спецификацию
```

## 2. Полный перевод текста скила

````text
---
name: to-spec
description: Превратите текущий разговор в спецификацию и опубликуйте её в трекере задач проекта. Никакого интервью — только синтез уже обсуждённого.
disable-model-invocation: true
---

**Цель:** синтезировать контекст текущего разговора и понимание кодовой базы в окончательную спецификацию.
**Строгое правило:** НЕ интервьюируйте пользователя и не начинайте новый раунд grilling. Если информации как будто не хватает, значит предыдущее grilling было неполным; синтезируйте спецификацию, используя только известные факты и явные допущения.

Вам уже должны быть предоставлены трекер задач и словарь triage-меток. Если `docs/agents/issue-tracker.md` или `docs/agents/triage-labels.md` отсутствует, скажите пользователю запустить `harness update` — он создаёт оба файла из шаблонов харнесса.

## Выполнение в двух фазах

Вы должны выполнить этот скил в двух отдельных фазах, чтобы пользователь согласовал стратегию тестирования до записи окончательного документа.

### Фаза 1: исследование и предложение seams

1. **Исследуйте кодовую базу:** используйте глоссарий домена проекта (`CONTEXT.md`) и соблюдайте все ADR в затрагиваемой области.
2. **Определите seams:** наметьте seams, в которых будет тестироваться функция.
   - Предпочитайте существующие seams новым.
   - Используйте самый высокий возможный seam.
   - Идеальное состояние: ровно *один* seam для всей функции.
3. **ОСТАНОВИТЕСЬ И СПРОСИТЕ:** представьте предложенные seams и одно имя integration-ветки в форме `integration/<service-or-team>`. Выведите slug из явного языка проекта/домена; никогда не угадывайте его. Попросите пользователя одобрить оба. **Не переходите к фазе 2, пока пользователь не подтвердит.**

### Фаза 2: подготовка и публикация (после одобрения пользователя)

1. **Подготовьте файл:** напишите спецификацию по `<spec-template>` ниже в собственной папке под `docs/tasks/`.
   - *Соглашение об именовании:* если ID issue известен, используйте его. Если нет, используйте описательный slug (например, `docs/tasks/add-user-auth/add-user-auth.md`) и позже переименуйте и папку, и файл, когда ID будет создан — полное соглашение, включая группировку в папке эпика, смотрите в `docs/agents/artifacts.md`.
   - Возьмите итоговый список файлов Discovery Context из `Live Artifact` текущей сессии; если публикация артефактов недоступна, возьмите вместо него утверждённый список путей из финальной Trunk summary. Добавьте его в завершающую секцию шаблона `## Relevant Files (Discovery Context)`. Сохраняйте каждый путь и переданный контекст; при подготовке не ищите и не заменяйте этот список заново.
2. **Опубликуйте в трекере:** опубликуйте issue через CLI настроенного трекера:
   - **GitHub:** `gh issue create --body-file <path>`.
   - **GitLab:** `glab issue create -R <project-url> --title '<title>' --description-file <path> --yes`. `<title>` остаётся в одинарных кавычках, каждый апостроф внутри него записывается как `'\''` в POSIX-shell или как `''` в PowerShell. `<project-url>` и другие плейсхолдеры GitLab (`<host>`, `<project-id>`) определены в `docs/agents/issue-tracker.md` → GitLab → Conventions. Номер эпика — последний сегмент URL issue, который печатает команда.
   - Не передавайте тело inline через `--body`/`--description` или heredoc: тела спецификаций содержат вложенные кавычки и backticks, которые ломают shell quoting.
3. **Примените метки:** это опубликованное issue действует как **эпик** функции. Примените следующие метки (полную таксономию смотрите в `docs/agents/triage-labels.md`):
   - `bug` ИЛИ `enhancement`;
   - `status::specs` (НЕ используйте `status::ready`, потому что сначала требуется декомпозиция);
   - `task-report::required` (если не сказано пропустить).
   - **GitLab:** `glab issue update <epic> -R <project-url> --label 'type::feature,status::specs,task-report::required'` (`type::bug` для бага; уберите `task-report::required`, если сказано пропустить). Метку, которой ещё нет в проекте, GitLab молча создаёт с цветом по умолчанию вместо ошибки, поэтому запустите `/setup-labels` до первого эпика.
   - *Примечание:* НЕ создавайте произвольные метки `epic::<slug>`. Позже `/to-tickets` свяжет тикеты с этим эпиком через родительскую связь трекера — GitHub sub-issues, а на GitLab секцию `## Parent: #<epic>` плюс связь issue `relates_to`; механизм см. в `docs/agents/issue-tracker.md#wayfinding-operations`.
4. **Убедитесь, что выбранная integration-ветка существует после успешного создания issue эпика:**
   - Прочитайте обязательное поле `base_branch` из `.harness/project.json`; если его нет, остановитесь и сообщите о некорректной конфигурации проекта. Это ветка релиза/базы, от которой начинается integration-ветка эпика.
   - Запишите документы прожарки, изменённые в текущем worktree: `git status --porcelain --untracked-files=all -- CONTEXT-MAP.md ':(glob)**/CONTEXT.md' ':(glob)**/docs/adr/**'`. Эти файлы пишут `/grill-with-docs` и `/domain-modeling`. Запишите каждый путь; для переименования (`old -> new`) запишите оба пути. Список может быть пустым.
   - Получите base ref. Создайте `integration/<service-or-team>` командой `git branch` от `origin/<base_branch>`, когда есть remote, иначе от локальной base branch. Не используйте `git switch -c` и `git checkout -b`: хук имени ветки разрешает их только для имён по `branch_pattern`.
   - Если integration-ветка уже есть локально или в remote, используйте её повторно без reset, force-update или удаления. Если публикация успешна, но создание ветки не удалось, сообщите о частичном состоянии и точном действии восстановления; не создавайте issue эпика повторно.
   - Если ветка уже есть в remote, не коммитьте в неё и не переключайте текущий worktree. Если список документов прожарки не пуст, сообщите, что они остаются незакоммиченными в текущем worktree. Укажите действие восстановления: закоммитить их в issue-ветке от `integration/<service-or-team>`, например в ветке первого дочернего тикета, и влить через её PR.
   - Если ветки нет в remote и список документов прожарки пуст, не переключайте текущий worktree: в нём могут быть несвязанные изменения.
   - Если ветки нет в remote и список документов прожарки не пуст, закоммитьте документы в ветку до её push. Отдельный worktree не создавайте:
     1. Переключите текущий worktree командой `git switch integration/<service-or-team>`. Незакоммиченные изменения переходят вместе с worktree. Если `git switch` отказывает из-за конфликта с незакоммиченными изменениями, остановитесь. Не используйте `--force`, `--discard-changes`, `--merge` и reset: они могут перезаписать изменения. Сообщите ошибку git и действие восстановления: отложить изменения командой `git stash push --include-untracked`, выполнить `git switch integration/<service-or-team>`, вернуть изменения командой `git stash pop`, разрешить конфликты и продолжить с подшага 2.
     2. Добавьте в индекс только записанные документы прожарки, явно перечислив пути: `git add -- <path>...`. Не используйте `git add -A`, `git add .` и `git commit -a`. Остальные изменения остаются незакоммиченными в рабочем дереве.
     3. Выполните коммит отдельной командой, без `&&`, `;`, конвейера и переменной: `git commit -m 'docs: <краткое описание эпика>'`. Сообщение пишите по правилам коммитов из `docs/agents/git-workflow.md`. Хук `block-direct-master` разрешает коммит в `integration/*` только в такой форме, только если индекс содержит лишь пути документации прожарки и только если ветки нет на `origin`.
     4. Если хук блокирует коммит, остановитесь и не выполняйте push. Сообщите текст хука и то, что документы остаются в индексе текущего worktree. Укажите действие восстановления: устранить причину, например путь вне документации прожарки в индексе или нет доступа к `origin`, и повторить подшаг 3.
   - Отправьте ветку, которой нет в remote, командой `git push -u origin integration/<service-or-team>`. После коммита документов прожарки текущий worktree остаётся на integration-ветке, несвязанные изменения остаются незакоммиченными.
   - Для локального трекера сделайте коммит документов прожарки, как описано выше, но не выполняйте push и сообщите, что ветка не была отправлена. В репозитории без remote создайте локальную ветку, не коммитьте и не отправляйте её. Сообщите, что ветка не была отправлена и документы прожарки остаются незакоммиченными.

---

<spec-template>

## Формулировка проблемы
Проблема, с которой сталкивается пользователь, с точки зрения пользователя.

## Решение
Решение проблемы с точки зрения пользователя.

## Пользовательские истории
Нумерованный список пользовательских историй, покрывающий каждое поведение функции.
Формат: `1. Как <роль>, я хочу <функцию>, чтобы <выгода>`
*(Пример: как клиент банка, я хочу видеть свой баланс, чтобы принимать обоснованные решения о тратах.)*

## Решения по реализации
Список модулей для создания/изменения, изменений интерфейсов, технических уточнений, архитектурных решений, изменений схемы, API-контрактов и конкретных взаимодействий.
- **НЕ** включайте конкретные пути файлов или общие фрагменты кода (они быстро устаревают).
- **Исключение:** если прототип создал фрагмент, идеально кодирующий решение (машина состояний, схема, форма типа), вставьте его и отметьте, что он получен из прототипа. Оставьте только части, насыщенные решением.

## Решения по тестированию
- Описание того, что делает тест хорошим здесь (тестируйте внешнее поведение, а не детали реализации).
- Какие модули будут тестироваться.
- Предшествующие примеры (аналогичные существующие тесты в кодовой базе).

## Вне области
Строгий список того, что НЕ будет сделано. Это ваша страховка от избыточной инженерии. Явно задайте границы, чтобы будущие агенты не построили больше запрошенного.

## Integration-ветка

- Ветка: `integration/<service-or-team>`
- Создана от: `base_branch` из `.harness/project.json`
- Дочерние issue-ветки начинаются от этой integration-ветки и открывают PR обратно в неё.

## Дополнительные заметки
Оставшийся контекст или ограничения.

## Relevant Files (Discovery Context)
Итоговый список файлов Discovery Context из `Live Artifact` текущей сессии либо, если публикация артефактов недоступна, из финальной Trunk summary, включая каждый путь и переданный контекст.

</spec-template>
````

## 3. Контракты

- **Вход (Input/Brief):** контекст обсуждения, известные факты и допущения, исследованные seams и предложенное имя integration-ветки.
- **Выход (Output/Report):** одобренная спецификация в `docs/tasks/`, опубликованное issue эпика с метками и существующая integration-ветка либо точный отчёт о частичном состоянии.
