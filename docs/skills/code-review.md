# Code Review — Ревью кода

## 1. Название и локализация

- **Английское название:** `code-review`
- **Русский перевод:**

```text
Ревью кода
```

## 2. Полный перевод текста скила

```text
---
name: code-review
description: Проверьте изменения после фиксированной точки (коммит, ветка, тег или merge-base) по двум осям — Standards (соответствует ли код документированным стандартам этого репозитория?) и Spec (соответствует ли код тому, что требовал исходный issue/spec?). Запускает обе проверки в параллельных подагентах и сообщает их рядом. Используйте, когда пользователь хочет проверить ветку, PR, незавершённые изменения или просит «review since X».
---

Двухосевое ревью diff-а между `HEAD` и фиксированной точкой, которую указывает пользователь:

- **Standards** — соответствует ли код документированным стандартам кодирования этого репозитория?
- **Spec** — точно ли код реализует исходный issue / spec?

Обе оси запускаются как **параллельные подагенты**, чтобы не загрязнять контекст друг друга, затем этот навык агрегирует их выводы.

### Граница runtime

Этот workflow не зависит от runtime. Язык вывода определяется `language` из `.harness/project.json`; используйте уже вручную настроенный механизм ревью. Workflow не должен запускать runtime-специфичный adapter, выбирать провайдера или модель либо изменять проверяемую ветку.

Issue tracker должен быть предоставлен. Если `docs/agents/issue-tracker.md` отсутствует, скажите пользователю запустить `/setup-matt-pocock-skills`.

## Процесс

### 1. Зафиксируйте точку отсчёта

Всё, что назвал пользователь, является фиксированной точкой: SHA коммита, имя ветки, тег, `main`, `HEAD~5` и т. д. Если её не указали, спросите.

Один раз зафиксируйте команду diff: `git diff <fixed-point>...HEAD` (три точки, поэтому сравнение идёт с merge-base). Также зафиксируйте список коммитов через `git log <fixed-point>..HEAD --oneline`.

Перед продолжением убедитесь, что фиксированная точка разрешается (`git rev-parse <fixed-point>`) и diff не пуст. Некорректная ссылка или пустой diff должны завершиться здесь, а не внутри двух параллельных подагентов.

### 2. Найдите источник спецификации

Ищите исходную спецификацию в таком порядке:

1. Ссылки на issue в сообщениях коммитов (`#123`, `Closes #45`, GitLab `!67` и т. п.) — получите их по workflow в `docs/agents/issue-tracker.md`.
2. Путь, переданный пользователем аргументом.
3. Файл спецификации под `docs/`, `specs/` или `.scratch/`, соответствующий имени ветки или функциональности.
4. Если ничего не найдено, спросите пользователя, где спецификация. Если он скажет, что её нет, подагент **Spec** пропустит проверку и сообщит «спецификация недоступна».

### 3. Найдите источники стандартов

Всё в репозитории, что документирует правила написания кода, например `CODING_STANDARDS.md` или `CONTRIBUTING.md`.

Помимо того, что документирует репозиторий, ось Standards всегда содержит описанный ниже **базовый набор запахов** — фиксированный набор запахов кода Фаулера (_Refactoring_, гл. 3), применимый даже когда репозиторий ничего не документирует. Для него действуют два правила:

- **Репозиторий имеет приоритет.** Документированный стандарт репозитория всегда побеждает; если он одобряет то, что базовый набор пометил бы, не сообщайте запах.
- **Всегда требуется суждение.** Каждый запах — помеченная эвристика («возможный Feature Envy»), а не жёсткое нарушение; как и для любого стандарта здесь, пропускайте всё, что уже принудительно обеспечивают инструменты.

Каждый запах читается как _что это_ → _как исправить_; сопоставляйте его с diff-ом:

- **Mysterious Name** — имя функции, переменной или типа не раскрывает, что она делает или хранит. → переименуйте; если честного имени не находится, дизайн мутный.
- **Duplicated Code** — одна форма логики встречается более чем в одном hunk-е или файле изменения. → извлеките общую форму и вызывайте её из обоих мест.
- **Feature Envy** — метод обращается к данным другого объекта больше, чем к собственным. → перенесите метод на данные, которым он завидует.
- **Data Clumps** — одни и те же несколько полей или параметров постоянно путешествуют вместе (тип, который хочет родиться). → объедините их в один тип и передавайте его.
- **Primitive Obsession** — примитив или строка заменяет понятие домена, заслуживающее собственного типа. → дайте понятию собственный маленький тип.
- **Repeated Switches** — один и тот же каскад `switch`/`if` по одному типу повторяется в изменении. → замените полиморфизмом или одной картой, общей для обоих мест.
- **Shotgun Surgery** — одно логическое изменение вынуждает разрозненные правки во множестве файлов diff-а. → соберите то, что меняется вместе, в один модуль.
- **Divergent Change** — один файл или модуль редактируется по нескольким несвязанным причинам. → разделите так, чтобы каждый модуль менялся по одной причине.
- **Speculative Generality** — абстракция, параметры или hooks добавлены для потребностей, которых нет в спецификации. → удалите их; сверните обратно, пока не появится реальная потребность.
- **Message Chains** — длинная навигация `a.b().c().d()`, от которой вызывающий код не должен зависеть. → спрячьте обход за одним методом первого объекта.
- **Middle Man** — класс или функция, которые в основном только делегируют дальше. → удалите посредника и вызывайте реальную цель напрямую.
- **Refused Bequest** — подкласс или реализатор игнорирует либо переопределяет большую часть наследуемого. → откажитесь от наследования и используйте композицию.

### 4. Проверьте обе оси

Запустите подагентов `code-review-standards` и `code-review-spec`, определённых в `.claude/agents/`, через вручную настроенный механизм coding application. Дождитесь обоих отчётов, затем верните их в эту основную сессию для агрегации. Не заменяйте ни одну ось встроенным ревью.

**Prompt для `code-review-standards`** должен включать:

- полную команду diff и список коммитов;
- список файлов-источников стандартов, найденных на шаге 3, **плюс базовый набор запахов из шага 3**, вставленный полностью: у подагента нет другого доступа к нему.

**Prompt для `code-review-spec`** должен включать:

- команду diff и список коммитов;
- путь или полученное содержимое спецификации.

Если спецификация отсутствует, пропустите подагента `code-review-spec` и отметьте это в финальном отчёте.

### 5. Агрегируйте

Представьте два отчёта под заголовками `## Standards` и `## Spec`, дословно или с лёгкой очисткой. **Не** объединяйте и не меняйте ранжирование выводов: две оси намеренно разделены (см. _Почему две оси_).

Завершите одной строкой: общее число находок по каждой оси и худшая проблема _внутри каждой оси_ (если есть). Не выбирайте единственного победителя между осями: именно этого перераспределения ранга разделение и не допускает.

## Почему две оси

Изменение может пройти одну ось и не пройти другую:

- Код, который следует каждому стандарту, но реализует не то → **Standards пройдена, Spec не пройдена.**
- Код, который делает ровно то, что требовал issue, но нарушает соглашения проекта → **Spec пройдена, Standards не пройдена.**

Раздельный отчёт не даёт одной оси скрыть другую.

### Язык вывода

Прочитайте `language` из `.harness/project.json` (по умолчанию `ru`, если файл или поле отсутствует). Если `ru`, пишите весь отчёт — оба brief-а подагентов и агрегированный вывод — на русском независимо от языка prompt-а. Если `en`, пишите на английском.
```

## 3. Контракты

- **Вход (Input/Brief):** фиксированная точка, diff, стандарты проекта и исходная спецификация.
- **Выход (Output/Report):** независимые отчёты `Standards` и `Spec`, затем краткая двухосевая сводка.
