````text
# Быстрая реализация

**Цель:** реализовать описанную пользователем работу по спецификации или тикетам в этой сессии без этапа архитектора, независимой роли QA и approval-gates координатора.

Это короткий маршрут. Используйте его для тикета, направление которого не вызывает вопросов, а радиус воздействия мал. Во всех остальных случаях используйте `/implement`, который запускает управляемый конвейер architect → developer → code-review → QA.

## Выполнение в трёх фазах

Строгий конвейер, выполняемый по порядку: **предварительная проверка** (подтвердить, что тикет действительно можно начать и что это должен делать данный агент) → **кодирование** (TDD, тесты, явно одобренный review, commit и push) → **PR и завершение** (предложить отдельную команду `/to-pull-requests`). Выбрать `/to-pull-requests` может только разработчик.

### Фаза 1: предварительная проверка

1. **Определите тикет.**
   - **Назван конкретный тикет** (номер issue, URL или путь `.scratch/<feature>/issues/NN-*.md`): используйте его.
     - **Немедленно остановитесь на `hitl`:** если у него есть `hitl` (см. `docs/agents/triage-labels.md`), сразу остановитесь и скажите пользователю запустить вместо этого `/to-guide` — не проверяйте по этому тикету ничего другого: этот агент реализует только работу `afk`.
   - **Назван эпик** (с `workflow::specs` или иным образом являющийся родителем декомпозиции), а не конкретный тикет: выберите следующий тикет сами вместо вопроса. Никогда автоматически не выбирайте тикет `hitl` — этот режим выполнения всегда проходит через `/to-guide`, а не через этого агента.
     - **GitHub/GitLab:** выполните тот же frontier-запрос, который использует `/wayfinder` (`docs/agents/issue-tracker.md#wayfinding-operations`), ограниченный подзадачами эпика и отфильтрованный по `afk` — открытый, незаблокированный, не занятый, первый в порядке декомпозиции. Заберите выбранный тикет (`gh issue edit <n> --add-assignee @me` в GitHub, `glab issue update <n> --assignee @me` в GitLab) до любой другой записи, как это делает `/wayfinder`, чтобы параллельная сессия (например, параллельный worktree) не выбрала тот же тикет. Если отфильтрованный frontier пуст, остановитесь и объясните пользователю почему: если остались открытые, незаблокированные и не занятые тикеты, но все они `hitl`, скажите это и укажите на `/to-guide`; иначе объясните, что пока ничего не разблокировано либо всё уже занято.
     - **Локальный трекер:** прочитайте каждый файл `.scratch/<feature>/issues/NN-*.md` в порядке имён файлов — это исключительно линейная цепочка — и возьмите первый, у которого одновременно `**Workflow:** workflow::ready` и `**Execution:** afk`. Если тикеты остаются, но каждый `workflow::ready` имеет `hitl`, сообщите об этом, назвав их, и укажите на `/to-guide` вместо автоматического выбора.
     - После такого выбора обрабатывайте тикет в остальном процессе точно так же, как явно названный.
   - **Ничего не названо:** если в этом репозитории есть документ git-процесса (например, `docs/agents/git-workflow.md`) с правилом «Issue First», остановитесь и попросите пользователя назвать существующий тикет либо сначала запустить `/to-spec`/`/to-tickets` — не начинайте работу. Иначе полностью пропустите эту проверку.
2. **Проверьте блокировки** у определённого тикета. Если у него есть `workflow::blocked` (см. `docs/agents/triage-labels.md`), проверьте его блокеры через трекер этого репозитория (нативные links зависимостей GitHub/GitLab либо поле `Blocked by:`/`**Blocked by:**` — см. `docs/agents/issue-tracker.md`).
   - Любой ещё открытый блокер → остановитесь и сообщите пользователю, какие именно. Не начинайте работу.
   - Все блокеры закрыты/разрешены → снимите блок до продолжения:
     - **GitHub/GitLab:** замените метку `workflow::blocked` на `workflow::ready`.
     - **Локальный трекер:** установите строку `**Workflow:**` файла в `workflow::ready`.
3. **Пометьте тикет как выполняемый**, когда действительно начинаете работу:
   - **GitHub/GitLab:** установите метку `workflow::in-progress`.
   - **Локальный трекер:** установите строку `**Workflow:**` файла в `workflow::in-progress`.
4. **Предварительная проверка Git перед редактированием файлов:**
   - Определите точную integration-ветку из раздела тикета `## Integration Branch` или для дочернего тикета, который её не содержит, из родительского эпика. Отсутствующее значение — блокер; не выводите ветку из памяти, текущего checkout или имени сервиса.
   - Текущая ветка должна соответствовать `branch_pattern` и быть issue-веткой. Если это не так, получите integration-ветку и создайте `feature/issue-<ID>-<slug>` от неё до кодирования. Никогда не делайте commit или push прямо в базовую ветку проекта или ветку `integration/*`.

### Фаза 2: кодирование

1. Используйте `/tdd`, где это возможно, на заранее согласованных seams.
2. Регулярно запускайте typechecking, регулярно — отдельные тестовые файлы, а в конце один раз — полный набор тестов.
3. Спросите разработчика: «Провести code review?» Остановитесь и дождитесь ответа.
   - **Да:** запустите `/code-review`. Он запускает subagents Standards и Spec через вручную настроенный механизм coding application, ждёт оба отчёта и возвращает их раздельные разделы `## Standards` и `## Spec` в эту основную сессию. Внесите все запрошенные изменения, затем перед продолжением повторите релевантные тесты.
   - **Нет:** зафиксируйте, что разработчик отказался от review, и продолжите.
4. Попросите у разработчика явное разрешение на commit и push. Остановитесь и дождитесь ответа.
5. После одобрения проверьте, что текущая ветка всё ещё соответствует `branch_pattern` и не является ни `base_branch`, ни `integration/*`; создайте commit завершённой работы с Semantic Commit Message и отправьте его в текущую issue-ветку. Сообщите разработчику результат commit и push.

### Фаза 3: PR и завершение

После успешного push предложите `/to-pull-requests <ticket>` как следующую команду. Не вызывайте её автоматически, не открывайте PR, не запускайте `qa-gate` и не закрывайте тикет в этом скиле.
````

## 3. Контракты

- **Вход (Input/Brief):** конкретный тикет либо эпик, его критерии и зависимые записи трекера; явное разрешение разработчика для review и для commit/push.
- **Выход (Output/Report):** реализация в issue-ветке, результаты проверок, состояние тикета и после push — предложение открыть PR отдельным скилом.
