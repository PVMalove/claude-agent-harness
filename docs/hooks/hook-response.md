## 1. Название и локализация
- **Английское название:** hook_response.py (hook verdict envelope)
- **Русский перевод / Суть:**

```text
Конверт ответа управляемых hooks: JSON-вердикт, код возврата по решению и профиль политики hooks проекта.
```
## 2. Полное описание
Каждый управляемый hook событий (`block-dangerous-git`, `block-direct-master`, `block-pr-merge`, `block-public-attribution`, `require-qa-gate`, `protect-hook-policy`, `check-branch-name`, `check-worktree-branch-name`, `require-bounded-check`, `block-scratch-outside-docs-tasks`, `count-skill-usage`, `mark-qa-gate-passed`) в начале сценария перезапускает себя через `hook_response.py run <hook_id> <bash> <сценарий>`. Advisory-hooks ChangeImpact (`impact-first-touch`, `targeted-check-reminder`, `sensitive-path-recheck`) запускают через конверт сразу общее тело: `hook_response.py run <hook_id> <python> change_impact_hooks.py <hook_id>`. Модуль читает stdin вызова, запускает исходный сценарий с тем же stdin, передаёт его stdout и stderr без изменений и последней строкой stderr печатает вердикт:

```json
{"hook_id":"block-pr-merge","profile":"standard","decision":"block","reason_code":"pr-merge","remedy":"…","evidence_ref":".claude/hooks/block-pr-merge.sh"}
```

- **Причина блокировки.** `reason_code` блокировки — код правила hook. Сценарий с несколькими правилами (`protect-hook-policy`) называет причину префиксом `[reason_code] ` в начале stderr; незарегистрированный префикс игнорируется.
- **Решение и код возврата.** `allow` и `warn` — код `0`, `block` — код `2`. Вердикт идёт в stderr, а не в stdout: Claude Code разбирает stdout при коде `0` как собственный JSON-протокол, и значения `allow`/`warn` в нём не определены.
- **Код исходного сценария.** `0` — `allow` с `reason_code` `ok`; `2` — блокировка с `reason_code` правила этого hook; любой другой код, сбой запуска, завершение по сигналу или зависание дольше тайм-аута — внутренняя ошибка. Тайм-аут тела — 50 с (`INNER_TIMEOUT_SECONDS`, меньше 60 с тайм-аута hook-а в runtime): процесс прерывается, вердикт `internal-error` выдаёт конверт, для критичного hook-а это `block` с кодом `2`, для остальных — `warn`.
- **Критичность (ADR 0024).** Критичные hooks (`block-public-attribution`, `block-direct-master`, `block-pr-merge`, `protect-hook-policy`, `check-branch-name`, `check-worktree-branch-name`, `block-dangerous-git`, `block-scratch-outside-docs-tasks`, `require-qa-gate`) при внутренней ошибке блокируют (`block`, `internal-error`, код `2`), в том числе при сбое самого конверта. Поведенческий `require-bounded-check` и учётные `count-skill-usage`, `mark-qa-gate-passed` при внутренней ошибке разрешают с предупреждением (`warn`, код `0`); учётные hooks по замыслу не блокируют, поэтому их код `2` тоже считается внутренней ошибкой.
- **Advisory-hooks ChangeImpact (ADR 0024, раздел 2a).** Класс `ADVISORY_HOOKS`: [`impact-first-touch`](impact-first-touch.md), [`targeted-check-reminder`](targeted-check-reminder.md) и [`sensitive-path-recheck`](sensitive-path-recheck.md). Тело всегда завершается кодом `0`. Предупреждение — первая строка stderr `[reason_code] remedy` с собственным кодом hook-а и, при наличии, строка `evidence_ref=<путь>`; stdout содержит только JSON протокола runtime. Конверт решает так: код `0` с префиксом hook-а — `warn` (stdout передаётся), код `0` без префикса — `allow`. Префикс `[internal-error]`, любой другой код, сбой запуска и тайм-аут — `warn` `internal-error` с кодом `0`, а stdout тела отбрасывается: частичный вывод сломал бы протокол `Stop` второго runtime. Тайм-аут тела advisory-hook — 10 с (`ADVISORY_TIMEOUT_SECONDS`), потому что тело стоит на горячем пути каждой правки; общий `INNER_TIMEOUT_SECONDS` и ветка критичных hooks не меняются. Ни в одном профиле advisory-hook не получает `block` и код `2`.
- **Активные профили advisory-hooks.** Конверт применяет профиль до запуска тела (`ACTIVE_PROFILES`): `impact-first-touch` и `targeted-check-reminder` работают в `standard` и `strict`, `sensitive-path-recheck` — только в `strict`. В остальных профилях конверт отвечает `allow` с `reason_code` `ok`, тело не запускается и состояние не пишется.
- **Профиль.** Берётся только из ключа `hook_policy` файла `.harness/project.json` проекта, в котором лежит `.claude/hooks/hook_response.py`. Переменные окружения, включая `HOOK_PROFILE`, и параметры инструмента не читаются. Проект без файла или без ключа получает `standard`. Hook не знает роль и пути команды и не может проверить условия эскалации, поэтому применяет самую строгую эскалацию ко всем вызовам: профиль — самый строгий из базового и всех `escalations[].profile` (проект с `minimal` и эскалацией до `standard` для роли `qa` получает `standard`, и `require-bounded-check` блокирует). Это только ужесточает: `hook_policy.resolve_profile` для любого вызова даёт профиль не выше. Ключ, который нельзя разобрать или значения которого неизвестны, и файл, который нельзя прочитать или разобрать, дают `strict` — сдвиг только в строгую сторону.
- **Что меняет профиль.** `minimal` понижает блокировку поведенческого hook (`require-bounded-check`) до предупреждения (`warn`, код `0`, `reason_code` правила сохраняется) и выключает advisory-hooks. Критичные hooks блокируют в любом профиле. `standard` сохраняет все блокирующие решения и включает `impact-first-touch` и `targeted-check-reminder`; проект без `hook_policy` ведёт себя как `standard`. `strict` сохраняет те же решения, включает ещё `sensitive-path-recheck` и добавляет fail-closed границы coordinator-а (ниже).
- **Граница strict (coordinator).** Под `strict` `dispatch propose` и `dispatch create` для code-review и QA, `qa run` и `dispatch publish` отказывают с кодом `2` и ошибкой `strict_impact_unknown`, если diff кандидата от базы batch (`--no-renames`, то есть и прежний путь переименования) меняет чувствительный путь, а VerificationPlan не доказывает ImpactSet (ADR 0023) для него. План доказывает влияние, когда все его стадии `full` или ни одна причина `impact.unknown` не относится к чувствительному изменённому пути и нет причины без пути. Отказ перечисляет до 20 чувствительных путей и называет границу; remedy — включить `verification_plan_policy` в конфиге orchestration и создать новый batch, чтобы review и QA несли план, либо человек-владелец меняет `hook_policy` в `.harness/project.json` и повторяет propose. Отказ происходит до любой мутации: brief не пишется, QA-lease не берётся, push не выполняется, поэтому повтор даёт то же решение. Источник ImpactSet — только VerificationPlan proposal или brief: граница не пересчитывает ImpactSet, поэтому `strict` без `verification_plan_policy` отказывает review и QA любому чувствительному изменению. Роль политики для эскалаций: `review` для code-review, `qa` для QA и `qa run`, `coordinator` для publish. Профиль propose берётся из `hook_policy` в `.harness/project.json`; `qa run` и publish решают по политике запущенного dispatch — снимку его пинованной конфигурации, хеш которого обязан совпасть с `hook_policy_sha256` brief-а (несовпадение — отказ целостности), так что правка `project.json` после approval решение не меняет. Brief без `hook_policy_sha256` получает `standard`. У publish план — VerificationPlan brief-а принятого QA. `minimal` и `standard` на этих границах ведут себя как раньше. Strict не проверяет каждый вызов инструмента, не запускает `make verify` и полный набор из hook-а и не блокирует команды восстановления `ledger lock-status`, `qa clear-stale-lease`, `batch rewind`, `dispatch cancel` и `ledger release-lock --force` (последняя по-прежнему требует `--approved-by`, `--approved-at` и `--reason`).
- **Решение R1 о Rust-части границ.** ADR 0024, раздел 2a, называет fail-closed проверку проверкой coordinator-а и Rust, а раздел 3 отдаёт авторитетную проверку модулю политики Rust для операций, которые исполняет Rust. Сейчас Rust runtime не исполняет ни `dispatch propose`, ни `qa run`, ни publish: эти операции исполняет Python. Поэтому по решению R1 все три границы проверяет одна Python-функция coordinator-а `hook_policy.require_strict_boundary`. Rust-проверку `qa run` по сохранённому `hook_policy_sha256` и плану добавит задача, которая переводит исполнение QA в Rust (ADR 0022). Исполнение QA в Python при этом не переносится: решение политики остаётся зоной Python. Скоупный hook субагента test-author (`test-author-guard.py`) подключён в описании агента, отвечает собственным протоколом мягкого отказа и через конверт не проходит.
- **Реестр.** Значения `hook_id`, `profile`, `decision` и `reason_code` зарегистрированы в `harness/orchestration/system_fields.v1.json` (поля `hook.id`, `hook.profile`, `hook.decision`, `hook.reason_code`). `parse_hook_response` в `harness/orchestration/hook_policy.py` читает вердикт как последнюю непустую строку вывода и отклоняет незарегистрированное значение ошибкой контракта.
- **Без конверта.** Если Python или `hook_response.py` недоступны, сценарий выполняется напрямую и решает сам, как раньше: критичные сценарии без Python по-прежнему блокируют.
- **Второй runtime.** Адаптер `.codex/hooks.json` вызывает те же сценарии, поэтому конверт, вердикт и профиль у него те же: профиль берётся из `hook_policy` проекта, а не из окружения runtime. Подключены поднабор для `Bash` на `PreToolUse` (критические guards и `require-bounded-check`) и `targeted-check-reminder` на `Stop` и `SubagentStop`; hooks на `Write` и `Edit` (в том числе `impact-first-touch`, `sensitive-path-recheck` и журнал касаний `targeted-check-reminder` до адаптера `apply_patch`, #830), `EnterWorktree` и `Skill` и `mark-qa-gate-passed` на `PostToolUse` не подключены (второй runtime вызывает `PostToolUse` и после команды с ненулевым кодом выхода, а кода выхода в payload нет), и `harness health` в проверке `hooks.policy` показывает их как отсутствующие. Проектные hooks этого runtime работают только после доверия слою `.codex/` проекта и каждому hook по хэшу. Слияние файлов настроек и состав адаптера описаны в [install-and-update.md](install-and-update.md).
- **Маркер повторного запуска.** Исходный сценарий запускается с переменной `HARNESS_HOOK_ENVELOPE=1`, чтобы не обернуть себя второй раз.

## 3. Контракты
- **Вход (Input/Brief):** `run <hook_id> <команда...>`; `hook_id` обязан быть зарегистрирован. JSON-payload вызова инструмента — через stdin.
- **Выход (Output/Report):**
  - **Разрешение/предупреждение:** код `0`, последняя строка stderr — вердикт с `decision` `allow` или `warn`.
  - **Блокировка:** код `2`, последняя строка stderr — вердикт с `decision` `block`; перед ней стоит сообщение исходного сценария.
  - **Неизвестный `hook_id` или неверный вызов:** код `2` и сообщение в stderr без вердикта.
