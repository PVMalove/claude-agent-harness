Verification

Проверки focused/failed-only никогда не дают права publish. Новый SHA после исправления требует full QA. Не дублировать полный прогон при каждом промежуточном TDD исправлении.

Crash recovery

Approved plan → Durable launch → IPC failure / SIGKILL → Rust reconcile → Same execution OR typed block → Immutable evidence + lease release

Контейнеры/процессы идентифицируются стабильной записью, а не одним PID. Не отпускать чужой QA lease и не создавать повторный worker при потерянном ACK.

# Executive summary — Harness Next

**Зафиксировано:** одна финальная архитектура и один production cutover; новые системные компоненты реализуются на Rust с первого коммита, а не сначала на Python с последующей переписью. Python сохраняет skills, policy, AI routing и lifecycle decisions. Rust владеет trusted execution supervisor, OCI, контрольными командами QA, transactional SQLite WAL operational state, процессами и recovery. Версионированный IPC и ownership matrix фиксируются до реализации. Допускаются вертикальные PR и contract tests, но без throwaway production implementations.

**Производительность:** на Developer — impacted/related tests, после ошибки — только failed node IDs или `pytest --lf` с изолированным кэшем, перед выходом — независимый full clean-room QA по финальному SHA. `--ff` не равен failed-only; clean-room ordered scenarios нельзя безопасно делить без явных зависимостей.

**Надёжность:** concurrency нескольких batch без глобального ожидания; QA-lane singleton; durable leases, crash reconciliation, idempotency после lost ACK, SIGKILL/host reboot и корректная классификация infra/code/unknown. Предотвращение циклов `rewind → risk → review → QA` (#781).

**Безопасность:** pinned image/plan digest, rootless Podman на Fedora с SELinux и Docker, Windows execution adapter; `minimal | standard | strict` hook profiles при `start-project` и `integrate-project` (safety никогда не ослабевает); change-impact enforcement вместо буквального копирования GateGuard; нет прямого Docker сокета или policy downgrade у worker. Настройки hooks не заменяют OS isolation.

**Статус GitHub:** #784 — новый целевой epic, а #634 #709 #774 #777 #778 #779 #781 — открытые issues, **реально дополнены** 20 октября 2026. #615 #756 #757 #758 #769 #780 закрыты, не переоткрывались. Specs/ADR в репозитории НЕ редактировались напрямую: сначала review и ADR согласование, затем PR в согласованной integration ветке.

## Непересматриваемое решение

**Одна целевая реализация, без промежуточных переписываний.** Python сохраняет AI routing, skills, DDD/workflow policy и presentation/CLI. **Rust с первого целевого коммита** реализует системный runtime, управление процессами и контейнерами, исполнение QA, durable operational ledger и crash recovery. SQLite WAL используется для транзакционного operational state; неизменяемые evidence и audit должны сохранить верифицируемую цепь целостности, формат/миграцию которых фиксирует ADR. Работа разбивается на интегрируемые вертикальные срезы, но ни один не вводит временную Python-реализацию нового Rust-компонента.

**Стабильные границы до реализации:** `ExecutionPlan`, `ExecutionReceipt`, `ExecutionOutcome`, `VerificationPlan`, `FailureDiagnosis`, `Lease`, `EvidenceManifest`, `ApprovedAccessPlan`; versioned Unix Domain Socket IPC на Linux, platform adapter для Windows; schema-version, idempotency keys, SHA-256 digest approval. Python никогда не пишет в новую SQLite базу runtime. Rust не принимает lifecycle/publish/approval решений: они остаются у Python coordinator, который вызывает Rust транзакционными командами через согласованный контракт. Единственный авторитетный writer каждой сущности и строго очерченная ownership-модель. Временная совместимость старых записей — migration adapter/read-only fallback, **не параллельный второй ledger writer**.

## Проверки обязательных свойств

1. Один full-suite на финальный candidate SHA при штатном пути. Несколько focused прогонов в dev не повторяют full-suite.
2. После failure разработчик исполняет точный nodeid / pytest `--lf --lfnf=none`; затем impact suite. Только новый clean-room full gate обеспечивает release evidence.
3. `pytest --ff` **не** означает failed-only; `--lf` применяется только с постоянным workspace-scoped cache. `scripts/verify.py` сейчас отключает cacheprovider по умолчанию и `mypy` temp cache удаляет — решить в рамках единого planner.
4. `test_clean_room.py` имеет shared context и ordered scenarios; нельзя произвольно пропускать сцену без декомпозиции fixtures/dependencies.
5. Fork/kill coordinator, затем Rust recovery: операция не дублируется, чужой PID не убивается, чужой lease не снимается.
6. Два batch одновременно проходят запись без global lock; singleton QA gate остается сериализованным. Нет deadlocks при сбое.
7. Подтвержденные инфраструктурные ошибки не тратят developer retry. Неизвестные ошибки fail closed без подмены code failure.
8. Процессы внутри sandbox не получают доступ к привилегированному Rust socket. Сервер строго валидирует approval-bound план, digest, identity и ACL.
9. Все runtime write операции либо транзакционно применены, либо идемпотентно откатываются/reconcile; audit остаётся проверяемым.
10. Полный cutover происходит только после тестов совместимости со старыми batch/evidence и замеров базовой версии. Бэкенд новых компонентов с первого дня Rust, никаких временных Python реализаций.

## Дополнение к единому target spec — Runtime Hook Profiles (включено в реализацию с первого release)

**Архитектурный принцип.** Профили `minimal | standard | strict` управляют поведенческими предупреждениями и pre-tool гейтами, но не заменяют и не могут отключать реальные границы OS sandbox, ACL Rust IPC, approvals и pinned dispatch. Один policy resolver и versioned `ApprovedHookPolicy` с `policy_digest`, закреплённым в immutable brief. Runtime enforce критичных запретов должен происходить в доверенном Rust boundary; Claude hooks и Codex adapters являются client-side дополнительными проверками, не единственным исполнителем защиты. Профиль нельзя менять через env переменную агента.

| Профиль | Поведение | Неизменяемые границы |
|---|---|---|
| `minimal` | Не блокировать за обычные style/impact reminders. Только жизненно важные проверки. | Secrets/credentials, branch ownership, destructive actions, approval and sandbox boundaries остаются включены |
| `standard` (новые проекты) | Критичные проверки + bounded first-touch change-impact evidence на рискованных файлах, предупреждения при отсутствии focused tests, дедупликация событий. | То же, плюс контролируемая диагностика |
| `strict` | Fail-closed на критичных паттернах: auth/permission/CI/migrations/secret/path traversal; машинно проверяемый impact evidence и аудит. | То же, причём explicit operator recovery имеет bounded procedure, не бесконечные DENY loops |

**Инсталляция и миграция.** `start-project` и `integrate-project` разрешают опциональную конфигурацию профиля и совместимые role/path overrides. Установка управляемых hooks повторяема без удаления чужих hooks. Старые проекты сохраняют наблюдаемую политику, если не выбран явный owner-approved переход; новые получают `standard`. `harness health` показывает effective policy, provenance, missing managed hooks, privileged runtime readiness и incompatible policy digest. При changed config уже созданный dispatch исполняется по исходному pinned digest, а новый план требует нового approval.

**DoD / тесты:** profile×role×sensitive path×tool matrix; changed hook profile after approval; symlink / hardlink bypass; missing unsafe secret; injected agent environment; nested Claude sandbox; recovery после hook failure; отсутствие циклических DENY и дублирования `make verify`; Linux/Windows; Codex и Claude adapter parity. В `strict` нельзя запускать все тесты после каждого Edit — планированием тестов владеет `VerificationPlan`.

**Проследить в issue:** https://github.com/PVMalove/claude-agent-harness/issues/784, карточки `HN-11`, `HN-12`, `HN-14` в интерактивной доске. Не откладывать hook profiles после Rust cutover и не писать временную Python policy-server реализацию.
