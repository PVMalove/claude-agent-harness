# Настройка проекта в консоли

Запустите `python3 harness/bin/harness.py console /path/to/project` из дистрибутива Harness.
Консоль сохраняет этот источник CLI при переходе в другой проект.

На главном экране нажмите «Открыть / подключить проект», введите путь и проверьте его.
Нужен локальный Git-репозиторий; для нового каталога сначала выполните `git init`.
Консоль показывает абсолютный корень проекта, действие `init`, `adopt` или `update`
и выбранный состав Harness. Workflow включает настройку `project.json`, Backend —
также роли и `orchestration.json`. При смене capabilities показанный состав заменяет
прежний набор управляемых capabilities.

План проверяет занятые discovery-пути, собственные файлы и дрейф управляемого снимка.
Конфликты нужно разобрать до установки; это меню не включает force или replace.
Подтвердите показанный план и нажмите «Установить». После успеха выбранный проект
становится целью всех разделов консоли. Для уже установленного проекта достаточно
«Сделать целевым / открыть». Отмена сохраняет прежнюю цель. Во время команды смена
проекта заблокирована; результаты прежнего dashboard не обновляют новый экран.

## Шаги и черновик

Откройте «Настройка конфигурации» и выберите один или оба файла. Мастер загружает
существующие значения, а отсутствующий файл начинает со штатного шаблона.
Без соответствующей capability он предлагает сначала установить её.

Шаги сгруппированы по секциям схемы. На каждом шаге видны назначение поля,
рекомендация и причина, текущий ответ и его влияние. Выберите ответ или введите
значение. Строки вводятся без кавычек; числа, списки и объекты — как JSON.
Одиночный выбор используется для взаимоисключающих значений, чекбоксы —
для boolean и списков enum. На странице выбора не больше четырёх значений;
кнопка «Другие варианты» открывает следующую группу.

Переходы «Назад» и «Далее» сохраняют ответы в черновике. Список шагов позволяет
перейти к нужному полю. Необязательный объект можно добавить, изменить или убрать
целиком; после добавления доступны его вложенные поля. Так редактируются дополнительные
профили, назначения ролей, access/tool policies и extensions.

Нажмите «Просмотр итога». Консоль показывает оба вида проверки — ограничения
JSON-схемы и действующие валидаторы Health/оркестрации — вместе с полными JSON
и различиями. Ошибки содержат имена полей для возврата к нужному шагу.
`approval_policy=auto` требует `trusted` и `worker_attestation_required=true`;
настройка `access_policy` сама не предоставляет runtime доступ.
Действительные команды QA и доступы проверяются диагностикой отдельно.

«Применить» требует подтверждения цели и перезаписывает выбранные рабочие файлы.
Изменение файла другим процессом за время работы мастера останавливает запись:
закройте черновик, загрузите новые значения и снова просмотрите итог.
Закрытие до применения отбрасывает черновик после подтверждения.

## Версии и восстановление

«Сохранить версию» сохраняет заполненный черновик без применения. Каждый снимок
содержит согласованный набор обоих файлов, включая отсутствие файла, дату,
описание, идентификатор, версию установленного Harness и SHA-256 файлов.
Версии находятся в `.harness/config-versions/` выбранного checkout, игнорируются Git
в стандартной установке и переживают soft/hard cleanup. Ledger и worktrees в снимок
не входят; восстановление не меняет уже записанные brief/batch.

Меню «Версии / откат» показывает метаданные и различия с активной конфигурацией.
После проверки хешей и совместимости выбранную версию можно восстановить
с подтверждением. Перед применением или откатом текущие файлы сохраняются отдельным
снимком: он позволяет вернуть прежнее состояние. Отсутствующие в снимке файлы
при восстановлении удаляются. Повреждённую или несовместимую версию применять нельзя;
исправьте копию через мастер и сохраните новую версию.

Запись сериализована файловой блокировкой и журналом. Во время незавершённой
транзакции читатели Health, трекера и координатора получают прежний набор.
При следующем открытии мастера незавершённая запись восстанавливается. Если после
сбоя файлы были изменены вручную, автоматическое восстановление останавливается,
чтобы сохранить внешние правки. Прямые ручные читатели JSON не используют этот
протокол; для согласованного чтения пары предназначен `read_config_bundle`.

## Подсказки через CLI

ИИ по умолчанию выключен. «Проверить CLI» проверяет доступность, флаги
и текущую авторизацию `codex`/`claude` без запроса к модели. Выберите доступный CLI
и нажмите «Подсказать с ИИ». Нужна уже действующая авторизация именно CLI;
мастер не открывает login, не запрашивает API-ключ и не читает auth-файлы.

Подпроцесс сохраняет штатные HOME/CODEX_HOME и работает в отдельном временном
каталоге. Запрос содержит имя/тип текущего поля, допустимые варианты, штатное
пояснение, ОС и наличие известных файлов стека. Команды, пути проекта и значения
его конфигурации не передаются. Контекст намеренно ограничен: помощник может
объяснить выбор, но не угадывает стек и права доступа по исходному коду.

Codex запускается через `exec` с read-only sandbox, без пользовательского config,
правил, shell, hooks, plugins, MCP из пользовательского config и других вспомогательных
инструментов. Claude Code использует `-p --safe-mode --tools "" --strict-mcp-config`,
с сохранением OAuth/keychain авторизации; `--bare` здесь не используется.
Сессия не продолжается и не сохраняется. Запрос ограничен 90 секундами и размером
ответа; переход к другому шагу или закрытие отменяет ожидающий результат.

Предложение можно взять отдельной кнопкой в черновик. Общие проверки и итоговое
подтверждение остаются обязательными. При отсутствии CLI/login, неподдерживаемой
версии, сетевой ошибке, лимите или неподходящем ответе мастер объясняет отказ
и продолжает работать с обычными подсказками.

Конфигурации, описания версий и ответы проверяются на узнаваемые секреты,
но это не универсальный детектор. Не вводите секреты в эти поля.
Храните авторизацию в штатном хранилище CLI.

## Итоговая диагностика

Для выбранного проекта откройте Diagnostics. Offline проверяет установку и
настройки окружения; Online отдельно проверяет GitHub/GitLab CLI, авторизацию,
репозиторий и права. Local-трекер пропускает сетевые проверки.
«Apply fixes» с повторным подтверждением применяет существующие исправления Health.
Команды остальных исправлений показаны для ручного запуска.

Анализ sandbox-конфигурации и реальная проверка доступа различаются в отчёте.
Пропущенная или непроверенная операция не считается успешной.
