# Протокол замера Repo Map (#268)

## 1. Цель и порог приёмки
Контролируемый before/after на фиксированном наборе задач, одинаковых моделях и commit. Считаются все prompt input tokens (включая повторные чтения, retry и failed sessions), latency, cache hit rate, median и p95. Quality guard — completion rate, post-integration defects, число файлов вне scope.

**Порог приёмки**: **≥25% снижения median discovery input tokens** и **нет статистически заметного ухудшения** quality guard; иначе Repo Map остаётся opt-in.
*Примечание: порог записан до первого замера.*

## 3. Определения метрик
(со ссылкой на источник данных из `data-sources.md`):
- **prompt input tokens сессии**: `input_tokens + cache_read_tokens + cache_write_tokens` по всем вызовам модели, включая retry и failed sessions (берутся из `dispatch telemetry`).
- **discovery input tokens запуска**: `prompt input tokens` от начала запуска до первого мутирующего вызова (`Edit`, `Write`, `Bash` с побочными эффектами и др.); для read-only ролей (architect) — токены всей сессии. Граница определяется по сырым транскриптам сессий.
- **latency**: время до конца discovery и общее время запуска. Вычисляется по меткам времени (`timestamp`) из транскриптов.
- **cache hit rate**: `cache_read_tokens / (input_tokens + cache_read_tokens + cache_write_tokens)` по данным телеметрии.
- **completion rate**: доля запусков, прошедших приёмочную проверку задачи (зафиксирована для каждой задачи). Failed-запуски входят в знаменатель как не пройденные.
- **post-integration defects**: число дефектов (падение `qa-gate` на интеграционной ветке + blocker-замечаний `code-review` после «готово»). Каждое blocker-замечание или падение теста после developer-стадии считается как 1 дефект.
- **файлы вне scope**: число файлов диффа за пределами заранее заданного scope задачи (вычисляется из scope review).

*Всё, чего нет в телеметрии, помечается `missing`, а не 0 и не оценкой.*

## 4. Агрегация
Сначала вычисляется **median по повторам внутри задачи** (по 3 запускам), затем **median и p95 по задачам** (по 12 задачам).
- Для `discovery input tokens` считается относительное снижение median (в процентах).
- Для `p95` (и всех остальных перцентилей) следует явно отметить: **при выборке из 12 задач p95 носит справочный характер, а не является критерием приёмки**, из-за широких доверительных интервалов на малых данных. 

## 5. Правило «статистически заметное ухудшение»
Используется парный bootstrap по задачам (10 000 ресэмплов, фиксированный seed `42`), одностороннее 90% CI.
Ухудшением quality guard считается:
- **completion rate**: падение > 10 п.п. (по нижней границе CI);
- **defects и файлы вне scope**: рост median (верхняя граница CI > 0 и рост точечной оценки ≥ 1).

Порог 25% для токенов принимается при условии: нижняя граница CI снижения median > 0 и точечная оценка ≥ 25%.
Ограничения мощности: при 12×3 запусках статистические тесты имеют низкую мощность для обнаружения мелких изменений, поэтому существенными признаются только крупные деградации.

## 6. Правила запуска
- **Порядок**: чередование задач (задача 1 «до», задача 1 «после», и так далее), чтобы дрейф провайдера/кеша не смещал одну сторону системно.
- **Кеш**: перед каждым запуском (для каждого из 36 прогонов) состояние кеша должно быть единообразным (холодный старт, без предзаполнения, пауза не менее 5 минут между задачами для сброса кеша API провайдера).
- **Невалидные запуски**: failed session из-за лимитов провайдера, таймаутов сети и других причин вне харнесса **не выбрасывается**, а учитывается с `failed=true` и фактическим числом затраченных токенов (они попадают в знаменатель `completion rate`). Выборочный перезапуск таких сессий запрещён.
