## Проверка SOLID по конкретным изменениям

- **Единая ответственность.** Терминальный вывод, расчёт стоимости и baseline
  выделены из `delivery_stats.py`: сбор источников и их представление меняются
  по разным причинам. Для `workflow/reports.py` сначала нужно зафиксировать
  состояния checkpoint/resume и порядок записей ledger.
- **Открытость к расширению.** Capability catalog и role manifests уже дают точки
  расширения без правки orchestration. В `contract.health_problems` проверки разных
  частей конфигурации собраны в одной функции (около 430 строк); расширение нового
  policy сейчас требует менять её тело. Разделять следует по проверяемому контракту,
  сохраняя порядок диагностик.
- **Подстановка и сегрегация интерфейса.** `qa_lane.CoordinatorOps` описывает только
  нужные lane операции. `qa_integration._ops()` лениво связывает его с фасадом
  coordinator; статический граф импортов видит цикл, но импорт выполняется в вызове.
  Убирать этот seam без доказанного второго adapter не нужно.
- **Инверсия зависимостей.** Источники Git/GitHub и локальных логов сосредоточены в
  `delivery_stats.py`; расчёты должны принимать уже собранные данные. Новый абстрактный
  adapter без вариативности не нужен. Для тестов сохраняются существующие точки
  подмены `_git`, `_gh` и пути к ledger.

## Порядок рефакторинга

1. **Сделано:** сохранить CLI и старые импорты; вынести терминальный renderer за
   интерфейс `render_terminal(report) -> str`, проверить отсутствующие источники и
   установленную копию.
2. **Сделано:** отделить расчёты стоимости и baseline от I/O сбора telemetry с
   сохранением публичных функций и версии baseline.
3. Перед переносом `contract.health_problems` и `workflow/reports.py` добавить
   характеризующие тесты порядка ошибок и ledger transitions, затем выделить
   тематические функции внутри той же поставляемой capability.
4. Разделить clean-room сценарии после фиксации их общей fixture и порядка стадий;
   новая структура не должна менять содержание интеграционного gate.

Приёмка каждого шага: существующие CLI/JSON и persisted records не меняются,
целевой тест проходит до и после переноса, затем проходит `python scripts/verify.py`.
