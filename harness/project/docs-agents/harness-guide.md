# Справочник команд и скиллов Claude Code

> На основе инструментов и методологии из репозитория [mattpocock/skills](https://github.com/mattpocock/skills) ([aihero.dev](https://www.aihero.dev/)), установленных в этом репозитории через `.harness/` (см. `.harness/harness.lock`).

Этот фреймворк и набор специализированных навыков (skills) оптимизирует процесс разработки с помощью AI-агентов, разбивая его на строгие фазы: от проектирования через устранение неопределённости до TDD-реализации вертикальных слайсов и автоматического ревью.

**Это не общее описание фреймворка, а справочник по тому, как он развёрнут именно в этом репозитории** — с локальными кастомизациями (раздел 7), справочником меток триажа (раздел 8), проектными надстройками `qa-gate`/`pr-composer` (раздел 6) и детерминированными hooks (раздел 9), которых нет в апстриме.

---

## 0. Как это подключено: `.harness/`

Скиллы физически лежат в `.harness/skills/*/SKILL.md` (управляются `.harness/harness.lock` — хэши файлов, версия, `source_revision`). Claude Code, Codex и другие рантаймы находят их через symlink'и в корне репозитория:

```text
.agents/skills  -> .harness/skills
.claude/skills  -> .harness/skills
```

Если после клонирования репозитория скиллы не видны (`/implement`, `/triage` и т.д. отсутствуют в списке) — значит либо нет `AGENTS.md`, либо сломаны эти symlink'и. Диагностика и починка — `harness health <repo>` / `harness update` из инструмента, которым был развёрнут этот harness (не пересоздавайте symlink'и вручную — относительный таргет должен резолвиться средствами конкретной ОС, `harness health` это проверяет, а не только «файл похож на симлинк»).

## 📋 Общая схема пайплайна

```text
[ Идея / Задача ]
       │
       ▼
1. Grilling (/grill-me / /grill-with-docs) ──► Устранение неопределённости (CONTEXT.md)
       │
       ▼
2. Wayfinder (/wayfinder)                  ──► Декомпозиция больших эпиков / дорожная карта
       │
       ▼
3. Спецификация (/to-spec)                 ──► Single Source of Truth (issue в трекере, эпик)
       │
       ▼
4. Тикетирование (/to-tickets)             ──► Вертикальные слайсы с зависимостями
       │
       ▼
5. Реализация (/implement <id>)            ──► TDD Loop + qa-gate + Sub-agent Review
       │
       ▼
6. PR (pr-composer)                        ──► Тело PR по шаблону git-workflow.md
       │
       ▼
7. Human QA & Merge                        ──► Приёмка кода разработчиком (hooks блокируют авто-мердж)
```

## 1. Этап проектирования и устранения неопределённости (Grilling)

Цель этапа — устранить любые серые зоны и нестыковки до написания первой строчки кода, построив «дерево зависимых решений».

### `/grill-me`

- **Назначение:** проектирование новых фич, модулей или архитектурных концепций с нуля, без привязки к существующему коду.
- **Как работает:**
  1. Переводит агента в интерактивный режим исследования («прожарка»).
  2. Агент не генерирует рабочий код, а задаёт серию последовательных вопросов раундами (*Frontier questions*).
  3. На основе ваших ответов агент динамически перестраивает дерево архитектурных решений.
  4. Процесс продолжается до достижения полного консенсуса и взаимопонимания (*shared understanding*).
- Вызывается только вручную (`disable-model-invocation: true`) — командой `/grill-me`.

### `/grill-with-docs`

- **Назначение:** проектирование изменений в контексте уже существующего репозитория и кодовой базы.
- **Как работает:**
  1. Агент предварительно сканирует репозиторий, архитектуру и стек проекта.
  2. Формирует или обновляет словарь предметной области в `CONTEXT.md` и ADR в `docs/adr/` (см. `docs/agents/domain.md`).
  3. Задаёт прицельные вопросы с учётом существующего кода: граничные случаи, каскадное удаление, блокировки, обратная совместимость API.
- Вызывается только вручную — `/grill-with-docs`.

### `/wayfinder`

- **Назначение:** декомпозиция масштабных эпиков и комплексных рефакторингов (например, миграция легаси-систем).
- **Как работает:**
  1. Предотвращает переполнение контекстного окна (*Dump Zone*), выявляя задачи, которые невозможно спроектировать за один проход.
  2. Строит структурированную дорожную карту (*Roadmap*) — issue с меткой `wayfinder:map`, дочерние тикеты `wayfinder:<type>` (см. `docs/agents/issue-tracker.md#wayfinding-operations`).
  3. Позволяет запускать независимые сессии гриллинга для каждого подмодуля с последующим объединением артефактов.
- Вызывается только вручную — `/wayfinder`.

Не спешите переходить к генерации кода. Режим «прожарки» (`/grill-me` или `/grill-with-docs`) — это критический момент формирования единого языка (Ubiquitous Language). Чем детальнее сформирован `CONTEXT.md`, тем меньше придётся переписывать код.

## 2. Фиксация требований и спецификация (Specification)

### `/to-spec`

- **Назначение:** синтез уже обсуждённого в единый источник правды — **не интервью**, просто оформление диалога в спецификацию.
- **Как работает:**
  1. Вызывается непосредственно в сессии после завершения этапа Grilling.
  2. Генерирует структурированную спецификацию и публикует её как issue в трекере (`docs/agents/issue-tracker.md`).
  3. Включает: описание проблемы, *User Stories*, критерии приёмки, архитектурные решения, **Out of Scope** — явные границы того, что реализовывать *запрещено*.
  4. **В этом репозитории** (локальная кастомизация, раздел 7): пишет спеку сначала файлом в `docs/tasks/`, публикует через `gh issue create --body-file`; помечает `ready-for-agent` и ставит `epic::<slug>` — decomposition через `/to-tickets` наследует эту метку на все дочерние тикеты (см. `docs/agents/triage-labels.md`).
- Вызывается только вручную — `/to-spec`.

Блок **Out of Scope** — ваша страховка от инициативности ИИ. Модели склонны к переинженерии: если явно не указать, что агенту запрещено трогать, скажем, конфигурацию инфраструктуры или прикручивать лишнее кэширование, он с большой вероятностью попытается это сделать.

## 3. Декомпозиция и нарезка задач (Ticketing)

### `/to-tickets`

- **Назначение:** трансформация спецификации в набор независимых вертикальных слайсов.
- **Как работает:**
  1. Нарезает задачи по функциональным фичам (End-to-End: от хранения данных до внешнего интерфейса), а не по горизонтальным слоям.
  2. Расставляет блокирующие связи (*blocking edges*) через нативные зависимости issue-трекера (или текстовое поле `Blocked by` там, где их нет).
  3. Гарантирует, что каждый тикет изолирован и укладывается в *Smart Zone* агента.
  4. **В этом репозитории**: если исходный issue — эпик (`epic::<slug>`), та же метка проставляется на каждый дочерний тикет; тикет, заблокированный другим ещё не закрытым тикетом той же декомпозиции, получает `blocked-by-ticket` вместо `ready-for-agent` — `/implement` проверяет и снимает эту метку при старте (раздел 7, ADR в `docs/adr/`).
- Вызывается только вручную — `/to-tickets`.

AI-агенты неизбежно «глупеют» и начинают галлюцинировать, когда контекстное окно переполняется историей правок и рассуждений.

- Завершили формирование тикетов через `/to-tickets`? Очищайте память командой `/clear`.
- Если реализация отдельной фичи затянулась, используйте `/compact`.
- Каждый `/implement` запускайте с чистого листа — агенту нужны только спецификация и узкая цель тикета.

Формируйте задачи по фичам (End-to-End), а не по технологическим слоям: узкая, но полная вертикаль сработает предсказуемее, чем абстрактное «написать весь слой доступа к данным».

## 4. Разработка (Implementation)

### `/implement [ссылка_или_номер_тикета]`

- **Назначение:** исполнение конкретного тикета строго по спецификации.
- **Как работает:**
  1. Запускается в **новой, чистой сессии**.
  2. Если вызван со ссылкой на тикет (номер/URL/путь к локальному файлу) и тот несёт `blocked-by-ticket` — сначала проверяет блокеры и либо снимает метку, либо отказывается стартовать, называя открытые блокеры (раздел 7).
  3. Строит код через `/tdd` (раздел 5), затем прогоняет `/code-review`.
  4. Коммитит на текущую (feature-)ветку.
  5. **В этом репозитории** (локальная кастомизация, раздел 7): следует `docs/agents/git-workflow.md` для открытия PR — запускает `qa-gate` перед `gh pr create`, делегирует тело PR субагенту `pr-composer` (раздел 6), затем останавливается и ждёт решения разработчика — ревью или доработки. Никогда не мерджит сам. Для локального (не-GitHub/GitLab) трекера, где нет закрытия через мердж, по завершении ставит тикету `**Status:** done`.
- Вызывается только вручную — `/implement`.

## 5. Автоматизированный контроль качества (Model-Invoked Skills)

Скрытые скиллы/субагенты, вызываемые автоматически внутри цикла `/implement` (без `disable-model-invocation`).

### `/tdd` (TDD Loop)

- **Назначение:** гарантия надёжности кода через Test-Driven Development.
- **Как работает:**
  1. **Red:** пишет изолированный тест под требования тикета и фиксирует падение.
  2. **Green:** пишет минимально необходимый код для прохождения теста.
  3. **Refactor:** очищает код без нарушения тестов — рефакторинг здесь, а не в самом цикле red→green.

### `/code-review`

- **Назначение:** независимая проверка написанного кода перед сдачей разработчику, в двух параллельных субагентах.
- **Как работает:**
  1. **Standards:** соответствие кодстайлу репозитория + базовый набор code smells (Fowler) — если инструмент линтинга/типизации уже проверяет что-то, эта ось это пропускает.
  2. **Spec:** аудит соответствия исходному issue/спеке — что упущено, что лишнее (scope creep), что реализовано неверно.
  3. **В этом репозитории** (локальная кастомизация, раздел 7): язык отчёта берётся из `language` в `.harness/project.json`.

## 6. Проектные надстройки поверх апстрима

Добавлены поверх стандартного набора `mattpocock/skills` специально для этого репозитория — их нет в оригинальном фреймворке.

### `/qa-gate` (skill, `context: fork`)

- **Назначение:** полный локальный прогон качества — команды из `qa_gate_commands` в `.harness/project.json` (lint/typecheck/test), по очереди, перед открытием PR.
- **Почему `context: fork`:** запускается в изолированном форкнутом субагенте — весь шум линтеров/тестов не засоряет основную сессию. При провале в основную сессию возвращается **полный** необрезанный вывод упавшей проверки; при успехе — только короткий итог PASS.
- Вызывается автоматически из `/implement` перед `gh pr create`, либо вручную — `/qa-gate`.

### `pr-composer` (subagent, `.claude/agents/pr-composer.md`)

- **Назначение:** заполняет структурированный PR-шаблон из `docs/agents/git-workflow.md` §3 (язык — из `.harness/project.json`) — в изолированном контексте, чтобы полный diff и история коммитов не засоряли основную сессию.
- Вызывается из `/implement` на шаге открытия PR, если `git-workflow.md` требует структурированный шаблон, а не короткое summary.

## 7. Локальные кастомизации (5 изменённых скиллов)

`.harness/harness.lock` фиксирует 5 скиллов с намеренными правками поверх апстрима (видно как `local_changed` в `harness diff` — это ожидаемо и постоянно, `harness update --force`/`harness adopt --replace-conflicts` их бы стёр). `triage` **не** входит в этот список — используется апстримный вариант as-is, с канонической парой ролей `bug`/`enhancement` + 5 состояний (`needs-triage`/`needs-info`/`ready-for-agent`/`ready-for-human`/`wontfix`).

| Скилл | Что изменено |
|---|---|
| `to-spec` | Проставляет `epic::<slug>` на публикуемый issue (контекстная метка поверх канонических ролей `triage` — сам `triage` про неё не знает); пишет спеку сначала файлом в `docs/tasks/`, публикует через `gh issue create --body-file`, а не инлайн-heredoc (тело спеки регулярно ломает heredoc-квотинг). |
| `to-tickets` | Пробрасывает `epic::<slug>` от родителя на дочерние тикеты; тикету, заблокированному другим ещё не закрытым тикетом той же декомпозиции, ставит `blocked-by-ticket` вместо `ready-for-agent`; не переписывает содержимое родительского issue (кроме списка дочерних номеров). |
| `implement` | Перед стартом по ссылке на тикет с `blocked-by-ticket` — проверяет блокеры, снимает метку либо отказывается стартовать. Добавлен шаг открытия PR по `docs/agents/git-workflow.md` с паузой на ревью разработчика, без авто-мерджа; плюс вызов `qa-gate`/`pr-composer` перед PR (раздел 6); для локального трекера ставит `**Status:** done` по завершении. |
| `ask-matt` | Та же PR-пауза отражена в описании `/implement`, которое `ask-matt` предлагает как маршрут. |
| `code-review` | Отчёт обязан выводиться на языке из `.harness/project.json` (`### Communication language`). |

## 8. Метки триажа

Источник истины — `docs/agents/triage-labels.md`. `triage` использует пять канонических ролей апстрима as-is (`needs-triage`/`needs-info`/`ready-for-agent`/`ready-for-human`/`wontfix`) — таблица соответствия ролей реальным строкам лейблов в этом файле, редактируется прямо там, если вы переименовали лейблы под свой трекер.

Поверх них `to-spec`/`to-tickets`/`implement` используют два контекстных лейбла, которые `triage` не читает и не выставляет:

| Метка | Применяет | Значение |
|---|---|---|
| `epic::<slug>` | `/to-spec`, `/to-tickets` | Issue — эпик, или подзадача, декомпозированная из эпика; одна и та же метка на всей группе. |
| `blocked-by-ticket` | `/to-tickets` ставит, `/implement` снимает | Тикет из декомпозиции, чьи блокеры (другие тикеты той же декомпозиции) ещё не закрыты. |

Подробности (цвета, создание `epic::*` лейблов ad hoc, поведение для локального markdown-трекера) — в `docs/agents/triage-labels.md`.

## 9. Детерминированные hooks (`.claude/settings.local.json`)

Часть правил из `docs/agents/git-workflow.md`/`artifacts.md` не полагается только на текст промпта — закреплена как hooks, которые физически блокируют действие (`exit 2`), а не просто советуют:

| Hook | Событие | Что блокирует |
|---|---|---|
| `block-direct-master.sh` | `PreToolUse(Bash)` | `git commit`/`git push`, если текущая ветка `master`/`main`. |
| `block-pr-merge.sh` | `PreToolUse(Bash)` | `gh pr merge` — безусловно, мердж только вручную. |
| `check-branch-name.sh` | `PreToolUse(Bash)` | `git checkout -b <имя>`, не соответствующее `branch_pattern` из `.harness/project.json`. |
| `check-worktree-branch-name.sh` | `PreToolUse(EnterWorktree)` | То же правило имени для нативного worktree-инструмента (раздел 10). |
| `block-scratch-outside-docs-tasks.sh` | `PreToolUse(Write\|Edit)` | Запись спек/скретчпадов в системные temp-директории вместо `docs/tasks/`. |
| `require-qa-gate.sh` | `PreToolUse(Bash)` | `gh pr create`, если `qa-gate` ещё не запускался/провалился в этой сессии (маркер пишет `mark-qa-gate-passed.sh` при успехе последней команды из `qa_gate_commands`). |
| `block-dangerous-git.sh` | `PreToolUse(Bash)` | `git reset --hard`, `git clean -f`/`-fd`, `git branch -D`, `git checkout .`, `git restore .` — адаптировано из апстримного скилла `git-guardrails-claude-code`, не входит в вендоренный `mattpocock-suite`. В отличие от апстрима **не** блокирует `git push` целиком — `git-workflow.md` требует пуш фиче-веток; push в `master`/`main` уже отдельно закрыт `block-direct-master.sh`. |
| `count-skill-usage.sh` | `PreToolUse(Skill)` | Ничего не блокирует — аналитика на будущее: считает частоту вызова каждого скилла в `.claude/.skill-usage.json`. |

Файл личный (`.claude/settings.local.json`, в `.gitignore`) — защищает только локальные сессии на этой машине, не CI и не других контрибьюторов.

### Атрибуция коммитов

`.claude/settings.local.json` также несёт `"attribution": {"commit": "", "pr": ""}` — детерминированно убирает строку `Co-Authored-By: Claude ...` из коммитов и футер из тела PR, вместо того чтобы полагаться на то, что никто не попросит иначе.

**Известная оговорка:** в апстриме Claude Code есть открытые баг-репорты о том, что `attribution.commit`/`attribution.pr` иногда не соблюдаются — системный trailer иногда побеждает настройку. Считайте это дополнительным слоем, а не гарантией; если атрибуция всё же проскочит в коммит, поправьте вручную.

| Команда | Источник | Назначение |
|---|---|---|
| `/compact` | Встроена в Claude Code | Сжимает историю диалога, оставляя ключевые факты. Используется при затягивании тикета. |
| `/clear` | Встроена в Claude Code | Полностью очищает сессию перед стартом нового тикета. |

## 12. Полный каталог скиллов проекта

Все 25 скиллов апстрима (`.harness/skills/`, capability `mattpocock-suite`) + 1 проектный (`qa-gate`, раздел 6). «Только вручную» = `disable-model-invocation: true` (не вызывается моделью автоматически, только `/имя`).

### Инженерные

| Скилл | Только вручную? | Описание |
|---|---|---|
| `ask-matt` | да | Роутер: подсказывает, какой скилл/поток подходит под вашу ситуацию. |
| `grill-with-docs` | да | Интервью для проектирования с учётом существующего кода; параллельно ведёт `CONTEXT.md`/ADR. |
