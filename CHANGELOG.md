# Changelog

Изменения выпусков записываются в формате [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/) и версионируются по SemVer.

## [1.3.1] - 2026-10-08

### Added

- **[Ограниченные инфраструктурные повторы]:** Проект может разрешить повторы QA и публикации после подтверждённого восстановления доступа. Координатор сохраняет утверждённые границы, бюджет и прежние отчёты (#619).
- **[Правила технического русского]:** Зафиксированы правила стандарта ASD-STE100 для документации и журнала изменений в `docs/technical-russian.md` (#645).
- **[Раздельная подготовка окружения QA]:** Параметр `qa_preparation` отделяет настройку окружения от выполнения проверок кода. Сбой инфраструктуры больше не списывает попытки разработчика (#618).
- **[Проверка прав доступа]:** Координатор проверяет права перед запуском QA, Git и публикации. При нехватке прав координатор останавливает операцию и выводит инструкцию по исправлению (#617).
- **[Классификация ошибок Git]:** Координатор точно определяет причину сбоя при операциях с Git. Система больше не подменяет отказ в доступе на ошибку конфликта слияния (#617).
- **[Автоматический путь auto]:** При `approval_policy: auto` координатор проходит путь от `batch approve` до принятого publish без человека. Политика согласует каждый шаг, а `batch auto-decide` принимает решения по отчётам и пишет их как `policy:auto` с evidence (#643).
- **[Остановки и итоговый отчёт]:** Закрытый список остановок прекращает автоматический путь и передаёт каждый следующий шаг человеку. Команда `batch auto-report` выводит итоговый отчёт до открытия PR; PR открывает только человек (#643).
- **[Первый коммит документов прожарки]:** `/to-spec` коммитит изменённые документы прожарки (`CONTEXT.md`, `CONTEXT-MAP.md`, ADR в `docs/adr/`) первым коммитом `docs: …` в новую integration-ветку эпика и публикует ветку с этим коммитом. Текущий checkout переключается на новую ветку, посторонние изменения в коммит не попадают. Хук `block-direct-master.sh` разрешает только такой коммит и только до публикации ветки (#644).
- **[Перенос неполных пунктов]:** Read-only роль перечисляет невыполненные пункты brief в `incomplete_items`. Координатор передаёт их целевой роли через `--carry-incomplete` или повторяет этап суженным retry (#501).
- **[Перезапуск tooling с изменениями]:** Перезапуск инструмента после сбоя наследует незакоммиченные изменения developer. Разработчик продолжает работу без потери правок (#502).
- **[Fix-forward разработчика]:** Brief `developer-retry` несёт закрытый список перенесённых пунктов, а отчёт закрывает каждый пункт. Координатор отклоняет отчёт, если история после snapshot переписана (#503).
- **[Rebase внутри retry]:** Маршрут `rebase-fix-forward` переносит работу developer на новый target внутри retry. Координатор сверяет перенесённые коммиты через `rebased_from` и patch-id (#504).
- **[Замещающий batch]:** Команда `batch create --supersedes` продолжает работу после `abandon` в новом batch. Новый batch переносит принятый план architect и последний принятый candidate (#506).
- **[Delta-review после fix-forward]:** Code-review после fix-forward проверяет только изменения исправления. Координатор переводит review в полный режим, если условия delta-review не выполнены (#625, #628).
- **[Политика доступа ролей]:** Конфигурация задаёт доступ ролей в режимах, которые не зависят от транспорта. Координатор передаёт работу роли только после подтверждения доступа воркера (#624).
- **[QA-evidence для хука]:** Хук `require-qa-gate` принимает принятое координатором QA-evidence того же HEAD. Повторный `make verify` перед PR больше не нужен (#631).
- **[Справка verify]:** Команда `scripts/verify.py --help` описывает стадии проверки и ничего не запускает. Неизвестный аргумент завершает команду с кодом 2.
- **[Новые схемы Archify]:** Каталог `docs/diagrams/` получил пять схем: память проекта, путь `approval_policy: auto`, продолжение PR, маршруты восстановления и швы модулей. Каждая схема имеет PNG-превью.

### Changed

- **[Обновление контекстного пакета]:** Координатор автоматически создает новый контекстный пакет при изменении источников памяти. Команда `dispatch create` больше не падает с ошибкой устаревшего контекста (#636).
- **[Очистка ресурсов QA]:** Команда `qa run` корректно освобождает очередь и ресурсы при любых ошибках. Процесс не зависает и не блокирует следующие запуски (#617).
- **[Предупреждения о границах изменений]:** Выход за границы разрешенных путей теперь формирует предупреждение вместо жесткого отказа. Оператор подтверждает такое изменение явным действием `override-warning` (#633).
- **[Требования к конфигурации auto]:** Проверка конфигурации и `harness health` отклоняют `approval_policy: auto` вместе с `human_approval_gate: tty` или без `worker_attestation_required: true` (#643).
- **[Batch auto после смены конфигурации]:** Batch, созданный при `approval_policy: auto`, согласует шаги политикой, только пока конфигурация проекта выбирает `auto`. После смены политики в конфигурации каждый переход такого batch требует `--approved-by` и `--approved-at` (#643).
- **[Ограничение времени Git]:** Харнесс ограничивает время вызовов Git в хуках, координаторе, `harness health`, очистке и установке. Зависший или отсутствующий Git завершает команду с инструкцией и не блокирует сессию.
- **[Ограничение шагов clean-room]:** Каждый шаг clean-room проверки ограничен по времени. Зависший шаг завершает проверку с понятной ошибкой вместо простоя CI.
- **[Документация на техническом русском]:** README и руководства `harness/docs/` следуют правилам `docs/technical-russian.md`. Содержание, пункты и команды не изменились.

### Fixed

- **[Причина сбоя трекера]:** `harness health --online` называет причину сбоя `git ls-remote origin`: учётные данные, TLS-сертификат, прокси или сеть. Подсказка указывает исправление, а stderr, URL `origin` и учётные данные не попадают в вывод (#626).
- **[Поиск тестов unittest]:** `harness install` больше не ставит `.harness/__init__.py`, и `python -m unittest` из корня проекта снова находит тесты проекта. `harness update` удаляет этот файл прежней установки (#626).
- **[Трекер в memory sync]:** `harness memory sync` берёт трекер из поля `tracker` в `.harness/project.json` и сохраняет подгруппы пути проекта. Команда явно адресует хост в `gh` и `glab` (#626).
- **[Closure после rebase]:** Closure перенесённых пунктов после `rebase-fix-forward` принимает только коммиты цепочки retry. Перенесённые копии прежних коммитов больше не закрывают пункты (#627).
- **[Подготовка batch в implement]:** `/implement` готовит batch только по английским агентским источникам. Русская документация больше не попадает в процедуру подготовки (#641).
- **[Ложная блокировка коммитов]:** Хук `block-direct-master` больше не блокирует команду из переменной, если слово `commit` стоит только в опции. Команды без `git commit` и `git push` проходят (#642).
- **[Ложный проход QA]:** QA gate выполнял только первую часть строковой команды вида `python a.py && python b.py`. Теперь оболочка выполняет всю цепочку, и gate видит каждый сбой.
- **[Хуки на Python 3.9]:** Хуки проекта снова работают на Python 3.9. Раньше ошибка импорта блокировала любую команду Bash.
- **[Порядок остановок auto]:** Политика `auto` ищет остановку в порядке: целостность, бюджет, маршрут. Исчерпанный бюджет больше не скрывает нарушение целостности.
- **[Блокеры review в auto]:** Политика `auto` не принимает отчёт review, если ось Standards или Spec называет `blockers`. Такой отчёт останавливает автоматический путь до решения человека.
- **[Итоговый отчёт auto]:** `batch auto-report` показывает находки координатора, которые ещё не попали в brief. Отчёт считает расход бюджета на один dispatch, а подсказка следующего шага учитывает смену политики.
- **[Очистка ledger]:** `ledger clean` больше не удаляет checkpoint живых batch. При нечитаемой записи batch команда отказывает и ничего не удаляет.
- **[Повтор после решения политики]:** Инфраструктурный повтор проверяет хеш QA-отчёта. Отчёт, изменённый после решения, больше не разрешает новый brief.
- **[Публикация dispatch]:** `dispatch publish` ограничивает время `git push` и точно сверяет ветку на remote. Зависший push больше не держит блокировку ledger.
- **[Освобождение очереди QA]:** Прерванный `qa run` освобождает lease и очередь QA. Захват очереди запуском `integration local-qa` больше не ломает восстановление dispatch.
- **[Checkpoint после сдвига базы]:** Координатор сравнивает checkpoint разработчика с базой отчёта после сдвига integration-ветки. Файлы из upstream больше не вызывают ложный отказ.
- **[Разрешение конфликтов]:** `integration resolve` после гонки с target называет созданный batch и точную команду `batch abandon`. Повтор resolve после этого проходит.
- **[Проверка локального QA]:** `integration local-qa` правильно сообщает, что ветка не основана на target. `context-package register` сравнивает `--base-commit` с фактической базой пакета.
- **[Файлы не в UTF-8]:** Координатор читает diff с файлами в устаревших кодировках без аварийного завершения. Отчёт или манифест роли не в UTF-8 даёт ошибку с инструкцией.
- **[Context Package]:** Context Package включает изменённые файлы с не-ASCII именами и вложенные ADR. Сбой Git при сборке пакета даёт ошибку с инструкцией.
- **[Устойчивость Repo Map]:** Repo Map переходит в деградированный режим при повреждённом lock, политике не в UTF-8 и ошибке чтения bundle. Кэш больше не оставляет временные файлы.
- **[Память проекта]:** Память принимает glob-шаблоны в корне проекта. Занятый индекс даёт ошибку «memory writer busy».
- **[Инвентарь интеграций]:** Установщик больше не перезаписывает нечитаемый `.harness/integrations.json`. Команда просит исправить файл и сохраняет записи проекта.
- **[Статистика доставки]:** Отчёт статистики проверяет карточку тарифов и сообщает инструкцию при нечитаемых файлах. Повреждённые записи ledger больше не прерывают отчёт.
- **[Пульт harness console]:** Экраны пульта показывают ошибку фонового запуска вместо бесконечного статуса «выполняется…». Дашборд по умолчанию перехватывает вывод команд.
- **[Сводка qa-gate]:** Сводка `qa-gate` сообщает `Status: ERROR`, если команду нельзя запустить. `diff_coverage` учитывает изменённые файлы с не-ASCII именами.

### Security

- **[Push из issue-ветки]:** Хук `block-direct-master` блокирует `git push --all`, `--branches`, `--mirror` и glob-refspec. Такие push могли обновить `main` или `integration/*`.
- **[Проверка приватных имён]:** `check_private_terms` блокирует публикацию, если Git не ответил вовремя. Раньше таймаут пропускал проверку.
- **[Каталог поколений ledger]:** Ledger отклоняет имя поколения с разделителями пути. Указатель больше не выходит за каталог ledger.
- **[Список vendor snapshot]:** Проверка vendor snapshot сверяет список файлов в `SHA256SUMS`, а не только их число. Лишняя или повторная строка больше не скрывает непроверенный файл.

## [1.3.0] - 2026-10-06

### Added

- **[Явная настройка трекера]:** Поле `tracker` в файле конфигурации задает тип и адрес трекера задач. Харнесс использует эти настройки для проверок, хуков и отчетов (#436).
- **[Проверка трекера в health]:** Команда `harness health` показывает параметры трекера в офлайн-режиме. При отсутствии настройки команда выводит готовый пример конфигурации (#436).
- **[Параметры трекера при установке]:** Команда `harness install` принимает параметры трекера через флаги командной строки. Установщик сохраняет существующий файл конфигурации проекта (#436).
- **[Полная поддержка GitLab]:** Скиллы и сценарии поддерживают работу с GitLab через CLI `glab`. Сценарии реализуют полный цикл запросов на слияние и адресацию хостов с нестандартным портом (#451).
- **[Статистика задач GitLab]:** Команда сбора статистики строит дерево эпика по связям задач. Метрики запросов на слияние собираются напрямую через `glab` (#449).
- **[Проверка версии glab]:** Команда `harness health` проверяет минимальную версию и авторизацию `glab`. При устаревшей версии команда предлагает инструкцию по обновлению (#451).
- **[Диагностика окружения в health]:** Команда `harness health` проверяет права песочниц и настройки кеша. Команда также контролирует соответствие базовых веток в открытых задачах (#583).
- **[Внутренний кеш uv]:** Харнесс размещает кеш пакетов внутри проекта (`UV_CACHE_DIR`). Это позволяет безопасно выполнять установку зависимостей в изолированной песочнице (#595).
- **[Стандарт технического английского]:** Харнесс включает правила технического английского для общения агентов. Файл инструкций связывается с проектом без перезаписи существующих файлов (#521).
- **[Автоматическое согласование отчетов]:** Режим `approval_policy: auto` позволяет координатору автоматически принимать успешные промежуточные отчеты. Публикация и открытие PR по-прежнему требуют подтверждения человека (#455).
- **[Гибкий план коммитов]:** Координатор сверяет покрытие критериев готовности по плану архитектора. Несовпадение точного числа коммитов больше не останавливает конвейер (#501).
- **[Маршруты восстановления задач]:** Координатор классифицирует сбои инструментов по таблице маршрутов. Координатор перезапускает инструмент без списания попытки разработчика (#496).
- **[Перенос замечаний в ревью]:** Координатор переносит замечания в задание для проверки кода. Рецензент получает точный список пунктов для контроля (#501).
- **[Параллельное выполнение задач]:** Координатор запускает параллельные задачи в изолированных рабочих каталогах. Блокировки по общим зонам файлов сняты (#531).
- **[Регистрация проверок интеграции]:** Команда `integration prepare` связывает задачу с опубликованной веткой. Команда сохраняет неизменяемую запись проверок (#532).
- **[Автоматическое обновление ветки]:** Команда `integration refresh` обновляет ветку задачи при сдвиге целевой ветки. Разработчику не нужно переделывать работу вручную (#533).
- **[Разрешение конфликтов интеграции]:** Роль `conflict-resolver` разрешает конфликты слияния в рамках выделенного бюджета. Оператор принимает решение о продолжении сессии (#534, #537).
- **[Учет результатов CI]:** Команда `integration collect-ci` запрашивает статус внешних проверок из трекера. Успешный CI заменяет повторный запуск тяжелых локальных тестов (#535).
- **[Локальная проверка интеграции]:** Команда `integration local-qa` выполняет полный локальный контроль качества. Команда использует этот режим при отсутствии внешнего CI (#536).
- **[Навигация по шагам интеграции]:** Команда `integration next` подсказывает следующее необходимое действие. Команда `/to-pull-requests` автоматизирует подготовку ветки к слиянию (#537).
- **[Защита от утечки имен]:** Хуки и тесты блокируют публикацию приватных внутренних терминов. Проверка работает локально и в CI перед созданием коммитов (#438).

### Changed

- **[Явная адресация в CLI]:** Команды `gh` и `glab` явно указывают целевой проект. Разработчики исключили ошибки перенаправления команд в чужой репозиторий (#440).
- **[Права групп GitLab]:** Проверка доступа корректно обрабатывает права, унаследованные от родительских групп. Пользователи получают доступ без лишних настроек (#440).
- **[Понятные ошибки проверки веток]:** Хуки проверки имен веток выводят точную причину отказа. Разработчик сразу видит проблему с доступом или номером задачи (#442).
- **[Уточнение руководств проекта]:** Документация описывает только реально устанавливаемые проверки. Разработчики удалили недостоверные обещания проверок на стороне CI (#587).
- **[Обоснованные блокировки задач]:** Скилл `/to-tickets` блокирует задачи только при реальной зависимости по данным. Пересечение файлов больше не создает ложных блокеров (#538).

### Fixed

- **[Точный разбор команд GitLab]:** Хук проверки распознает команды создания MR с короткими флагами. Разработчики устранили ложные срабатывания на текст внутри комментариев и кавычек (#443).
- **[Проверка метаданных публикации]:** Хук проверяет параметры команд трекера и файлы описаний. Текст многострочных блоков ввода больше не анализируется как код (#444, #559).
- **[Создание интеграционной ветки]:** Хук защиты от прямых коммитов проверяет каждый каталог в команде. Публикация новой интеграционной ветки больше не блокируется (#446, #476).
- **[Блокировка только реальных команд]:** Хук опасных команд Git реагирует исключительно на реальный запуск. Харнесс разрешает упоминание команд в цитатах и скриптах (#566).
- **[Корректная проверка путей]:** Хуки временных файлов разрешают запись в каталоги памяти агентов. Хуки проверяют объем вывода тестов только при реальном запуске (#445).
- **[Фиксация проверок в worktree]:** Скилл `qa-gate` корректно находит конфигурацию в связанных рабочих каталогах. Скилл надежно записывает маркер прохождения тестов (#463, #600).
- **[Строгая фиксация контроля качества]:** Скрипт проверки выставляет маркер только при полном прохождении проверок. Маскировка ошибок через `|| true` больше не позволяет обойти контроль (#611).
- **[Безопасное обновление эпиков]:** Скилл `/to-tickets` обновляет описание эпика через файлы. Это предотвращает искажение текста из-за экранирования в командной строке (#447).
- **[Очистка неактивных рабочих каталогов]:** Команда жесткой очистки удаляет неактивные рабочие каталоги после отправки изменений. Мусор больше не накапливается на диске (#565).
- **[Стабильная работа на Windows]:** Установщик корректно обрабатывает неинтерактивный ввод на Windows. Команда `health` экранирует пути и безопасно запрашивает задачи (#514, #602).
- **[Устойчивость блокировок журнала]:** Координатор повторяет попытки при занятой блокировке журнала. Координатор автоматически снимает поврежденные блокировки по таймауту (#498, #525).
- **[Надежный перезапуск разработчика]:** Повторный запуск разработчика наследует контекстный пакет и инструкции. Отмененные задачи не мешают продолжению работы (#524, #540).
- **[Устранение взаимных блокировок]:** Промежуточная фиксация изменений продолжается без задержек. Разработчики устранили ошибки зависания при проверке окружения (#606).
- **[Ранние отчеты остановки]:** Координатор корректно принимает отчет об остановке до изменения файлов. Конвейер требует соблюдения всех проверок перед кодированием (#607).
