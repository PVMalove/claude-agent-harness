# Changelog

Изменения выпусков записываются в формате [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/) и версионируются по SemVer.

## [1.3.0] - 2026-10-06

### Added

- Явный трекер проекта: необязательное поле `tracker: {type, host, project}` в `.harness/project.json` — единственный источник трекера для `harness health`, hooks, скиллов и отчётности. Без поля трекер определяется разбором `origin` с учётом схемы, userinfo, порта и подгрупп.
- `harness health`: проверка `tracker.project` без сети показывает тип, хост, проект и источник трекера; без поля `tracker` выдаёт `warn` с готовым сниппетом, при расхождении поля с `origin` — `warn`, и используется поле.
- `harness install` предлагает значения поля `tracker` по умолчанию из `origin` и принимает их флагами `--tracker-type`, `--tracker-host` и `--tracker-project`; существующий `.harness/project.json` не переписывается.
- Паритет GitHub/GitLab: скиллы публикации эпика, тикетов и меток, полный цикл merge request (MR в интеграционную ветку с `Related to`, MR в ветку по умолчанию с `Closes` и проверкой закрытия тикета), triage и гайды workflow и трекера целевого проекта дают рабочие команды `glab` с явной адресацией проекта. `glab api` получает хост через `GITLAB_HOST`: `glab` отклоняет порт в `--hostname`, поэтому так работает и хост с нестандартным портом.
- Delivery stats для GitLab: дерево эпика строится по связям `relates_to` и разделу `## Parent`, данные MR берутся через `glab` с явной адресацией проекта.
- `harness health` требует `glab` не ниже 1.117.0 для GitLab-трекера проекта (старше — `fail` с подсказкой обновления) и проверяет авторизацию `glab` ровно на хосте трекера.
- `harness health` проверяет настройки песочниц обоих поддерживаемых runtime, включая запись в каталог кеша `uv`, и согласованность раздела `## Git base` открытых тикетов в работе с интеграционной веткой или `base_branch`.
- Кеш `uv` внутри проекта (`UV_CACHE_DIR`), чтобы `uv sync` работал в песочнице.
- Общий контракт технического английского для целевых проектов и backend-оркестрации; обязательная ссылка на него в `AGENTS.md` предлагается без замены seed-файлов.
- Backend-оркестрация: `approval_policy: auto` — координатор сам принимает чистые отчёты любого batch, включая чистый QA; publish, открытие PR, merge, совпавшие risk triggers, findings, упавшие проверки и blockers остаются ручными.
- Backend-оркестрация: commit plan архитектора закрепляется при accept, расхождение числа коммитов с планом не блокирует pipeline, а `dod_coverage` сверяется с `commit_map` и `covers` плана.
- Backend-оркестрация: поле `route` в routing record и таблица маршрутов восстановления; маршрут `tooling-retry` для сбоя инструмента без расхода developer-бюджета и маршрут `bypass-rerun` для read-only роли, обошедшей блокировку.
- Backend-оркестрация: находки координатора при accept переносятся отдельными пунктами в brief code-review.
- Backend-оркестрация: batch закрепляет явный scope (`--allowed-path`, `allowed_paths` попадают в `write_paths` brief писателя), а замок по zone снят: параллельные batch с пересекающимися файлами идут в своих ветках и worktree, единственный предел — `concurrency_budget`. `zone` осталась необязательной аудит-меткой, старые конфиги, ledger и briefs принимаются (#531).
- Backend-оркестрация: учёт интеграции после publish — `integration prepare` связывает тикет, опубликованную ветку, batch и пару candidate/target SHA, а `integration link-evidence` регистрирует evidence проверок пары отдельной неизменяемой записью (#532).
- Backend-оркестрация: `integration refresh` перебазирует issue-ветку на сдвинувшийся target при подготовке PR вместо принудительного возврата к developer; проверки свежести базы перед code-review и publish больше нет (#533).
- Backend-оркестрация: роль `conflict-resolver` и маршрут `integration resolve` — resolver продолжает сессию по human-decision и ограничен двумя target-циклами и бюджетом; провалившаяся проверка обновлённой пары тоже уходит в resolver (#534, #537).
- Backend-оркестрация: CI как доказательство проверенного объединённого результата PR — необязательное поле `ci_required_checks` в `.harness/project.json`, команда `integration collect-ci` и учёт в `integration status` только принятого коллектором CI (#535).
- Backend-оркестрация: `integration local-qa` — запасной полный QA точной пары candidate/target через общую очередь QA, когда CI отсутствует или непригоден (#536).
- Backend-оркестрация: read-only `integration next` и подсказка следующего шага после `collect-ci`; `to-pull-requests` ведёт актуализацию ветки, resolver, CI, запасной QA и handoff для ручного merge (#537).
- Проверка приватных имён перед публикацией в репозитории харнесса: staged diff, коммиты, имя ветки и тела публикаций проверяются в `make verify`, repo-local hook и CI, а вывод называет только место и номер термина. В архив релиза и в целевые проекты проверка не входит.

### Changed

- Все вызовы `gh` и `glab` адресуют проект трекера явно, поэтому другой remote или учётные данные другого хоста не перенаправляют команду.
- Права на GitLab учитывают членства, унаследованные от родительских и приглашённых групп.
- Branch-name hooks проверяют issue через трекер проекта и называют причину отказа: issue не найдена, issues отключены, нет авторизации или проект недоступен.
- Гайды целевого проекта больше не обещают CI-проверку атрибуции, которую харнесс не устанавливает.
- `to-tickets`: блокер между тикетами ставится только за зависимость по результату или известную несовместимость требований, с причиной; пересечение файлов блокером не является, а блокер снимает подтверждённый merge предшественника, а не push, publish, принятый QA или открытый PR (#538).

### Fixed

- QA-gate распознаёт `glab mr create`, в том числе с `-s`/`--source-branch`; `glab mr merge` и `glab mr accept` блокируются так же, как `gh pr merge`, а запрет merge решается по разобранным токенам команды и не срабатывает на текст в heredoc, кавычках и комментариях.
- Проверка публичных метаданных читает короткие флаги `gh` и `glab`, комментарии к issue и PR/MR и `glab api … -F body=@<file>`, а тела heredoc не разбирает как команды.
- Zero Direct Commits проверяет checkout каждого `git commit` и `git push` в команде; первый push новой интеграционной ветки не блокируется.
- `block-dangerous-git` блокирует запуск опасных команд git, а не их упоминание в тексте.
- Scratch-path hook называет настоящую причину для пути вне проекта и не блокирует каталог памяти runtime; bounded-check срабатывает только на реальный запуск тестов или QA-набора.
- QA-маркер записывается после принятого QA evidence координатора и в linked worktree; skill `qa-gate` в linked worktree берёт `.harness` основного checkout.
- QA-маркер засчитывает только прогон всей последней команды из `qa_gate_commands` — отдельными командами или целиком в обёртке `bash -lc` или `-Command` — и только если успех вызова означает её успех; частичный прогон и маскировка вроде `|| true` маркер больше не ставят.
- `to-tickets` называет команды дописывания списка подзадач в эпик: `gh issue edit --body-file` на GitHub и `glab issue update --description-file` на GitLab.
- Hard cleanup убирает чистые неактивные worktree на ветках `integration/*` и в detached HEAD, если их коммиты сохранены на `origin`.
- `harness install` на Windows не считает stdin из NUL терминалом; `harness health` на Windows экранирует путь в сниппете и запрашивает тикеты без `&`.
- Backend-оркестрация: `dispatch wait` и `report submit` переживают занятый lock ledger, а `ledger release-lock` снимает lock с нечитаемой записью владельца по возрасту.
- Backend-оркестрация: developer-retry стартует с компакта, промпт воркера строится от Context Package и содержит обязательный протокол отчётности, а batch carry-over после `batch resume` пропускает abandoned dispatch.
- Backend-оркестрация: write-checkpoint продолжается без дедлока из-за стартовой аттестации runtime (#606).
- Backend-оркестрация: ранний `blocked`-отчёт писателя, остановленного до изменения кода, принимается, а implement требует полные gates (review, qa) до запуска developer (#607).

## [1.2.0] - 2026-10-02

### Added

- Память проекта (RAG): вычисляемый SQLite FTS5 кэш «как это решали раньше» на основе локальных источников (ADR, глоссарий, архив задач, Completion reports, QA findings и Lifecycle ledger).
- Команды `harness memory`: `build` (построение кэша), `search` (поиск с ранжированием BM25), `rebuild` (полная пересборка), `sync` (санитизированный snapshot тикетов и PR из трекера) и `eval` (офлайн-оценка качества).
- Замороженные указатели памяти в Context Package: подбор релевантных карточек по цели и DoD тикета с метаданными (заголовок, статус, путь, hash) без включения недоверенного текста источников; поддержка флага `--no-memory`, квот по типам источников и лимита токенов внутри бюджета пакета.
- Доказательная база памяти в Completion report: поля `used_memory` (использованные источники) и `lessons` (извлечённые уроки).
- Диагностика памяти проекта в `harness health`: проверка доступности SQLite FTS5, конфигурации `memory_policy`, свежести индекса и snapshot трекера.
- Общий индекс для linked worktree: чтение локального индекса основного checkout без повторной индексации.
- Офлайн golden-гейт качества поиска на корпусе тикетов с замером recall@k и уровня шума.
- Документация и руководство по памяти проекта (`harness/docs/project-memory.md`) и процедуре обновления существующих проектов в `harness/docs/harness-guide.md`.

### Changed

- Конфигурация проекта `.harness/project.json` поддерживает опциональные секции `memory` и `memory_policy` (по умолчанию память выключена, существующие проекты продолжают работать без opt-in).

### Fixed

- Предотвращено зависание завершения цикла asyncio в тестах консоли и добавлена ограниченная диагностика Windows verify.

## [1.1.1] - 2026-10-02

### Fixed

- Backend-оркестрация: retry developer-отчёта без `accept` больше не заводит batch в тупик. Следующий developer dispatch пинит `snapshot_commit` на кандидат этого отчёта, создаётся и отправляется, а его коммиты продолжают историю кандидата: `commit_map` считает только новые коммиты. Для такого кандидата можно зарегистрировать risk assessment, и code-review/QA он не открывает. Retry после принятого кандидата работает как раньше.
- Backend-оркестрация: `dispatch create` выполняет те же проверки brief, что `dispatch send`, включая связь кандидата с risk assessment. Brief, который send гарантированно отклонит, больше не выдаётся, а remedy называет нужную команду.

## [1.1.0] - 2026-09-28

### Added

- `harness uninstall <repo>`: полное удаление харнесса из проекта — `.harness/`, discovery-ссылок, seed-файлов, `AGENTS.md`, `CLAUDE.md` и строк харнесса в `.gitignore`. Без `--apply` выводится план; `--apply --confirm UNINSTALL` применяет его, предварительно копируя изменённые проектом файлы и проектные данные `.harness/` в `.harness-uninstall-backup/<время>/`. При активных batch оркестрации удаление отклоняется.
- `harness console`, раздел Harness: план и применение удаления харнесса (ввод `UNINSTALL`).

## [1.0.1] - 2026-09-28

### Added

- `harness console`, раздел Harness: команды `update --force-managed-files` и `update --force-seed-files`, предпросмотр hard-очистки; команды очистки soft/hard (план и применение) сгруппированы после команд установки.

### Changed

- `harness console`: фон задан только у экрана — остальные элементы прозрачны и разделены рамками с заголовками (верхняя полоса со значком меню `☰`, «Вывод» команд, Diagnostics, Reports, отчёт, хронология, QA-логи, Help, Repo Map); выбранный элемент списков, дерева и вкладок и кнопка под курсором выделяются цветом, без заливки.
- `harness console`, Dashboard: в «Состоянии» перечислены ошибки и предупреждения health, факты Repo Map выводятся по одному на строку; панель прокручивается внутри рамки.
- `harness console`: кнопка «Offline checks» на Dashboard и в Diagnostics повторно запускает офлайн-проверки.

### Fixed

- `harness console`: в невысоком окне панели Harness и Orchestration больше не наезжают друг на друга — списки состояний и команд прокручиваются внутри своих рамок.

## [1.0.0] - 2026-09-28

### Added

- Первый стабильный выпуск переносимого Agent Harness с capability-снимками, CLI установки, оркестрацией и Repo Map.
- GitHub Release с архивом установки, SHA-256 и заметками из этого раздела; публикуется автоматически после merge в `master`, если тега версии из `harness/VERSION` ещё нет.
- Управляемый пример `.harness/orchestration.example.json` для `backend-orchestration`: обновляется при `init`, `adopt` и `update`; `init` один раз создаёт из него `.harness/orchestration.json`.
- Справочник оркестрации `harness/orchestration/README.md`: устройство coordinator и все поля `orchestration.json` с дефолтами.
- README: каталог всех скилов с описаниями на русском, инструкции `harness health` и `harness console`.
- Русские описания проектных агентов в `docs/agents/` с полным переводом манифестов и `docs/agents/README.md`.
- `harness console`: тёплая тема в палитре терракоты и янтаря, знак харнесса с описанием установки на главном экране, раскраска статусов в Diagnostics и раздел `Help` (также `F1`).
- `harness console`: в разделе Harness — состояние установки и использование пайплайна, в Orchestration — статистика пайплайна и история batch с фильтром по состоянию и переходом к хронологии.
- Переписан справочник `harness-guide.md`: навигация по задачам, таблицы-шпаргалки, примеры команд и вывода, восемь новых диаграмм Archify (выбор команды установки, `/to-spec`, `/wayfinder`, `/fast-implement`, `/tdd`, метки `status::*`, два сквозных примера).
- Все 23 диаграммы в `docs/diagrams/` проходят `archify finalize` (validate, deliver, check, browser-check); превью перегенерированы, картинки справочника поставляются рядом с ним в `harness/docs/diagrams/`, а `scripts/verify.py` сверяет их с `docs/diagrams/previews/`.

### Changed

- Установщик глобального слоя переименован в `bin/install-global.py`: запуск `python3 bin/install-global.py ...`.
- Справочник харнесса и руководство по backend-оркестрации перенесены из `docs/agents/` в управляемый снимок `.harness/docs/{harness-guide,backend-orchestration}.md` (источник — `harness/docs/`) и обновляются командой `harness update`; прежние копии в `docs/agents/` целевого проекта больше не используются и удаляются вручную.
