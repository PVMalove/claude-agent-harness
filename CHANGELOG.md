# Changelog

Изменения выпусков записываются в формате [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/) и версионируются по SemVer.

## [Unreleased]

### Added

- **[Запись lifecycle через runtime store]:** При `ledger.json` версии 4 каждая мутация batch и dispatch идёт в Rust runtime операцией `state.write` (протокол 1.1): блок `_ledger_lock` команды стал единицей записи, примитивы ledger накапливают мутации, чистый выход отправляет по одной транзакции `BEGIN IMMEDIATE` на batch с CAS по `revision` каждой прочитанной строки, порядком строк `batch` → `qa_lane` → `generation`, записью `operations` (повтор с тем же `operation_id` возвращает сохранённый результат, тот же id с другим запросом — `idempotency_conflict`) и одной записью audit на мутацию. Python не открывает `runtime.db`, не берёт `.coordinator.lock` и не имеет запасного пути записи; `revision_conflict`, `store_busy` и `runtime_unavailable` — разные ошибки с кодом выхода 2 и кодом в скобках первой строки REMEDY. Каждый внешний блок `_ledger_lock` читает свежий снимок store (опрос `dispatch wait` видит новый `reported` и heartbeat), отказ `qa run` по доступу и отказ `dispatch create` по `needs_attention` сохраняют свои записи, недостающий checkpoint audit строится до транзакции записи, а ошибка чтения store при проверке даёт `store_busy` или `internal`, а не `invariant_violation`. Схема store версии 2 добавляет таблицу `operations`, `revision` строк `dispatch_status`, `qa_queue` и `record`, столбец `execution_state` с CHECK терминального состояния dispatch и singleton `audit_checkpoint`; `harness-runtime serve` переводит store версии 1 на версию 2 при старте, а store более новой версии отказывает без записи. Реестр `systemFields.v1` получил `runtime.operation_state` и `runtime.execution_state` (#801).
- **[Checkpoint audit-цепочки и `ledger validate --full`]:** Обычная команда проверяет только записи audit после checkpoint, запись двигает checkpoint, а удалённый или повреждённый checkpoint означает полную проверку и перестраивается без ошибки. `coordinator.py ledger validate --full` (операция `state.validate`) пересчитывает цепочку от genesis без checkpoint, сверяет её с якорем импорта, манифестом и хешами legacy audit, запускает `integrity_check` и сверяет каждую строку, записанную командой, с последней записью audit её пути: находятся удаление, вставка и перестановка записей. `ledger migrate`, `ledger clean` и `ledger reset` в эпохе runtime store отказывают кодом 2 (#801).
- **[Команда `harness-runtime migrate` и runtime store]:** `harness-runtime migrate --repo <repo>` переводит state-каталог установки 1.x (ledger версии 3) в SQLite-store `state/runtime.db` одной операцией по ADR 0020: предусловия (нет QA-lease и очереди, нет dispatch в `dispatched`/`working` — строже ADR 0020, живость worker-а не проверяется, поэтому оператор дожидается отчётов или переводит зависшие dispatch в `abandoned`, структура и хэши ledger и контракт batch проходят Rust-проверку, равную `ledger validate`: запечатанные recovery events, startup evidence, context pressure, carried items, attention, записи `auto` и равенство batch его immutable plan; состояние, которое отклоняет `ledger validate`, отклоняет и migrate кодом 2, а списки полей и значений Rust сверяет с Python тест), legacy-замок `.coordinator.lock` с `owner.json` (`operation: runtime-cutover`) и удерживаемым `flock`, снимок state в `.harness/orchestration/state-snapshots/<utc>/` с `snapshot-manifest.json` и `fsync`, импорт в `runtime.db.importing`, сверка паритета в Rust (sha256 канонического JSON каждой записи выбранного поколения и проекции строк, расхождение допустимо только в полях правила repair, чью запись `migration-repair` с `before_sha256` и `after_sha256` хранит audit; legacy `audit/*.json` и `lock-audit/*.json` лежат в `legacy_audit` побайтно, первая запись цепочки `legacy-import` несёт `manifest_sha256`), повторный хэш state против снимка и точка фиксации: `runtime.db`, `AUTHORITY.json`, затем `ledger.json` с `version: 4` — старая установка 1.x отказывает с кодом 2. Каждый отказ и сбой печатает `REMEDY:` с действием оператора. Команда печатает одну JSON-строку и завершается с кодом 0 (повтор после точки фиксации — `already_cut_over: true` без изменений), 2 (отказ по предусловию, ничего не изменено), 3 (сбой после начала, частичный store удалён, authority прежняя) или 4 (legacy-запись во время импорта, расхождение паритета). Живой владелец замка не снимается, мёртвый — только по вердикту `owner-dead` с записью в `lock-audit`; legacy-поколения и audit не переписываются. Импорт чинит #781: batch с `risk_reassessment_required = true` без `risk_reassessment_candidate` получает `risk_reassessment_pending_next = true`, запись `migration-repair` хранит `before_sha256`, `after_sha256` и правило, а CHECK таблицы `batch` не принимает такую строку. Каноническая форма JSON Rust совпадает байт в байт с `_canonical` Python (golden-фикстура проверяется обоими языками). В debug-сборке `HARNESS_RUNTIME_TEST_PAUSE_AT` и `HARNESS_RUNTIME_TEST_FAIL_AT` останавливают или ломают каждый шаг для SIGKILL-тестов; в release-сборке этих хуков нет. Quarantine и overlay system-fields старой миграции не переносятся: состояние с неизвестным или нечитаемым значением отклоняется целиком (#797).
- **[Откат `harness-runtime rollback --to-legacy`]:** Команда `harness-runtime rollback --to-legacy [--repo <repo>] --approved-by <человек> --approved-at <время RFC 3339> --reason <текст>` возвращает state-каталог из runtime store установке 1.x по ADR 0020, раздел 5. Пустое поле approval и время не в формате RFC 3339 или из будущего отклоняются кодом `malformed_request`, approver `policy:` — кодом `policy_denied`. Команда держит замок экземпляра `serve` (работающий `serve` — код 2, `lease_held`), берёт legacy-замок с `operation: runtime-rollback` и отказывает кодом 2 без записи, если схема store новее runtime, в QA-lane есть lease или очередь либо исполнение dispatch в `launching`, `running`, `stopping` или `unknown`; dispatch в `dispatched` или `working` с остановленным исполнением или без него экспортируется как есть. Затем Rust пишет неизменяемый архив `state/runtime-export/<store_id>.tar` (детерминированный ustar: `store_meta.json`, вся audit-цепочка, operations, revisions и `execution_state`, `qa_lane.json`, `MANIFEST.json` с sha256), новое поколение формата v3 со всеми каталогами записей, побайтной копией legacy audit импортированного поколения и записью `runtime-rollback`, и сверяет поколение со store правилом паритета импорта. Store получает audit-запись `runtime-rollback` с sha256 архива, выходит из WAL и становится read-only; `runtime.db` не удаляется, версия схемы не понижается. `AUTHORITY.json` получает `authority: file-ledger`, `rolled_back_from`, поколение и архив, а замена `ledger.json` на `version: 3` — точка фиксации. Повтор после неё отвечает `already_rolled_back: true` с кодом 0, повтор после сбоя продолжает с последнего завершённого шага. Архив, который незавершённая попытка установила до audit-записи `runtime-rollback`, не назван ни одной записью, поэтому повтор заменяет его архивом изменившегося store; архив, названный этой записью, не заменяется. Коды выхода 0/2/3/4 те же, что у `migrate` (#803).
- **[Чтение `dispatch status`, `batch list`, `batch decision-packet` и `qa status` из store]:** При `ledger.json` версии 4 эти четыре команды получают записи через `runtime_client` (операция `state.read`, записи в форме legacy-файлов из одной read-транзакции и ревизия store) и не открывают ни файловый ledger, ни `runtime.db`; замок ledger не берётся, а `store_busy` и `revision_conflict` показываются как прежний `ledger_busy`. Runtime подключает store лениво: `hello` называет `store_id` и feature `state.read`, когда store — authority. `dispatch status` в этой эпохе не опрашивает движок и ничего не пишет, поле `report` пакета решения — адрес записи внутри store. Остальные команды coordinator при версии 4 по-прежнему отказывают с кодом 2; мутации через store остаются за #801 (#797).
- **[Сервер `harness-runtime serve` и `coordinator runtime status`]:** Rust workspace `native/harness-runtime` (crates `contracts`, `ipc` и бинарь `harness-runtime`, без `unsafe`) слушает Unix domain socket `$XDG_RUNTIME_DIR/harness/<repo-id>.sock` (без `XDG_RUNTIME_DIR` — каталог `runtime/` в state-каталоге репозитория). Каталог `0700`, сокет и файл токена `<repo-id>.token` — `0600`; uid клиента проверяется через `SO_PEERCRED`, токен предъявляется в `hello`. Кадр — длина `u32` big-endian и JSON UTF-8; `hello` согласует версию протокола по общему major. `runtime_client.py` повторяет запрос с тем же `operation_id` до `request_deadline`; недоступный runtime даёт `runtime_unavailable` без записи в обход, ошибка протокола — код 2 и `[<код>]` в первой строке `REMEDY:`. Коды ошибок и домены отказов runtime добавлены в реестр `systemFields.v1`, drift-проверка Python и Rust входит в CI. При заданном `XDG_RUNTIME_DIR` один runtime на репозиторий обеспечивает файл блокировки `<repo-id>.lock` в каталоге runtime, а linked worktree обслуживается тем же runtime, что и основной checkout, поскольку `hello` сверяет `repo-id` общего git-каталога. Без `XDG_RUNTIME_DIR` каталог runtime строится от корня рабочего дерева: клиент из linked worktree не находит сокет основного checkout (`runtime_unavailable`), а `serve --repo <worktree>` запускает второй runtime со своей блокировкой; пока ADR 0021 и ADR 0022 не согласуют запасной каталог с общим git-каталогом, запускайте runtime и клиентов с одним и тем же `XDG_RUNTIME_DIR`. Docker-исполнитель на preflight отклоняет план, корень которого совпадает с каталогом, сокетом или токеном runtime, лежит под ними, содержит существующий общий каталог `$XDG_RUNTIME_DIR/harness` либо содержит сокет или токен работающего runtime. Без `XDG_RUNTIME_DIR` каталог лежит в `shared_storage` плана, а проверка выполняется только на preflight: контейнер, одобренный при остановленном runtime, увидит сокет и токен runtime, запущенного позже. Пока работает docker-worker, не запускайте `harness-runtime` без `XDG_RUNTIME_DIR` вне корней плана; вынос запасного каталога из корней плана остаётся за ADR 0022. Команда `runtime status` только читает (ADR 0021, #792).
- **[Наблюдение за worker]:** `dispatch observe` читает локальные события, `terminal.json` и ledger без вызова модели; консоль показывает выбранный worker в разделе рабочих сессий с ответами на запросы native permissions. Закрытие, повторное открытие и reconnect панели не останавливают worker и не запускают второй процесс (#716).
- **[Ранний сбой worker]:** `execution_policy.worker_startup_timeout_seconds` (120 секунд по умолчанию) закрепляется в brief. `dispatch wait` возвращает `startup_failed` при доказанном раннем выходе, `startup_timeout` при пропущенном первом self-report и `worker_exited_without_report`, если после self-report процесс исчез без отчёта; последнее событие ничего не меняет в ledger (#716).
- **[Перезапуск одним решением]:** `batch resume-stop --restart` заменяет цепочку из двух подтверждений одним решением человека для доказанно остановленного worker. Причина повтора architect (`retry_reason`) попадает в brief из `--note`, пустая заметка отклоняется (#716).
- **[Доставка отчёта после отказа инструмента]:** `report submit --relayed-by --relay-reason --source-sha256` доставляет уже существующий файл отчёта и записывает отправителя в audit (#716).
- **[Диагностика sandbox_denied]:** Если ledger недоступен для записи (EROFS, EACCES, EPERM), команды возвращают `sandbox_denied` с путём и подсказкой про `sandbox.filesystem.allowWrite`, а не traceback `OSError` (#716).
- **[ChangeImpact и план проверки]:** `harness/repo_map/change_impact.py` строит по diff `base..candidate` (`git diff -M --name-status`) `ImpactSet`: `changed`, `impacted_modules` (обратное транзитивное замыкание по import-рёбрам графа Repo Map, построенного в процессе, без отсечения по бюджету токенов), `related_tests` без отсечения по первым N файлам и `unknown` с причинами. Изменение `conftest.py` любого уровня, `pyproject.toml`, `uv.lock`, `Makefile`, `.github/**`, скриптов verify, `harness/CAPABILITIES.json` или `skills/**`, удалённый или переименованный модуль с импортёрами, файл не на Python, динамический импорт, недоступный парсер (`graph-degraded`) и превышение порога `related_tests` выставляют `unknown`. Новый необязательный ключ `verification_plan_policy` (`max_related_tests`, `stages`) замораживается в batch при `batch create`; `dispatch propose` для developer-retry, code-review и qa строит `verification_plan` (стадии с `stage_id`, `kind`, `argv`, `timeout_seconds`, `selection`, `nodeids`, `environment_fingerprint`): стадия pytest получает `focused` по `ImpactSet` либо `full` при `unknown` и для qa. План лежит в brief, а его digest привязан к approval как `verification_plan_sha256`. Batch без ключа работает по замороженным командам, как раньше. Словари `selection` и `kind` зарегистрированы в `systemFields.v1` как `verification_plan.selection` и `verification_plan.stage_kind`. `repo_map_policy` замораживается в batch вместе с политикой плана, политика обязана содержать стадию `pytest`, а digest образов docker входит в `environment_fingerprint`. Файл Python, скрытый от графа политикой Repo Map или не разобранный парсером, который называет затронутый модуль, ставит `unknown` (`unseen-importer`); граф `base` при удалении или переименовании строится только по изменённым файлам. Исполнение плана, failed-only, кэши и полный clean-room gate на publish остаются за другими задачами ADR 0023 (#793).
- **[Отказ `impact_not_covered`]:** `dispatch propose` и `dispatch create` для code-review и qa отказывают с кодом 2 и перечнем тестов, если стадия pytest плана не `full` и не выбирает какой-либо из `related_tests` `ImpactSet`. Проверка машинная: текст отчёта роли её не заменяет (#793).
- **[Повтор только упавших тестов и stage evidence]:** `scripts/verify.py --worktree-cache` держит кэши mypy и pytest и JUnit предыдущего прогона в `.harness/.sandboxes/cache/<worktree-id>/<environment_fingerprint>/`: кэш другого worktree или другого `environment_fingerprint` не читается, а при `HARNESS_VERIFY_COLD` (его ставит gate runner только в clean-room QA, но не при локальном запуске через обёртку `test_summary.py`) флаг отказывает с кодом 2, так что clean-room QA остаётся холодным. `--failed-only` запускает одну стадию pytest с точными nodeid упавших тестов из JUnit того же кэша; переименованный или исчезнувший nodeid переводит выбор в `focused` (уцелевшие тестовые файлы целиком), пустой выбор и pytest, не собравший ни одного теста, дают `not_run` с кодом 5, а не `pass`. `--failed-first` по-прежнему только порядок и записывается как выбор `full`. `--evidence-dir` пишет `stage-evidence.v1` для mypy, pytest и clean-room: раздельные файлы stdout и stderr с sha256, код выхода, длительность, упавшие nodeid из JUnit и `not_run` для недошедших стадий. Одна схема (Python `harness/gate_runner/stage_evidence.py`, Rust `contracts::stage_evidence`) читается обеими сторонами по общему golden-файлу и сверяется со словарями `systemFields.v1`, поэтому Rust QA executor пишет её без изменений. Gate runner пишет такое же evidence для каждой команды (раздельные очищенные потоки, длительность, nodeid из `HARNESS_STAGE_JUNIT_XML`), помечает окружение clean-room прогона холодным и хранит документ и потоки как неизменяемые `qa-artifacts`, связанные хвостовой строкой `stage-evidence:` журнала QA в `qa run` и локальном QA. Недошедшая команда получает `not_run` всегда, а не только при `qa_preparation`, в том числе в `checks_run` отчёта QA. Failed-only, focused и кэшированные результаты publish не разрешают: его разрешает только полный clean-room прогон на итоговом SHA (#798).
- **[Egress-proxy для `network.hosts`]:** Контейнерный исполнитель `docker` принимает непустой `network.hosts`: для каждого dispatch он создаёт сеть `--internal` и отдельный sidecar из закреплённого digest образа `container.proxy_image`, а worker получает только эту сеть и переменные `HTTP_PROXY`/`HTTPS_PROXY` (в том числе строчные). Прокси пропускает HTTP и `CONNECT` только к хостам плана на портах 80 и 443, один раз резолвит имя и отказывает для loopback, link-local, unspecified, multicast и IP-литералов; остальное получает 403. Имя хоста LLM API нужно указать явно, а протоколы кроме HTTP(S), включая ssh git, не поддерживаются. При пустом списке хостов worker по-прежнему запускается с `--network none` без sidecar. Код прокси и `Dockerfile.proxy` поставляются в `.harness/container/` как часть `backend-orchestration` с контролем дрейфа; харнесс образы не собирает и не скачивает. Сеть, sidecar и worker получают метки `harness.dispatch`, `harness.repository`, `harness.plan_digest`, а сбой на любой ступени запуска удаляет все созданные объекты в обратном порядке (#706).
- **[Статус и очистка контейнерного worker]:** Для dispatch с квитанцией `docker` `dispatch status` и `dispatch wait` спрашивают движок о контейнере из `launch_id` и показывают `worker` (`state`, `exit_code`, `teardown`). Первое доказательство остановки (`exited` или `missing`) навсегда сохраняется как `worker_exit`; worker, завершившийся без report, сразу становится `stale` и поднимает существующий `stale-dispatch` с exit code. Тишина остановку не доказывает, а CLI движка, который не запустился или не ответил, даёт `unknown`, а не `missing`. Если контейнер вышел раньше записи report и подготовленный report лежит в `report_staging_path`, `stale-dispatch` рекомендует сначала `report submit --file`, а `dispatch wait` возвращает `staged_report`. `dispatch status` без `--dispatch` опрашивает движок не более чем о четырёх dispatch за чтение, остальные показывает как `not_observed`. Когда dispatch терминален, ресурсы по меткам — worker, sidecar и сеть — удаляются только после записи `worker_exit`, а работающий worker никогда не останавливается; `dispatch cancel --runtime-stopped` сохраняет квитанцию и доказательство. `harness cleanup` удаляет контейнерные ресурсы-сироты только этого репозитория, пропускает работающий worker, открытый dispatch и терминальный dispatch без доказательства (#708).
- **[Слияние hooks при установке]:** `harness init`, `adopt` и `update` сливают управляемые hook-записи в `.claude/settings.local.json` по пути команды `.claude/hooks/<скрипт>`: недостающие записи добавляются, устаревшие заменяются, записи пользователя сохраняются, `--force-seed-file` и `--force-seed-files` по-прежнему заменяют файл шаблоном целиком. Запись, которую пользователь изменил, остаётся без изменений, а команда печатает `[WARNING]` и строки `hooks conflict`; повторный `harness update` ничего не меняет в файле и печатает строки `hooks merge` и `hooks check` (#799).
- **[Адаптер hooks второго runtime]:** Установка создаёт `.codex/hooks.json` из тех же скриптов `.claude/hooks/` с критическими guards и `require-bounded-check` на `PreToolUse` для `Bash`; файл сливается по тем же правилам, а запись интеграции называется `pvmalove-suite-codex-hooks`. Hooks на `Write` и `Edit`, `EnterWorktree` и `Skill` для него не подключаются, как и `mark-qa-gate-passed` на `PostToolUse`: этот runtime вызывает `PostToolUse` и после команды с ненулевым кодом выхода, а кода выхода в payload нет, поэтому hook записал бы маркер QA-гейта для упавшего прогона, а проектные hooks работают только после доверия слою `.codex/` и каждому hook по хэшу (#799).
- **[Проверка `hooks.policy`]:** `harness health` показывает действующий профиль hooks и его источник, эскалации, наличие, исполняемость и проводку критических hooks по каждому runtime, дрейф от шаблона и события, которых нет у runtime. Критический hook без события и без проверки вне hook даёт `warn`, а не молчаливый пропуск; проект без ключа `hook_policy` по-прежнему получает профиль `standard` без миграции `.harness/project.json` (#799).
- **[Профиль `standard` в навыках]:** `start-project` и `integrate-project` называют профиль `hook_policy` в манифесте и после `harness init` проверяют `.harness/project.json` и `hooks.policy`; `hook_policy` существующего проекта остаётся за его владельцем (#799).
- **[Поведенческие hooks ChangeImpact]:** Три advisory-hooks по матрице ADR 0024, раздел 2a, работают через конверт `hook_response.py` и общее тело `change_impact_hooks.py` и никогда не блокируют. `impact-first-touch` (`PreToolUse` `Write|Edit`, профили `standard` и `strict`) один раз за операцию сообщает модели о первом касании рискованного пути, влияние которого ChangeImpact не вычисляет по графу. `targeted-check-reminder` ведёт журнал касаний и на `Stop` и `SubagentStop` напоминает отчитать targeted-проверки brief в `checks_run`, если файлы менялись после отчёта; ход он не продолжает. `sensitive-path-recheck` (только `strict`) сообщает о каждой новой правке чувствительного пути и пишет evidence-запись. Повтор того же события в той же операции (`session_id` и `agent_id`) молчит, а новый digest или новая операция дают новое уведомление; маркеры создаются через `O_EXCL` в `.harness/.sandboxes/hook-events/`. Внутренняя ошибка, нечитаемый ввод и тайм-аут 10 с разрешают действие с диагностикой и пустым stdout; критичные guards по-прежнему блокируют. Значения зарегистрированы в systemFields.v1, `harness health` показывает новые строки в `hooks.policy` (#802).
- **[Fail-closed границы профиля `strict`]:** Под `strict` `dispatch propose` и `dispatch create` для code-review и QA, `qa run` до QA-lease и `dispatch publish` до push отказывают с кодом 2 и ошибкой `strict_impact_unknown`, если кандидат меняет чувствительный путь ADR 0024, раздел 2, а VerificationPlan не доказывает его ImpactSet. Запущенный dispatch решает по политике, которую закрепил его `hook_policy_sha256`; `minimal` и `standard` на этих границах не меняются, а команды восстановления не проверяются. По решению R1 все границы проверяет одна Python-функция coordinator-а: Rust runtime пока не исполняет ни одну из этих операций, а Rust-проверку `qa run` добавит задача, которая переводит исполнение QA в Rust (#802).
- **[Остаточные ограничения hooks ChangeImpact]:** Второй runtime подключает только `targeted-check-reminder` на `Stop` и `SubagentStop`; строки `Write` и `Edit` и журнал касаний ждут адаптера `apply_patch` (#830), поэтому до него напоминание там молчит. Hardlink на чувствительный файл обходит только предупреждение `sensitive-path-recheck`: авторитетны критический `protect-hook-policy` и diff-проверка границы `strict` (#802).

### Fixed

- **[Проверка ветки перед коммитом]:** `block-direct-master` блокирует commit/push, если Git вернул ошибку при определении текущей ветки. Ответ `HEAD` с ненулевым кодом выхода больше не считается разрешённой веткой (#725).
- **[Хеш закреплённого runtime после cutover]:** Каталог `.harness/orchestration/state-snapshots` (снимок state, который делает `harness-runtime migrate`) не входит в хеш runtime, закрепляемый в batch: после cutover команды batch, спланированного до него, не отказывают с «the harness runtime changed after this batch was planned» (#801).
- **[Выходы из Настройки, Версий и Обновить Harness; секреты в Настройке]:** Номер раздела и меню на экранах Настройка, Версии конфигурации и Обновить Harness закрывают экран, как Esc, и затем открывают раздел, поэтому Главная обновляется; «Отмена» в подтверждении, поднятом с экрана Версий, оставляет пользователя на экране Версий. Значения секретов, уже записанные в `project.json` и `orchestration.json`, больше не попадают в интерфейс: страница просмотра (итоговые файлы и различия), редактор поля и различия версий показывают маску `••••••`, а применение, резервная копия, проверка устаревших данных и `reject_secrets` работают с настоящими данными.
- **[Тест-автор в полном маршруте `/implement`]:** `test-author-preflight.sh` принимает необязательный `--worktree <путь>` и отвечает `checkout_mismatch`, если путь не совпадает с checkout скрипта или аргументы неверны, поэтому in-process developer отдельного worktree больше не получает `{"status":"ok"}` для основного checkout. Внешний transport автора не включает (`transport_unsupported`); любой отказ оставляет обычный TDD с названной причиной, не blocker. Новый clean-room сценарий `full_route_worktree` проверяет, что тест не попадает в основной checkout (#768).
- **[Временные данные QA и isolated runner]:** Команды `qa run` получают собственный `TMPDIR` в `.harness/.sandboxes/runs/qa/tmp-*`, который удаляется после прогона, а helper базы данных isolated runner создаёт каталог в `TMPDIR` вместо жёстко заданного `/tmp`. Внутри bubblewrap `/tmp` теперь, как hermetic `/tmp` в Bazel, — свой пустой каталог `.harness/.sandboxes/runs/isolated-test-<id>/tmp-*` на каждый запуск, удаляемый после него, а не tmpfs. Read-only `/tmp` внешнего sandbox больше не роняет QA (#769).
- **[Падение QA из-за окружения]:** Если QA gate упал по признакам окружения (`Read-only file system` или `Permission denied` на пути вне репозитория) и в выводе нет признаков дефекта кода, `batch auto-decide` не тратит developer-retry, а останавливает автоматический путь с причиной `no-automatic-route`/`qa-environment-failure` и remedy. Настоящее падение теста по-прежнему ведёт к retry (#769).
- **[QA-lease после занятого ledger]:** `qa run`, который после взятия QA-lease встретил ledger, занятый другой операцией, больше не оставляет lease на час. Освобождение QA-lane ждёт lock до 30 секунд, затем снимает lease и запись очереди своего dispatch и возвращает dispatch в `approved`, так что тот же dispatch сразу запускается снова. Если lock так и не освободился, ошибка называет dispatch, владельца lease и время его истечения, а `qa clear-stale-lease` после истечения lease возвращает такой dispatch в `approved` (поле `restored_dispatch_state` в ответе и записи восстановления). Lease другого владельца и lease нового запуска того же dispatch не снимаются (#776).
- **[Ветка задачи ниже базы интеграции]:** `batch create` отказывает с ошибкой `branch_start_missing_base` и не записывает batch, если ветка worktree не содержит свежий tip `origin/<integration_ref>`, который batch закрепил бы как базу. Раньше tip, сдвинутый между `git worktree add` и `batch create`, становился базой, и файлы чужих коммитов попадали в `changed_files`, scope warnings и оценку риска задачи. Remedy называет `git -C <worktree> merge --ff-only <база>`; coordinator сам ветку не двигает. Batch, заменяющий брошенный (`--supersedes`), и batch маршрута conflict-resolver так не проверяются: базу в их ветку приносит их собственный маршрут (#802).

## [1.5.1] - 2026-10-18

### Added

- **[Профили проверок batch]:** Необязательный ключ `verification_profiles` в `.harness/orchestration.json` задаёт команды developer и code-review для области путей. `batch create` замораживает команды первого профиля, чьи `paths` покрывают все `--allowed-path`; при частичном покрытии или без ключа batch получает общие списки, а clean-room QA по-прежнему выполняет `verification_commands` (#756).

- **[Принудительное снятие lock]:** `ledger release-lock --force --approved-by --approved-at --reason` снимает lock при любом вердикте только по одобрению человека и пишет запись аудита с контрольной суммой, которую проверяет `ledger validate`. Ни одна политика, включая `auto`, команду не запускает; в консоли она доступна с подтверждением (#759).

- **[Причина сбоя трекера]:** `harness health --online` называет причину сбоя `git ls-remote origin`: учётные данные, TLS-сертификат, прокси или сеть. Подсказка указывает исправление, а stderr, URL `origin` и учётные данные не попадают в вывод (#626).
- **[Поиск тестов unittest]:** `harness install` больше не ставит `.harness/__init__.py`, и `python -m unittest` из корня проекта снова находит тесты проекта. `harness update` удаляет этот файл прежней установки (#626).
- **[Трекер в memory sync]:** `harness memory sync` берёт трекер из поля `tracker` в `.harness/project.json` и сохраняет подгруппы пути проекта. Команда явно адресует хост в `gh` и `glab` (#626).
- **[Closure после rebase]:** Closure перенесённых пунктов после `rebase-fix-forward` принимает только коммиты цепочки retry. Перенесённые копии прежних коммитов больше не закрывают пункты (#627).
- **[Подготовка batch в implement]:** `/implement` готовит batch только по английским агентским источникам. Русская документация больше не попадает в процедуру подготовки (#641).
- **[Ложная блокировка коммитов]:** Хук `block-direct-master` больше не блокирует команду из переменной, если слово `commit` стоит только в опции. Команды без `git commit` и `git push` проходят (#642).
- **[Ложный проход QA]:** QA gate выполнял только первую часть строковой команды вида `python a.py && python b.py`. Теперь оболочка выполняет всю цепочку, и gate видит каждый сбой.
- **[Хуки на Python 3.9]:** Хуки проекта снова работают на Python 3.9. Раньше ошибка импорта блокировала любую команду Bash.
- **[Порядок остановок auto]:** Политика `auto` ищет остановку в порядке: целостность, бюджет, маршрут. Исчерпанный бюджет больше не скрывает нарушение целостности.
- **[Блокеры review в auto]:** Политика `auto` не принимает отчёт review, если ось Standards или Spec называет `blockers`. Такой отчёт останавливает автоматический путь до решения человека.
- **[Итоговый отчёт auto]:** `batch auto-report` показывает находки координатора, которые ещё не попали в brief. Отчёт считает расход бюджета на один dispatch, а подсказка следующего шага учитывает смену политики.
- **[Очистка ledger]:** `ledger clean` больше не удаляет checkpoint живых batch. При нечитаемой записи batch команда отказывает и ничего не удаляет.
- **[Повтор после решения политики]:** Инфраструктурный повтор проверяет хеш QA-отчёта. Отчёт, изменённый после решения, больше не разрешает новый brief.
- **[Публикация dispatch]:** `dispatch publish` ограничивает время `git push` и точно сверяет ветку на remote. Зависший push больше не держит блокировку ledger.
- **[Освобождение очереди QA]:** Прерванный `qa run` освобождает lease и очередь QA. Захват очереди запуском `integration local-qa` больше не ломает восстановление dispatch.
- **[Checkpoint после сдвига базы]:** Координатор сравнивает checkpoint разработчика с базой отчёта после сдвига integration-ветки. Файлы из upstream больше не вызывают ложный отказ.
- **[Разрешение конфликтов]:** `integration resolve` после гонки с target называет созданный batch и точную команду `batch abandon`. Повтор resolve после этого проходит.
- **[Проверка локального QA]:** `integration local-qa` правильно сообщает, что ветка не основана на target. `context-package register` сравнивает `--base-commit` с фактической базой пакета.
- **[Файлы не в UTF-8]:** Координатор читает diff с файлами в устаревших кодировках без аварийного завершения. Отчёт или манифест роли не в UTF-8 даёт ошибку с инструкцией.
- **[Context Package]:** Context Package включает изменённые файлы с не-ASCII именами и вложенные ADR. Сбой Git при сборке пакета даёт ошибку с инструкцией.
- **[Устойчивость Repo Map]:** Repo Map переходит в деградированный режим при повреждённом lock, политике не в UTF-8 и ошибке чтения bundle. Кэш больше не оставляет временные файлы.
- **[Память проекта]:** Память принимает glob-шаблоны в корне проекта. Занятый индекс даёт ошибку «memory writer busy».
- **[Инвентарь интеграций]:** Установщик больше не перезаписывает нечитаемый `.harness/integrations.json`. Команда просит исправить файл и сохраняет записи проекта.
- **[Статистика доставки]:** Отчёт статистики проверяет карточку тарифов и сообщает инструкцию при нечитаемых файлах. Повреждённые записи ledger больше не прерывают отчёт.
- **[Пульт harness console]:** Экраны пульта показывают ошибку фонового запуска вместо бесконечного статуса «выполняется…». Дашборд по умолчанию перехватывает вывод команд.
- **[Сводка qa-gate]:** Сводка `qa-gate` сообщает `Status: ERROR`, если команду нельзя запустить. `diff_coverage` учитывает изменённые файлы с не-ASCII именами.

### Security

- **[Push из issue-ветки]:** Хук `block-direct-master` блокирует `git push --all`, `--branches`, `--mirror` и glob-refspec. Такие push могли обновить `main` или `integration/*`.
- **[Проверка приватных имён]:** `check_private_terms` блокирует публикацию, если Git не ответил вовремя. Раньше таймаут пропускал проверку.
- **[Каталог поколений ledger]:** Ledger отклоняет имя поколения с разделителями пути. Указатель больше не выходит за каталог ledger.
- **[Список vendor snapshot]:** Проверка vendor snapshot сверяет список файлов в `SHA256SUMS`, а не только их число. Лишняя или повторная строка больше не скрывает непроверенный файл.

- **[Перенос замечаний в ревью]:** Координатор переносит замечания в задание для проверки кода. Рецензент получает точный список пунктов для контроля (#501).
- **[Параллельное выполнение задач]:** Координатор запускает параллельные задачи в изолированных рабочих каталогах. Блокировки по общим зонам файлов сняты (#531).
- **[Регистрация проверок интеграции]:** Команда `integration prepare` связывает задачу с опубликованной веткой. Команда сохраняет неизменяемую запись проверок (#532).
- **[Автоматическое обновление ветки]:** Команда `integration refresh` обновляет ветку задачи при сдвиге целевой ветки. Разработчику не нужно переделывать работу вручную (#533).
- **[Разрешение конфликтов интеграции]:** Роль `conflict-resolver` разрешает конфликты слияния в рамках выделенного бюджета. Оператор принимает решение о продолжении сессии (#534, #537).
- **[Учет результатов CI]:** Команда `integration collect-ci` запрашивает статус внешних проверок из трекера. Успешный CI заменяет повторный запуск тяжелых локальных тестов (#535).
- **[Локальная проверка интеграции]:** Команда `integration local-qa` выполняет полный локальный контроль качества. Команда использует этот режим при отсутствии внешнего CI (#536).
- **[Навигация по шагам интеграции]:** Команда `integration next` подсказывает следующее необходимое действие. Команда `/to-pull-requests` автоматизирует подготовку ветки к слиянию (#537).
- **[Защита от утечки имен]:** Хуки и тесты блокируют публикацию приватных внутренних терминов. Проверка работает локально и в CI перед созданием коммитов (#438).

### Changed

- **[Явная адресация в CLI]:** Команды `gh` и `glab` явно указывают целевой проект. Разработчики исключили ошибки перенаправления команд в чужой репозиторий (#440).
- **[Права групп GitLab]:** Проверка доступа корректно обрабатывает права, унаследованные от родительских групп. Пользователи получают доступ без лишних настроек (#440).
- **[Понятные ошибки проверки веток]:** Хуки проверки имен веток выводят точную причину отказа. Разработчик сразу видит проблему с доступом или номером задачи (#442).
- **[Уточнение руководств проекта]:** Документация описывает только реально устанавливаемые проверки. Разработчики удалили недостоверные обещания проверок на стороне CI (#587).
- **[Обоснованные блокировки задач]:** Скилл `/to-tickets` блокирует задачи только при реальной зависимости по данным. Пересечение файлов больше не создает ложных блокеров (#538).

### Fixed

- **[Точный разбор команд GitLab]:** Хук проверки распознает команды создания MR с короткими флагами. Разработчики устранили ложные срабатывания на текст внутри комментариев и кавычек (#443).
- **[Проверка метаданных публикации]:** Хук проверяет параметры команд трекера и файлы описаний. Текст многострочных блоков ввода больше не анализируется как код (#444, #559).
- **[Создание интеграционной ветки]:** Хук защиты от прямых коммитов проверяет каждый каталог в команде. Публикация новой интеграционной ветки больше не блокируется (#446, #476).
- **[Блокировка только реальных команд]:** Хук опасных команд Git реагирует исключительно на реальный запуск. Харнесс разрешает упоминание команд в цитатах и скриптах (#566).
- **[Корректная проверка путей]:** Хуки временных файлов разрешают запись в каталоги памяти агентов. Хуки проверяют объем вывода тестов только при реальном запуске (#445).
- **[Фиксация проверок в worktree]:** Скилл `qa-gate` корректно находит конфигурацию в связанных рабочих каталогах. Скилл надежно записывает маркер прохождения тестов (#463, #600).
- **[Строгая фиксация контроля качества]:** Скрипт проверки выставляет маркер только при полном прохождении проверок. Маскировка ошибок через `|| true` больше не позволяет обойти контроль (#611).
- **[Безопасное обновление эпиков]:** Скилл `/to-tickets` обновляет описание эпика через файлы. Это предотвращает искажение текста из-за экранирования в командной строке (#447).
- **[Очистка неактивных рабочих каталогов]:** Команда жесткой очистки удаляет неактивные рабочие каталоги после отправки изменений. Мусор больше не накапливается на диске (#565).
- **[Стабильная работа на Windows]:** Установщик корректно обрабатывает неинтерактивный ввод на Windows. Команда `health` экранирует пути и безопасно запрашивает задачи (#514, #602).
- **[Устойчивость блокировок журнала]:** Координатор повторяет попытки при занятой блокировке журнала. Координатор автоматически снимает поврежденные блокировки по таймауту (#498, #525).
- **[Надежный перезапуск разработчика]:** Повторный запуск разработчика наследует контекстный пакет и инструкции. Отмененные задачи не мешают продолжению работы (#524, #540).
- **[Устранение взаимных блокировок]:** Промежуточная фиксация изменений продолжается без задержек. Разработчики устранили ошибки зависания при проверке окружения (#606).
- **[Ранние отчеты остановки]:** Координатор корректно принимает отчет об остановке до изменения файлов. Конвейер требует соблюдения всех проверок перед кодированием (#607).
