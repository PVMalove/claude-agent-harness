# Triage

Move issues on the project issue tracker through a small state machine of triage roles.

If this repo treats external pull requests as a request surface (see the issue-tracker config), triage covers them too: **a PR is an issue with attached code** — same roles, same states, same machine, with a few deltas marked "for a PR" below. Resolve a bare `#42` to an issue or PR per the tracker config.

Every comment or issue posted to the issue tracker during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — how to write durable agent briefs
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — how the `.out-of-scope/` knowledge base works

## Roles

This project uses a namespace-based label taxonomy instead of the upstream `bug`/`enhancement` categories. Every triaged issue carries exactly one label from each of the first three axes, plus context labels where they apply. If any axis ends up with zero or multiple labels, flag it and ask the maintainer before doing anything else.

**Execution mode** — who does the work:

- `hitl` — human-in-the-loop; needs architectural review, testing, or approval from the maintainer
- `afk` — away-from-keyboard; an agent can complete it alone

**Type** (`type::*`) — what kind of session this is:

- `type::spec` — specification drafting
- `type::research` — codebase or infrastructure investigation
- `type::prototype` — throwaway code to test a hypothesis
- `type::grilling` — requirements-gathering session
- `type::implementation` — writing production code
- `type::map` — a Wayfinder epic-mapping ticket (see the `wayfinder` skill; its own `wayfinder:<type>` labels apply on top of this, they're a separate namespace)

**Workflow state** (`workflow::*`) — where it sits in the pipeline:

- `workflow::ready` — fully specified, ready to be picked up (by an agent if `afk`, by the maintainer if `hitl`)
- `workflow::in-progress` — currently being worked on in an active session
- `workflow::blocked` — blocked, either by another ticket's dependency or because triage is waiting on more information from the reporter (post triage notes either way, see the needs-info template below)

**Context labels** — applied when relevant, not part of the required three:

- `epic::<name>` — this ticket belongs to a larger effort (e.g. `epic::member`). Distinct from `wayfinder:*`, which is reserved for Wayfinder's own ticket-type namespace.
- `task-report::required` — the agent must post a completion report. Apply this by default to every ticket unless the maintainer says to skip it.
- `out-of-scope` — this project's replacement for `wontfix`: the request was explicitly rejected. Applied at close time (see "Apply the outcome" below), not during normal triage.

An unlabeled issue is implicitly "needs triage" — there is no dedicated label for that state, it's just the absence of the three required axes.

For a PR, the same labels read against the attached code: `workflow::ready` + `afk` means a brief is attached and an agent should take the next step on the diff; `workflow::ready` + `hitl` means it's ready for the maintainer to review or merge.

These are the actual label strings for this repo (no translation table needed — this taxonomy fully replaces the upstream canonical roles). See `docs/agents/triage-labels.md`.

State transitions: analyze an unlabeled issue to determine its `type::*` and whether it's `hitl` or `afk`, then place it in `workflow::ready` or `workflow::blocked` (dependency or missing info). `workflow::blocked` returns to `workflow::ready` once the blocker clears or the reporter replies. The maintainer can override at any time — flag transitions that look unusual and ask before proceeding.

## Invocation

The maintainer invokes `/triage` and describes what they want in natural language. Interpret the request and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to workflow::ready"
- "What's ready for agents to pick up?"

## Show what needs attention

Query the issue tracker and present three buckets, oldest first:

1. **Unlabeled** — never triaged.
2. **Missing one of the three required axes** — partially triaged, evaluation in progress.
3. **`workflow::blocked` with reporter activity since the last triage notes** — needs re-evaluation.

When PRs are in scope, include external PRs in these buckets and tag each line `[PR]` or `[issue]`. Discovery surfaces only *external* PRs (the tracker config defines who counts as external) — a collaborator's in-flight PR is not triage work. This filter is discovery-only; an explicitly named PR is always triaged regardless of author.

Show counts and a one-line summary per item. Let the maintainer pick.

## Triage a specific issue or PR

1. **Gather context.** Read the full issue or PR (body, comments, labels, author, dates; for a PR, the diff too). Parse any prior triage notes so you don't re-ask resolved questions. Explore the codebase using the project's domain glossary, respecting ADRs in the area. Run two checks against the codebase: (a) **redundancy** — search for an existing implementation of the requested behavior by domain concept (not just the request's wording), and report where you looked. If found, it's an already-implemented rejection, handled under `out-of-scope` (step 5). (b) **prior rejection** — read `.out-of-scope/*.md` and surface any that resembles this request.

2. **Recommend.** Tell the maintainer your recommended `type::*`, execution mode (`hitl`/`afk`), and workflow state, with reasoning, plus a brief codebase summary relevant to the request — including whether it's already implemented. Wait for direction.

3. **Verify the claim.** Before any grilling, check that the claim holds up. For a bug-shaped report, reproduce it from the reporter's steps. For a PR, confirm the diff does what it claims — check it out, run the relevant tests or commands. Report what happened: confirmed (with code path), failed, or insufficient detail (a strong signal to route to `workflow::blocked` pending more info). A confirmed verification makes a much stronger agent brief.

4. **Grill (if needed).** If the request needs fleshing out, call the Skill tool twice, for "grilling" and "domain-modeling" — grill it into shape a round of questions at a time, sharpening domain terms and updating `CONTEXT.md`/ADRs inline as decisions land.

5. **Apply the outcome:**
   - `workflow::ready` + `afk` — post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)). Apply the `type::*` label for the work ahead (usually `type::implementation`).
   - `workflow::ready` + `hitl` — same brief structure, but note why it can't be delegated (judgment calls, external access, design decisions, manual testing).
   - `workflow::blocked` — post triage notes (template below): a dependency ticket to wait on, or missing info from the reporter.
   - Rejected — apply `out-of-scope` (this project's `wontfix` equivalent), remove any `workflow::*` label, and close, with the comment depending on *why*:
     - **Already implemented** — the change already exists in the codebase. Point to where it lives; do **not** write to `.out-of-scope/` (that KB is for *rejected* requests, not built ones).
     - **Rejected (bug-shaped report)** — polite explanation, then close. Skip the `.out-of-scope/` write — that KB is for rejected requests, not invalid bug reports.
     - **Rejected (feature/behavior request)** — write to `.out-of-scope/`, link to it from a comment, then close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - Still unlabeled after step 1–4 (partial progress only) — leave it unlabeled, or apply just the axis you've resolved. Optional comment noting what's settled so far.

Apply `task-report::required` by default alongside any `workflow::ready` outcome, unless the maintainer says to skip it. If the ticket is part of a larger effort, apply `epic::<name>` too.

## Quick state override

If the maintainer says "move #42 to workflow::ready", trust them and apply the label directly — ask only if the execution mode (`hitl`/`afk`) isn't already clear from context. Confirm what you're about to do (label changes, comment, close), then act. Skip grilling. If moving to `workflow::ready` + `afk` without a grilling session, ask whether they want to write an agent brief.

## Triage notes template (for `workflow::blocked`)

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, not "please provide more info".

## Resuming a previous session

If prior triage notes exist on the issue or PR, read them, check whether the reporter has answered any outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.
