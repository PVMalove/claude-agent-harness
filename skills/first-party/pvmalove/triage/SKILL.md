# Triage

Move issues on the project issue tracker through a small state machine of triage roles.

If this repo treats external pull requests as a request surface (see the issue-tracker config), triage covers them too: **a PR is an issue with attached code** — same roles, same states, same machine, with a few deltas marked "for a PR" below. Resolve a bare `#42` to an issue or PR per the tracker config.

Every comment or issue posted to the issue tracker during triage **must** start with this disclaimer:

```
> *This was generated by AI during triage.*
```

## Reference docs

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — how to write durable agent briefs
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — how the `.out-of-scope/` knowledge base works

## Roles

This project uses a namespace-based label taxonomy for state, on top of the upstream `bug`/`enhancement` category pair. Every triaged issue carries exactly one `bug`/`enhancement` label and exactly one `workflow::*` label; while it carries `workflow::specs` the execution-mode axis below doesn't apply yet (see that role), otherwise it also carries exactly one of `hitl`/`afk`. If any required axis ends up with zero or multiple labels, flag it and ask the maintainer before doing anything else.

**Category** — unchanged from upstream:

- `bug` — something is broken
- `enhancement` — new feature or improvement

**Workflow state** (`workflow::*`) — where it sits in the pipeline:

- `workflow::specs` — design/spec-writing: an epic or large task still being turned into a spec and decomposed into tickets (normally applied by `/to-spec`, not by triage directly — see below). Too early to take into development; execution mode isn't decided yet.
- `workflow::ready` — fully specified, ready to be picked up (by an agent if `afk`, by the maintainer if `hitl`)
- `workflow::in-progress` — currently being worked on in an active session
- `workflow::blocked` — blocked, either by another ticket's dependency or because triage is waiting on more information from the reporter (post triage notes either way, see the triage notes template below)

**Execution mode** — who does the work (required once an issue leaves `workflow::specs`):

- `hitl` — human-in-the-loop; needs architectural review, testing, or approval from the maintainer
- `afk` — away-from-keyboard; an agent can complete it alone

**Context labels** — applied when relevant, not part of the required axes above:

- `out-of-scope` — this project's replacement for `wontfix`: the request was explicitly rejected. Applied at close time (see "Apply the outcome" below), not during normal triage.

`task-report::required` is a context label too, but `triage` doesn't apply or read it — `/to-spec` and `/to-tickets` apply it, `/implement` acts on it. See `docs/agents/triage-labels.md`.

An unlabeled issue is implicitly "needs triage" — there is no dedicated label for that state, it's just the absence of the required axes.

For a PR, the same labels read against the attached code: `workflow::ready` + `afk` means a brief is attached and an agent should take the next step on the diff; `workflow::ready` + `hitl` means it's ready for the maintainer to review or merge.

These are the actual label strings for this repo (no translation table needed — this taxonomy fully replaces the upstream canonical state roles; the category pair is unchanged from upstream). See `docs/agents/triage-labels.md`.

Never apply upstream canonical labels (`ready-for-agent`, `ready-for-human`, `needs-triage`, `needs-info`, `wontfix`) or the retired `epic::<slug>` — if the maintainer asks to group a ticket under an epic via a label, remind them grouping is now a tracker-native link instead of a label — GitHub sub-issues, GitLab's `Part of #<map>` convention, or the local-markdown folder structure (see `docs/agents/issue-tracker.md#wayfinding-operations`).

State transitions: analyze an unlabeled issue to determine `bug`/`enhancement` and whether it's `hitl` or `afk`, then place it in `workflow::ready` or `workflow::blocked` (dependency or missing info) — or, if it's too large to specify in one triage pass, `workflow::specs` and point the maintainer at `/to-spec`. `workflow::blocked` returns to `workflow::ready` once the blocker clears or the reporter replies — that transition is `/implement`'s job, at the moment it starts work on that specific ticket, not a sweep `triage` runs over a decomposition on its own initiative. The maintainer can override at any time — flag transitions that look unusual and ask before proceeding.

## Invocation

The maintainer invokes `/triage` and describes what they want in natural language. Interpret the request and act. Examples:

- "Show me anything that needs my attention"
- "Let's look at #42" (issue or PR)
- "Move #42 to workflow::ready"
- "What's ready for agents to pick up?"

## Show what needs attention

Query the issue tracker and present three buckets, oldest first:

1. **Unlabeled** — never triaged.
2. **Missing one of the required axes** — partially triaged, evaluation in progress.
3. **`workflow::blocked` with reporter activity since the last triage notes** — needs re-evaluation.

When PRs are in scope, include external PRs in these buckets and tag each line `[PR]` or `[issue]`. Discovery surfaces only *external* PRs (the tracker config defines who counts as external) — a collaborator's in-flight PR is not triage work. This filter is discovery-only; an explicitly named PR is always triaged regardless of author.

Show counts and a one-line summary per item. Let the maintainer pick.

## Triage a specific issue or PR

1. **Gather context.** Read the full issue or PR (body, comments, labels, author, dates; for a PR, the diff too). Parse any prior triage notes so you don't re-ask resolved questions. Explore the codebase using the project's domain glossary, respecting ADRs in the area. Run two checks against the codebase: (a) **redundancy** — search for an existing implementation of the requested behavior by domain concept (not just the request's wording), and report where you looked. If found, it's an already-implemented rejection, handled under `out-of-scope` (step 5). (b) **prior rejection** — read `.out-of-scope/*.md` and surface any that resembles this request.

2. **Recommend.** Tell the maintainer your recommended category (`bug`/`enhancement`), execution mode (`hitl`/`afk`), and workflow state, with reasoning, plus a brief codebase summary relevant to the request — including whether it's already implemented. If the request is epic-sized (too big to specify in this pass), recommend `workflow::specs` and point at `/to-spec` instead of a state/mode pair. Wait for direction.

3. **Verify the claim.** Before any grilling, check that the claim holds up. For a bug, reproduce it from the reporter's steps. For a PR, confirm the diff does what it claims — check it out, run the relevant tests or commands. Report what happened: confirmed (with code path), failed, or insufficient detail (a strong signal to route to `workflow::blocked` pending more info). A confirmed verification makes a much stronger agent brief.

4. **Grill (if needed).** If the request needs fleshing out, call the Skill tool twice, for "grilling" and "domain-modeling" — grill it into shape a round of questions at a time, sharpening domain terms and updating `CONTEXT.md`/ADRs inline as decisions land.

5. **Apply the outcome:**
   - `workflow::ready` + `afk` — post an agent brief comment ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `workflow::ready` + `hitl` — same brief structure, but note why it can't be delegated (judgment calls, external access, design decisions, manual testing).
   - `workflow::specs` — point the maintainer at `/to-spec` to turn this into a proper spec and decomposition; don't write an agent brief for it.
   - `workflow::blocked` — post triage notes (template below): a dependency ticket to wait on, or missing info from the reporter.
   - Rejected — apply `out-of-scope` (this project's `wontfix` equivalent), remove any `workflow::*` label, and close, with the comment depending on *why*:
     - **Already implemented** — the change already exists in the codebase. Point to where it lives; do **not** write to `.out-of-scope/` (that KB is for *rejected* requests, not built ones).
     - **Rejected (bug-shaped report)** — polite explanation, then close. Skip the `.out-of-scope/` write — that KB is for rejected requests, not invalid bug reports.
     - **Rejected (feature/behavior request)** — write to `.out-of-scope/`, link to it from a comment, then close ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - Still unlabeled after step 1–4 (partial progress only) — leave it unlabeled, or apply just the axis you've resolved. Optional comment noting what's settled so far.

## Quick state override

If the maintainer says "move #42 to workflow::ready", trust them and apply the label directly — ask only if the execution mode (`hitl`/`afk`) isn't already clear from context. Confirm what you're about to do (label changes, comment, close), then act. Skip grilling. If moving to `workflow::ready` + `afk` without a grilling session, ask whether they want to write an agent brief.

## Triage notes template (for `workflow::blocked`)

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, not "please provide more info".

## Resuming a previous session

If prior triage notes exist on the issue or PR, read them, check whether the reporter has answered any outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.

## Роли

Этот проект использует таксономию меток на основе пространств имен для состояний, поверх оригинальной пары категорий `bug`/`enhancement`. Каждая отсортированная задача содержит ровно одну метку `bug`/`enhancement` и ровно одну метку `workflow::*`; пока она содержит `workflow::specs`, ось режима выполнения, описанная ниже, еще не применяется (см. эту роль), в противном случае она также содержит ровно одну из `hitl`/`afk`. Если по какой-либо обязательной оси оказывается ноль или несколько меток, отметьте это и спросите мейнтейнера, прежде чем делать что-либо еще.

**Категория (Category)** — без изменений по сравнению с оригиналом:

- `bug` — что-то сломано
- `enhancement` — новая функция или улучшение

**Состояние рабочего процесса (Workflow state)** (`workflow::*`) — где она находится в конвейере:

- `workflow::specs` — проектирование/написание спецификации: эпик или крупная задача, которая все еще превращается в спецификацию и разбивается на тикеты (обычно применяется через `/to-spec`, а не напрямую сортировкой — см. ниже). Слишком рано брать в разработку; режим выполнения еще не решен.
- `workflow::ready` — полностью специфицировано, готово к взятию в работу (агентом, если `afk`, мейнтейнером, если `hitl`)
- `workflow::in-progress` — в настоящее время находится в работе в активной сессии
- `workflow::blocked` — заблокировано, либо из-за зависимости от другого тикета, либо потому, что сортировка ждет дополнительной информации от автора (в любом случае опубликуйте заметки по сортировке, см. шаблон заметок по сортировке ниже)

**Режим выполнения (Execution mode)** — кто выполняет работу (обязательно, как только задача покидает `workflow::specs`):

- `hitl` — человек-в-цикле (human-in-the-loop); требует архитектурного ревью, тестирования или одобрения мейнтейнера
- `afk` — не у клавиатуры (away-from-keyboard); агент может выполнить это самостоятельно

**Контекстные метки (Context labels)** — применяются, когда это уместно, не являются частью обязательных осей выше:

- `out-of-scope` — замена `wontfix` в этом проекте: запрос был явно отклонен. Применяется во время закрытия (см. "Применение результата" ниже), а не во время обычной сортировки.

`task-report::required` также является контекстной меткой, но `triage` не применяет и не читает её — её применяют `/to-spec` и `/to-tickets`, а `/implement` действует на её основе. См. `docs/agents/triage-labels.md`.

Задача без меток неявно "нуждается в сортировке" — выделенной метки для этого состояния нет, это просто отсутствие обязательных осей.

Для PR те же метки читаются по отношению к прикрепленному коду: `workflow::ready` + `afk` означает, что бриф прикреплен, и агент должен сделать следующий шаг по диффу; `workflow::ready` + `hitl` означает, что он готов для ревью или слияния мейнтейнером.

Это фактические строки меток для этого репозитория (таблица перевода не нужна — эта таксономия полностью заменяет оригинальные канонические роли состояний; пара категорий остается неизменной по сравнению с оригиналом). См. `docs/agents/triage-labels.md`.

Никогда не применяйте оригинальные канонические метки (`ready-for-agent`, `ready-for-human`, `needs-triage`, `needs-info`, `wontfix`) или устаревшую `epic::<slug>` — если мейнтейнер просит сгруппировать тикет под эпиком с помощью метки, напомните ему, что группировка теперь является нативной ссылкой трекера, а не меткой — подзадачи GitHub (sub-issues), соглашение GitLab `Part of #<map>` или структура локальных markdown-папок (см. `docs/agents/issue-tracker.md#wayfinding-operations`).

Переходы состояний: проанализируйте задачу без меток, чтобы определить `bug`/`enhancement` и является ли она `hitl` или `afk`, затем поместите ее в `workflow::ready` или `workflow::blocked` (зависимость или отсутствующая информация) — или, если она слишком велика для спецификации за один проход сортировки, в `workflow::specs` и направьте мейнтейнера к `/to-spec`. `workflow::blocked` возвращается в `workflow::ready`, как только блокиратор исчезает или автор отвечает — этот переход является задачей `/implement` в момент начала работы над этим конкретным тикетом, а не проверкой (sweep), которую `triage` запускает по декомпозиции по собственной инициативе. Мейнтейнер может переопределить это в любое время — помечайте переходы, которые выглядят необычно, и спрашивайте, прежде чем продолжить.

## Вызов (Invocation)

Мейнтейнер вызывает `/triage` и описывает, чего он хочет, на естественном языке. Интерпретируйте запрос и действуйте. Примеры:

- "Покажи мне все, что требует моего внимания"
- "Давай посмотрим на #42" (задача или PR)
- "Перемести #42 в workflow::ready"
- "Что готово для взятия агентами?"

## Показать, что требует внимания

Сделайте запрос в трекер задач и представьте три корзины, начиная с самых старых:

1. **Без меток (Unlabeled)** — никогда не сортировались.
2. **Отсутствует одна из обязательных осей** — частично отсортированы, оценка в процессе.
3. **`workflow::blocked` с активностью автора с момента последних заметок по сортировке** — требует переоценки.

Когда PR входят в область видимости, включайте внешние PR в эти корзины и помечайте каждую строку `[PR]` или `[issue]`. Обнаружение находит только *внешние* PR (конфигурация трекера определяет, кто считается внешним) — текущий PR соавтора не является работой для сортировки. Этот фильтр предназначен только для обнаружения; явно указанный PR сортируется всегда, независимо от автора.

Покажите количество и однострочное резюме по каждому элементу. Позвольте мейнтейнеру выбрать.

## Сортировка конкретной задачи или PR

1. **Сбор контекста.** Прочитайте задачу или PR полностью (тело, комментарии, метки, автор, даты; для PR еще и дифф). Проанализируйте любые предыдущие заметки по сортировке, чтобы не задавать повторно уже решенные вопросы. Исследуйте кодовую базу, используя глоссарий предметной области проекта, соблюдая ADR (Architecture Decision Records) в данной области. Запустите две проверки по кодовой базе: (a) **избыточность** — поищите существующую реализацию запрошенного поведения по концепции предметной области (а не только по формулировке запроса) и сообщите, где вы искали. Если найдено, это отклонение как уже реализованное, обрабатываемое в рамках `out-of-scope` (шаг 5). (b) **предыдущий отказ** — прочитайте `.out-of-scope/*.md` и покажите все, что похоже на этот запрос.

2. **Рекомендация.** Сообщите мейнтейнеру вашу рекомендованную категорию (`bug`/`enhancement`), режим выполнения (`hitl`/`afk`) и состояние рабочего процесса с обоснованием, плюс краткое резюме кодовой базы, относящееся к запросу — включая то, реализован ли он уже. Если запрос размером с эпик (слишком велик для спецификации за один проход), порекомендуйте `workflow::specs` и укажите на `/to-spec` вместо пары состояние/режим. Ждите указаний.

3. **Верификация утверждения.** Перед любым детальным прояснением (grilling) убедитесь, что утверждение подтверждается. Для бага воспроизведите его по шагам автора. Для PR подтвердите, что дифф делает то, что заявляет — скачайте его, запустите соответствующие тесты или команды. Сообщите, что произошло: подтверждено (с путем в коде), не удалось или недостаточно деталей (сильный сигнал направить в `workflow::blocked` в ожидании дополнительной информации). Подтвержденная верификация делает бриф агента гораздо более сильным.

4. **Детальное прояснение (Grill) (при необходимости).** Если запрос нуждается в конкретизации, вызовите инструмент Skill дважды, для "детального прояснения" и "моделирования предметной области" — проясните его раунд за раундом вопросов, уточняя термины предметной области и обновляя `CONTEXT.md`/ADRs прямо в тексте по мере принятия решений.

5. **Применение результата:**
   - `workflow::ready` + `afk` — опубликуйте комментарий с брифом для агента ([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `workflow::ready` + `hitl` — та же структура брифа, но укажите, почему это не может быть делегировано (решения, требующие суждения, внешний доступ, проектные решения, ручное тестирование).
   - `workflow::specs` — направьте мейнтейнера к `/to-spec`, чтобы превратить это в надлежащую спецификацию и декомпозицию; не пишите для этого бриф агента.
   - `workflow::blocked` — опубликуйте заметки по сортировке (шаблон ниже): тикет зависимости, которого нужно дождаться, или недостающая информация от автора.
   - Отклонено — примените `out-of-scope` (эквивалент `wontfix` в этом проекте), удалите любую метку `workflow::*` и закройте, при этом комментарий зависит от *причины*:
     - **Уже реализовано** — изменение уже существует в кодовой базе. Укажите, где оно находится; **не** пишите в `.out-of-scope/` (эта база знаний для *отклоненных* запросов, а не для уже созданных).
     - **Отклонено (отчет, похожий на баг)** — вежливое объяснение, затем закрытие. Пропустите запись в `.out-of-scope/` — эта база знаний для отклоненных запросов, а не для недействительных отчетов о багах.
     - **Отклонено (запрос на функцию/поведение)** — напишите в `.out-of-scope/`, дайте на него ссылку в комментарии, затем закройте ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - Все еще без меток после шагов 1–4 (только частичный прогресс) — оставьте без меток или примените только ту ось, которую вы разрешили. Опциональный комментарий, отмечающий, что решено на данный момент.

## Быстрое переопределение состояния

Если мейнтейнер говорит "перемести #42 в workflow::ready", доверьтесь ему и примените метку напрямую — спрашивайте только в том случае, если режим выполнения (`hitl`/`afk`) еще не ясен из контекста. Подтвердите, что вы собираетесь сделать (изменения меток, комментарий, закрытие), затем действуйте. Пропустите детальное прояснение. Если перемещаете в `workflow::ready` + `afk` без сессии прояснения, спросите, хотят ли они, чтобы вы написали бриф для агента.

## Шаблон заметок по сортировке (для `workflow::blocked`)

```markdown
## Заметки по сортировке (Triage Notes)

**Что мы установили на данный момент:**

- пункт 1
- пункт 2

**Что нам все еще нужно от вас (@автор):**

- вопрос 1
- вопрос 2
```

Зафиксируйте всё решенное во время прояснения в разделе "установили на данный момент", чтобы работа не потерялась. Вопросы должны быть конкретными и выполнимыми, а не просто "пожалуйста, предоставьте больше информации".

## Возобновление предыдущей сессии

Если в задаче или PR есть предыдущие заметки по сортировке, прочитайте их, проверьте, ответил ли автор на какие-либо открытые вопросы, и представьте обновленную картину, прежде чем продолжить. Не задавайте повторно уже решенные вопросы.
-->
